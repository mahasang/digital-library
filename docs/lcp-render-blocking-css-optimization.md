## 1. Render-blocking CSS resource ที่แน่ชัด

ตรวจสอบ HTML/HTTP header ที่ตอบกลับจริงจาก production build (`npm run build && npm run start -- -p 3001`):

```
Link: </_next/static/css/2795e9b72fcb6529.css>; rel=preload; as="style"
<link rel="stylesheet" href="/_next/static/css/2795e9b72fcb6529.css" data-precedence="next"/>
```

- **มีไฟล์ CSS เดียวเท่านั้น** สำหรับทั้ง `/` และ `/research` (เนื้อหาเดียวกันทุก byte — content hash เดียวกัน) ไม่มี CSS แยกต่อ route
- ขนาดจริง (uncompressed): **48,637 bytes** — ตัวเลข "10,549 bytes" ในรายงานเดิมคือขนาดหลังบีบอัด (gzip/brotli) ที่ Lighthouse วัดจาก network transfer จริง (CSS บีบอัดได้ดีเพราะมี pattern ซ้ำเยอะ เช่น hex color/CSS variable declaration)
- **Cache-Control**: `public, max-age=31536000, immutable` — cache แบบยาวสุดเท่าที่ทำได้แล้ว (1 ปี, immutable) ผ่านกลไก content-hash filename ของ Next.js เอง

## 2. ประเภทของ CSS (Requirement 2)

ตรวจสอบ `app/globals.css` (ไฟล์เดียวที่ import เข้า `app/layout.tsx` — เป็น**ไฟล์ CSS ไฟล์เดียวในทั้งโปรเจกต์**, ยืนยันด้วย `grep -rn "import.*\.css"` ทั่วทั้ง `app/`, `components/`, `lib/`) ประกอบด้วย:

| ส่วน | สัดส่วนโดยประมาณ | หมวดหมู่ |
| --- | --- | --- |
| `@tailwind base/components/utilities` | ส่วนใหญ่ของไฟล์ | First-party, generated by Tailwind (purge ตาม `content` ใน `tailwind.config.ts` ที่ scope ไว้เฉพาะ `app/**`/`components/**` ถูกต้องอยู่แล้ว) |
| Design token (`--color-*`, `--gray-*`, ฯลฯ) × 3 สถานะ (light/dark-media/dark-explicit) | ~150 บรรทัด | First-party, **theme tokens ที่ห้ามลบ** |
| `:focus-visible`, `.skip-link` | ~30 บรรทัด | First-party, **accessibility styles ที่ห้ามลบ** |
| `.line-clamp-*` | ~20 บรรทัด | First-party utility (ใช้จริงใน `ResearchCard`) |
| `.cover-tone-0` ถึง `-7` × light/dark | ~40 บรรทัด | First-party — **ใช้จริงใน viewport แรกของ `/research`** (การ์ดที่ไม่มีปกจริงเรียก `CategoryCover`) จึงย้ายออกจาก critical path ไม่ได้ |
| `.reader-shell[data-reader-theme]` | ~20 บรรทัด | First-party — ใช้เฉพาะหน้า `/research/[id]/read` เท่านั้น (ไม่เกี่ยวกับ `/research`/`/` เลย) |

## 3. LCP element, parent layout, font loading (Requirement 3)

**LCP element** (ยืนยันซ้ำจาก `lcp-breakdown-insight` audit): ข้อความบรรยายใต้หัวข้อ H1 ของหน้า `/research`

```html
<p class="mt-1.5 text-sm text-gray-500">
  ค้นหาและกรองงานวิจัยขององค์กรจากคลังเอกสารดิจิทัล — รวมค้นหาเนื้อหาภายในไฟล์ PDF
</p>
```

**Parent layout** (`app/research/page.tsx`): `<section className="py-10 sm:py-12"><Container><div className="mb-8"><h1>...</h1><p>...</p></div><Suspense>...</Suspense></Container></section>` — โครงสร้างตื้นมาก ไม่มี flex/grid ที่ซับซ้อนเหนือ element นี้เลย **ไม่พบ layout dependency ที่ผิดปกติเฉพาะจุดของ element นี้เอง**

**Font loading**: `Noto_Sans_Thai` จาก `next/font/google` (`app/layout.tsx`) ตั้งค่า `display: "swap"` **ถูกต้องอยู่แล้ว** — `next/font` self-host ฟอนต์ที่ build time (ไม่มี request ไปโดเมนภายนอกเลย, ไม่ block ด้วย `@font-face` แบบเดิม) ตรวจสอบ `font-display-insight` audit (รายงานก่อนหน้า) ได้ **score 1, ไม่มีปัญหา** — ฟอนต์ไม่ใช่สาเหตุ

**สาเหตุของความล่าช้า**: `lcp-breakdown-insight` เดิมชี้ว่า `elementRenderDelay` (~1,241ms จากทั้งหมด) มาจาก `mainthread-work-breakdown` ที่ "Style & Layout" (644ms) เป็นตัวใหญ่ที่สุด — **เป็นต้นทุนของการคำนวณ style/layout ของทั้งหน้า** (นับรวม `ResearchExplorer`/`FilterBar`/`ResearchGrid`/การ์ดหลายใบ) ไม่ใช่ต้นทุนเฉพาะของ paragraph นี้เอง เพราะ browser ต้องมี CSSOM ที่สมบูรณ์ (รอ CSS โหลดเสร็จ) ก่อนจึงจะเริ่มคำนวณ layout ของ**ทุก**อย่างบนหน้ารวมถึงข้อความนี้ได้ — เป็นกลไกปกติของ render-blocking CSS ไม่ใช่ความผิดปกติเฉพาะจุด

## 4. CSS inlining จะกระทบ caching หรือไม่ (Requirement 4)

**กระทบแน่นอนและเป็นผลลบ** — เหตุผล:

- ตอนนี้: browser ดาวน์โหลด CSS ไฟล์นี้**ครั้งเดียว** (จากหน้าแรกที่เข้า ไม่ว่าจะเป็นหน้าไหนก่อน) แล้ว**ใช้ซ้ำได้ทันทีจาก cache** (ไม่มีการดาวน์โหลดซ้ำเลย) สำหรับการเข้าหน้าอื่นๆ ทุกหน้าในเว็บไซต์ นานสูงสุด 1 ปี (`immutable`) เพราะใช้ content-hash filename เดียวกันทุก route
- ถ้า inline CSS เข้าไปใน HTML โดยตรง: **ทุก HTML response ของทุก route ต้องพก CSS ก้อนนี้ไปด้วยทุกครั้ง** (inline `<style>` cache แยกจาก HTML ไม่ได้ ต้องดาวน์โหลดมาพร้อม HTML เอกสารเสมอ) ทำให้การนำทางข้ามหน้า (ซึ่งเกิดบ่อยกว่าการเข้าหน้าแรกครั้งเดียวมาก สำหรับผู้ใช้จริงที่เรียกดูหลายหน้า) **แย่ลง** แทนที่จะดีขึ้น เพราะเสียประโยชน์ของการ cache ข้าม navigation ไปทั้งหมด
- นี่คือเหตุผลที่ตรงกับคำเตือนของงานนี้เองที่ว่า **"Do not blindly inline all CSS"** — การ inline CSS ทั้งก้อนเข้าไปในทุกหน้าจะทำให้ประโยชน์จากการ cache แบบ 1 ปีที่มีอยู่แล้วหายไปทันที

**ไม่มี duplicate CSS**: เพราะมีไฟล์ CSS เดียวสำหรับทั้งแอป (ไม่มี route-specific CSS chunk แยก) การ inline ก็จะไม่ได้สร้าง "ซ้ำ" กับตัวมันเองในความหมายนั้น แต่จะสร้าง**ภาระซ้ำ**ในทุก HTML response แทน ซึ่งเป็นปัญหาคนละแบบแต่ร้ายแรงไม่ต่างกัน

## 6. ทำไมจึงไม่แก้โค้ดในงานนี้ — สรุปแต่ละทางเลือกที่งานนี้อนุญาต

ตรวจสอบทางเลือกทั้งหมดที่ระบุไว้ว่าเป็น "low-risk changes ที่ควรพิจารณา" ทีละข้อ:

| ทางเลือก | ผลตรวจสอบ |
| --- | --- |
| ใช้ `next/font` ให้ถูกต้อง (ถ้าฟอนต์เป็นสาเหตุ) | ✅ ใช้ถูกต้องอยู่แล้ว — ฟอนต์ไม่ใช่สาเหตุ (หัวข้อ 3, 5) ไม่มีอะไรต้องแก้ |
| Preload เฉพาะ font/resource ที่พิสูจน์แล้วว่าจำเป็นต่อ LCP | LCP element เป็น**ข้อความ** ไม่ใช่รูปภาพ ไม่มี resource เฉพาะให้ preload เพิ่มเติม — Next.js preload CSS หลักด้วย `Link` header อยู่แล้ว (หัวข้อ 1) |
| ลบ stylesheet import ที่ไม่จำเป็นออกจาก public layout | ตรวจแล้วมี CSS import เดียวในทั้งโปรเจกต์ (`app/globals.css`) และทุกส่วนในนั้นเข้าเงื่อนไข "ห้ามลบ" ของงานนี้เอง (theme token/focus-visible/dark mode/a11y/Tailwind) — ไม่มี import ที่ "ไม่จำเป็น" ให้ลบ |
| Defer non-critical third-party styles | ไม่มี third-party stylesheet ใดๆ ในโปรเจกต์เลย — ไม่มีอะไรให้ defer |
| ลด CSS ที่ไม่ได้ใช้จริงบน public route | Lighthouse `unused-css-rules` ให้ score 1 (ไม่พบปัญหา) มาก่อนแล้ว — ยืนยันซ้ำว่า CSS ที่มีถูกใช้จริงเกือบทั้งหมด |
| ลดความซับซ้อนของ layout/style dependency ที่หน่วง LCP | ตรวจ DOM ancestor ของ LCP element แล้วพบว่าตื้นมาก ไม่มีจุดผิดปกติเฉพาะจุด (หัวข้อ 3) — ความล่าช้าเป็นต้นทุนโดยรวมของ CSS ทั้งหน้า ไม่ใช่ของ element นี้โดยเฉพาะ |

**ทางเลือกเดียวที่พอมีจริง** (ไม่ได้อยู่ในรายการที่ระบุไว้ แต่พิจารณาเพิ่มเติมเอง): แยก `.reader-shell[data-reader-theme]` (ใช้เฉพาะหน้า `/read`, ไม่เกี่ยวกับ `/research`/`/` เลย) ออกเป็นไฟล์ CSS ต่างหาก — **ปฏิเสธทางเลือกนี้เพราะ**:
1. ขนาดเล็กมาก (~20 บรรทัด จากทั้งหมด 327 บรรทัดของไฟล์) คาดว่าน้อยกว่า 1 KB หลังบีบอัด — เล็กกว่าความแปรปรวนตามธรรมชาติของการวัด Lighthouse เอง (TBT เคยวัดต่างกันถึง 230ms/30ms/60ms จาก build เดียวกันเป๊ะในการทดสอบก่อนหน้านี้ — ดู `docs/research-page-performance-audit.md`) จึงแทบเป็นไปไม่ได้ที่จะวัดผลต่างได้จริงอย่างมีนัยสำคัญ
2. เพิ่ม CSS file ที่สองให้ต้องจัดการ (versioning, cache invalidation แยก) แลกกับผลประโยชน์ที่วัดไม่ได้จริง — ไม่ผ่านเกณฑ์ "low-risk, **measured**" ของงานนี้เอง (การเปลี่ยนแปลงต้องได้สัดส่วนกับผลที่วัดได้จริง ไม่ใช่แค่ทฤษฎี)
3. เสี่ยงเรื่อง dark mode/theme token synchronization โดยไม่จำเป็น (`.reader-shell` ใช้ค่าเดียวกับ `--color-*` tokens หลัก — ต้องระวังไม่ให้สองไฟล์ desync กันในอนาคต) แลกกับผลที่แทบวัดไม่ได้

**สรุป**: `app/globals.css` **มีขนาดเล็กและ cacheable อยู่แล้วจริงๆ** ตามเงื่อนไขที่งานนี้ระบุไว้สำหรับกรณี "ไม่ต้องแก้" — Next.js จัดการ preload/precedence/caching ให้อย่างถูกต้องตามมาตรฐานอยู่แล้วโดยไม่ต้องตั้งค่าเพิ่ม (ไม่ได้เปิด `experimental.optimizeCss`/critters ซึ่งจะเป็นการ inline CSS อัตโนมัติแบบที่งานนี้เตือนไว้ไม่ให้ทำ) การเปลี่ยนแปลงใดๆ ที่เหลืออยู่ในขอบเขตที่อนุญาตจะกระทบเนื้อหาที่ต้องห้ามแตะ หรือให้ผลลัพธ์ที่เล็กเกินกว่าจะวัดได้จริง จึง**ไม่มีการแก้ไขโค้ดในงานนี้**

**หมายเหตุ — 1 เทสต์ไม่เกี่ยวข้องที่ fail ซ้ำ**: `e2e/public-home-cache.spec.ts` (ทดสอบ cache invalidation ของหมวดหมู่ — ไม่เกี่ยวกับ CSS/LCP เลย) fail 3 ครั้งติดต่อกันระหว่างการทดสอบรอบนี้ (รวมถึงตอนรันแยกเดี่ยวและหลัง restart dev server ใหม่สะอาด) ตรวจสอบแล้วว่า **ไม่ใช่ regression จากงานนี้**: (1) `git status` ยืนยันไม่มีการแก้โค้ดเลยในงานนี้ (2) `dev-server.log` แสดงว่า POST สร้าง/ลบหมวดหมู่ทั้งสองครั้งตอบ `200` สำเร็จ (แค่การตรวจสอบฝั่ง client ว่าเห็นผลบนหน้าแรกภายใน 20 วินาทีที่ timeout ไป ไม่ใช่ operation จริงล้มเหลว) (3) ตรวจ `docker ps` พบว่า `supabase_vector_Ebooks` (container log-aggregator ของ local Supabase) อยู่ในสถานะ crash-loop ("Restarting" ซ้ำๆ) ขณะที่ container อื่นที่เกี่ยวข้องกับ operation นี้จริง (`db`/`rest`/`auth`/`realtime`) ยังปกติดี — สอดคล้องกับสภาพแวดล้อม local ที่ทำงานต่อเนื่องมาหลายชั่วโมงในเซสชันนี้ ไม่ใช่ปัญหาของโค้ด **ไม่ได้แก้ไข/restart container ใดๆ ในงานนี้เพราะอยู่นอกขอบเขตงาน CSS/LCP โดยตรง** — แนะนำให้ตรวจสอบ local Supabase stack แยกต่างหากหากยังพบปัญหานี้ต่อเนื่อง

## 9. คำแนะนำที่พิจารณาแล้วแต่ตั้งใจไม่ทำ (Requirement: "any recommendation deliberately not implemented and why")

1. **แยก `.reader-shell` tokens ออกจาก `globals.css`** — ปฏิเสธ เหตุผลเต็มอยู่ในหัวข้อ 6 (ผลเล็กเกินกว่าจะวัดได้จริง, เพิ่มความเสี่ยง desync ของ theme token, ไม่คุ้มกับความซับซ้อนที่เพิ่ม)
2. **เปิด `experimental.optimizeCss` (critters) ใน `next.config.ts`** — ปฏิเสธโดยตรง เพราะเป็นกลไก inline critical CSS อัตโนมัติแบบ heuristic ที่งานนี้เตือนไว้ชัดเจนว่าไม่ให้ทำ ("Do not blindly inline all CSS") อีกทั้งยังเป็น experimental feature ที่ Next.js เองไม่รับประกันความเสถียร ต้องเพิ่ม dependency (`critters`) ใหม่ และจะกระทบ caching ตามที่วิเคราะห์ไว้ในหัวข้อ 4
3. **Manual critical-CSS extraction (เขียนเอง แยก above-the-fold CSS ออกจากส่วนที่เหลือ)** — ปฏิเสธ เพราะเนื้อหาเกือบทั้งหมดของ `globals.css` (theme token, Tailwind utilities ที่การ์ด/ปุ่ม/ฟอร์มใช้จริงในหน้าแรกที่เห็น) **เป็น critical path จริงอยู่แล้ว** ไม่ใช่ CSS ส่วนเกิน — การแยกจะต้อง maintain สอง source of truth (critical vs non-critical) ด้วยมือทุกครั้งที่แก้ theme token ในอนาคต ความเสี่ยงสูงกว่าประโยชน์ที่ได้มาก
4. **บีบอัด/ลด token count ในระบบสี** (เช่น ลดจำนวน shade ของแต่ละสีจาก 10 เหลือน้อยกว่า) — ปฏิเสธ เพราะเป็นการเปลี่ยน design system/theme token โดยตรง ซึ่งงานนี้ห้ามไว้ชัดเจน ("Do not remove... theme tokens")
