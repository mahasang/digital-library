# Production Checklist (Functional & Security QA)

เอกสารนี้เป็นรายการตรวจสอบเชิงฟังก์ชัน/ความปลอดภัยก่อนเปิดใช้งานจริง เน้น
การทดสอบตามบทบาทและ Super Admin Dashboard โดยเฉพาะ — สำหรับขั้นตอน deploy
บน Vercel (env vars, migration, Storage buckets) ดูที่
[`deployment-checklist.md`](deployment-checklist.md) แทน เอกสารทั้งสองใช้คู่กัน

## 1. ทดสอบตามบทบาท (Role-by-role)

ทดสอบด้วยบัญชีจริงอย่างน้อย 1 บัญชีต่อบทบาท (สมัครผ่าน `/register` แล้วปรับ
บทบาทตามต้องการผ่าน SQL หรือ `/dashboard/users`/`/superadmin/users`):

- [ ] **Guest**: ค้นหา/ดูรายละเอียดงานวิจัยที่เป็น public ได้โดยไม่ต้องล็อกอิน
      เข้าหน้าที่ต้องล็อกอิน (`/account`, `/favorites` ฯลฯ) แล้วถูกพาไป `/login`
- [ ] **Member**: อ่าน/ดาวน์โหลดงานวิจัยระดับ member_only ได้, บันทึกรายการโปรดได้,
      เข้า `/submit-research` หรือ `/dashboard` ไม่ได้ (ถูกพาไป `/403` หรือ `/login`)
- [ ] **Staff**: ส่งงานวิจัยได้, ดูสถานะที่ `/my-submissions` ได้, เข้า `/dashboard`
      ไม่ได้
- [ ] **Librarian**: อนุมัติ/ปฏิเสธ/ขอแก้ไข/เผยแพร่/เก็บถาวรงานวิจัยได้ที่
      `/dashboard/approvals`, เข้า `/dashboard/users` และ `/superadmin` ไม่ได้
- [ ] **Admin**: จัดการผู้ใช้/บทบาท (member–admin) ที่ `/dashboard/users` ได้,
      ดู Audit Log ที่ `/dashboard/audit-logs` ได้, **เข้า `/superadmin/*` ไม่ได้
      (ทดสอบทุก sub-route ที่มี — ถูกพาไป `/403` เสมอ)**
- [ ] **Super Admin**: เข้า `/superadmin/*` ได้ทุกหน้า, เห็นเมนู "Super Admin"
      ในหน้า Header, เห็นสิทธิ์ทั้งหมดของ Admin ด้วย (เช่น `/dashboard` ยังใช้ได้)

## 2. RLS และ Server-side Authorization

- [ ] ผู้ใช้ที่ไม่มีสิทธิ์พอ เรียก Server Action ตรง (ไม่ผ่าน UI) แล้วถูกปฏิเสธ
      ด้วยข้อความทั่วไป ไม่ใช่ error ดิบของ Postgres
- [ ] Admin (rank 40) แก้ไขฟิลด์ใหม่ในตาราง `settings` (เช่น `registration_enabled`)
      ผ่าน API โดยตรงไม่ได้ — ถูก RLS trigger ปฏิเสธ แต่ยังแก้ไขฟิลด์เดิม
      (ชื่อระบบ, โลโก้ URL, ข้อมูลติดต่อ) ผ่าน `/dashboard/settings` ได้ตามปกติ
- [ ] Admin มอบ/ถอดถอนบทบาท `super_admin` ให้ผู้ใช้อื่นไม่ได้ (RLS ปฏิเสธ)
- [ ] ถอดถอนบทบาท Super Admin คนสุดท้ายในระบบไม่ได้ (ทั้งผ่าน UI และ SQL โดยตรง)

## 3. การตั้งค่าหลายบทบาท (Multi-role)

- [ ] ที่ `/superadmin/users/[id]` ติ๊กเพิ่มบทบาทที่ 2 ให้ผู้ใช้คนเดียวกันได้
      (เช่น Staff + Librarian พร้อมกัน) โดยไม่ลบบทบาทเดิม — บทบาทเหล่านี้
      (member/staff/librarian/admin) มีผลทันทีไม่ต้องยืนยันซ้ำ
- [ ] ถอนติ๊กบทบาทออกได้ทีละบทบาท โดยไม่กระทบบทบาทอื่นที่มีอยู่
- [ ] สิทธิ์ที่ได้จริงหลังมีหลายบทบาทตรงกับ rank สูงสุดที่มี (ทดสอบเข้าหน้าที่
      บทบาทสูงกว่าปลดล็อกได้จริง)
- [ ] **มอบ/ถอดถอนสิทธิ์ Super Admin**: คลิก checkbox แถว "Super Admin" ที่
      `/superadmin/users/[id]` ต้องเปิดกล่องยืนยันเสมอ (ไม่เปลี่ยนสถานะทันที
      เหมือนบทบาทอื่น) — ปุ่มยืนยันต้องกดไม่ได้จนกว่าจะพิมพ์ `CONFIRM` หรือ
      อีเมลผู้ใช้เป้าหมายให้ตรงกัน พิมพ์ผิดแล้วลองส่งต้องถูกปฏิเสธด้วยข้อความ
      ทั่วไป (ไม่ใช่ error ดิบ)
- [ ] ถอดถอนสิทธิ์ Super Admin ของผู้ใช้ที่ไม่ใช่คนสุดท้าย → สำเร็จ และปรากฏใน
      "ประวัติที่ถูกดำเนินการกับบัญชีนี้" พร้อมผู้กระทำ/เหตุผล (ถ้าใส่)
- [ ] ถอดถอนสิทธิ์ Super Admin คนสุดท้ายในระบบ (ทั้งผ่าน UI นี้และ SQL โดยตรง)
      → ต้องถูกปฏิเสธเสมอ พร้อมข้อความอธิบายชัดเจน ไม่ใช่ error ดิบ

## 4. อัปโหลดโลโก้/Favicon และลบไฟล์ค้าง

- [ ] ที่ `/superadmin/system-settings` อัปโหลดไฟล์โลโก้ใหม่ (PNG/JPEG/WEBP/SVG,
      ไม่เกิน 2 MB) สำเร็จ และรูปแสดงผลจริงในหน้า Header หลังบันทึก
- [ ] อัปโหลดไฟล์ที่เกินขนาด/ผิดชนิดแล้วถูกปฏิเสธก่อนอัปโหลดจริง (client-side)
- [ ] ที่ `/superadmin/storage` เห็นไฟล์ที่ไม่มีการอ้างอิงในฐานข้อมูล
      (เช่น หลังแก้ไขงานวิจัยแล้วแทนที่ไฟล์ PDF เดิม)
- [ ] กดลบไฟล์ค้าง ต้องมี dialog ยืนยันก่อนเสมอ และลบสำเร็จจริงหลังยืนยัน
- [ ] พยายามลบไฟล์ที่เพิ่งถูกอ้างอิงใช้งาน (ทดสอบ race condition) ถูกปฏิเสธ
      พร้อมข้อความอธิบาย ไม่ลบไฟล์ที่ยังใช้งานอยู่
- [ ] **ทดสอบไฟล์นามสกุลไม่ตรงกับ MIME type**: เปลี่ยนนามสกุลไฟล์ที่ไม่ใช่ PDF
      (เช่น เปลี่ยน `.png` เป็น `.pdf` โดยไม่แปลงไฟล์จริง) แล้วอัปโหลดที่
      `/submit-research` → ต้องถูกปฏิเสธทั้งฝั่ง client (ก่อนอัปโหลด) และ
      ฝั่ง server (แม้พยายามส่ง path ตรงผ่าน Server Action ข้ามการตรวจสอบ
      ฝั่ง client) — ดู [`file-security.md`](file-security.md) สำหรับขอบเขต/
      ข้อจำกัดของการตรวจสอบนี้ (ยังไม่มี malware scanning)

## 5. ข้อความ Error ที่ผู้ใช้เห็น

- [ ] จำลอง error จริง (เช่น ตัดการเชื่อมต่อฐานข้อมูลชั่วคราว หรือใส่ข้อมูล
      ที่ทำให้ constraint ล้มเหลว) แล้วตรวจสอบว่าข้อความที่ผู้ใช้เห็นเป็น
      ภาษาไทยทั่วไป **ไม่มี**: SQL query, stack trace, ชื่อ constraint/column
      ดิบ, connection string, token, หรือ secret ใดๆ
- [ ] เปิด DevTools Network tab ตรวจสอบ response ของ Server Action/API ที่ error
      ว่าไม่มีข้อมูลอ่อนไหวหลุดออกมาในตัว response เอง

## 6. CAPTCHA (Cloudflare Turnstile)

ทดสอบเฉพาะเมื่อตั้งค่า `NEXT_PUBLIC_TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY`
ไว้แล้ว:

- [ ] เปิดสวิตช์ "เปิดใช้งาน CAPTCHA" ที่ `/superadmin/security` → widget ปรากฏ
      จริงที่ `/register` และ `/submit-research`
- [ ] สมัครสมาชิก/ส่งงานวิจัยโดยไม่ยืนยัน widget → ปุ่มส่งกดไม่ได้/ถูกปฏิเสธ
      (ไม่สร้างบัญชี/ไม่บันทึกงานวิจัย)
- [ ] ยืนยัน widget สำเร็จแล้วส่งฟอร์ม → สร้างบัญชี/บันทึกงานวิจัยได้ปกติ
- [ ] ปิดสวิตช์ CAPTCHA → widget หายไป ส่งฟอร์มได้โดยไม่ต้องยืนยัน
- [ ] เปิดสวิตช์ไว้แต่ลบ/ไม่ได้ตั้งค่าคีย์ → ระบบต้อง **fail-open** (widget ไม่
      แสดง แต่ฟอร์มยังส่งได้ปกติ ไม่ใช่ error หรือหน้าใช้งานไม่ได้)

## 7. MFA (ยืนยันตัวตนสองขั้นตอน)

**MFA เป็นข้อบังคับสำหรับบทบาท Super Admin เท่านั้น** (ตั้งแต่ช่วงที่ 16) —
บทบาทอื่น (Member/Staff/Librarian/Admin) MFA ยังเป็นทางเลือกเหมือนเดิมทุก
ประการ ดูรายละเอียดเต็มที่ [`superadmin-guide.md`](superadmin-guide.md) หัวข้อ 14

- [ ] ที่ `/account` เพิ่มอุปกรณ์ยืนยันตัวตน (TOTP) สำเร็จ (สแกน QR ด้วยแอป
      เช่น Google Authenticator แล้วกรอกรหัส 6 หลักถูกต้อง) — ทดสอบกับบัญชี
      บทบาทใดก็ได้ ใช้งานได้เหมือนกันทุกบทบาท
- [ ] **Super Admin ที่ยังไม่มี MFA ที่ verified แล้ว พยายามเข้า `/superadmin`
      ตรงๆ → ต้องถูกเด้งไปหน้า `/setup-mfa` ทันที** (ไม่ใช่แค่แบนเนอร์เตือน —
      เข้าหน้าอื่นใน `/superadmin/*` ไม่ได้เลยจนกว่าจะตั้งค่าสำเร็จ)
- [ ] ตั้งค่า MFA ที่ `/setup-mfa` สำเร็จ → ระบบพาไปหน้าที่ตั้งใจจะเข้าโดย
      อัตโนมัติ
- [ ] Super Admin ที่ตั้งค่า MFA แล้ว **ล็อกเอาต์แล้วล็อกอินใหม่** → พยายาม
      เข้า `/superadmin/*` ต้องถูกเด้งไปหน้า `/mfa-challenge` (ไม่ใช่
      `/setup-mfa` อีกแล้ว) กรอกรหัสถูกต้องแล้วจึงเข้าหน้าที่ต้องการได้จริง
- [ ] เรียก Server Action ของ `/superadmin/*` โดยตรง (ไม่ผ่านการนำทางหน้าปกติ)
      ตอนเซสชันยังเป็น `aal1` → ต้องถูกปฏิเสธเสมอ (`requireMinRank(50)` ตรวจ
      `aal2` ซ้ำอีกชั้นเสมอ)
- [ ] ผู้ใช้บทบาทอื่น (Member/Staff/Librarian/Admin) ที่ **ยังไม่ได้ตั้งค่า
      MFA** ใช้งานหน้าของตัวเอง (`/dashboard/*` เป็นต้น) ได้ตามปกติทันที โดย
      ไม่ถูกเด้งไปหน้ายืนยันใดๆ เลย (การบังคับ MFA จำกัดเฉพาะ `/superadmin/*`
      เท่านั้น)
- [ ] ลบอุปกรณ์ MFA ที่ `/account` สำเร็จ แล้วล็อกอินใหม่ไม่ถูกเด้งไปหน้า
      ยืนยันอีกต่อไป (ยกเว้น Super Admin ซึ่งจะถูกเด้งไป `/setup-mfa` ทันที
      เพราะกลับไปอยู่สถานะ "ไม่มี verified factor")
- [ ] **รีเซ็ต MFA ให้ผู้ใช้อื่น**: ที่ `/superadmin/users/[id]` กด "รีเซ็ต
      MFA" ให้บัญชีทดสอบที่มี MFA อยู่แล้ว (ต้องพิมพ์อีเมลผู้ใช้เป้าหมายยืนยัน
      ขั้นที่ 1 แล้วพิมพ์ `RESET MFA` + ระบุเหตุผลยืนยันขั้นที่ 2) → อุปกรณ์เดิม
      ถูกลบ, ผู้ใช้ถูกออกจากระบบทันทีทุกเซสชัน (ถ้าเดิม verified แล้ว), และถ้า
      เป็นบัญชี Super Admin จะถูกเด้งไป `/setup-mfa` ทันทีในการเข้าครั้งถัดไป
- [ ] Super Admin รีเซ็ต MFA ของตัวเองไม่ได้ (ปุ่มถูกซ่อน และ Server Action
      ปฏิเสธซ้ำอีกชั้นหากพยายามเรียกตรง)

## 8. จัดลำดับหมวดหมู่/หน่วยงาน (Drag-and-Drop)

- [ ] ที่ `/superadmin/categories` ลากหมวดหมู่หลักเพื่อจัดลำดับใหม่ → บันทึก
      สำเร็จ และลำดับที่หน้าแรก/`/research` เปลี่ยนตามจริง
- [ ] ลากหมวดหมู่ย่อยข้ามไปหมวดหมู่หลักอื่น → parent เปลี่ยนจริง ปรากฏถูกกลุ่ม
- [ ] ใช้ปุ่มเลื่อนขึ้น/ลง (แทนการลาก) → ทำงานได้ผลลัพธ์เดียวกับการลาก
- [ ] ใช้เมนูเลือกหมวดหมู่หลักปลายทาง (แทนการลากข้ามกลุ่ม) → ทำงานได้ผลลัพธ์
      เดียวกัน
- [ ] ที่ `/superadmin/organizations` ทดสอบลากวาง/ปุ่มเลื่อนขึ้นลงเช่นเดียวกัน
      → ลำดับมีผลกับตัวเลือกหน่วยงานในฟอร์มส่งงานวิจัยด้วย
- [ ] ล็อกอินด้วยบัญชี Librarian/Admin (rank < 50) แล้วเรียก RPC จัดลำดับตรง
      (เช่นผ่าน DevTools/Postman ไปที่ `/rest/v1/rpc/superadmin_reorder_categories`)
      → ต้องถูกปฏิเสธด้วยข้อความ "ต้องมีสิทธิ์ Super Admin..." (ไม่ใช่ error ดิบ)
- [ ] ยืนยันว่า Librarian/Admin ยังเพิ่ม/แก้ไข/ปิดใช้งาน/ลบหมวดหมู่-หน่วยงานที่
      `/dashboard/categories`/`/dashboard/organizations` ได้ปกติ (ฟีเจอร์เดิม
      ไม่ถูกกระทบจากการเพิ่มหน้าจัดลำดับใหม่)
- [ ] ทดสอบตั้งหมวดหมู่หลักให้วนกลับมาเป็นหมวดหมู่ย่อยของตัวเอง (circular
      reference) ทั้งผ่าน `/dashboard/categories` (dropdown) และ SQL ตรง →
      ต้องถูกปฏิเสธเสมอ

## 9. Centralized Logging และ Uptime Monitoring

- [ ] `GET /api/health` ตอบกลับ `200` พร้อม `checks.database`/`checks.storage`
      เป็น `"ok"` — ไม่มีข้อมูลลับ/รายละเอียด infrastructure ใดๆ ในคำตอบ
- [ ] หากตั้งค่า `LOG_PROVIDER` ไว้: `/superadmin/system-logs` แสดงสถานะ
      "เชื่อมต่อแล้ว" ตรงกับ provider ที่ตั้งค่าไว้จริง
- [ ] หากยังไม่ได้ตั้งค่า `LOG_PROVIDER`: `/superadmin/system-logs` แสดง
      คำแนะนำการเชื่อมต่อ ไม่ใช่ log ปลอม และระบบยังทำงานได้ปกติ (log ผ่าน
      Vercel Runtime Logs เหมือนเดิม)
- [ ] เชื่อมต่อบริการ Uptime Monitoring ภายนอกเข้ากับ `/api/health` แล้ว (ดู
      [`uptime-monitoring.md`](uptime-monitoring.md)) — ทดสอบว่า monitor
      รายงานสถานะ "up" จริง

## 10. คุณภาพโค้ด

- [ ] `npm run lint` ผ่านไม่มี error
- [ ] `npx tsc --noEmit` ผ่านไม่มี error
- [ ] `npm run build` (production build) สำเร็จ ทุก route ของ `/superadmin/*`
      ปรากฏในผลลัพธ์ (รวม `/superadmin/categories`, `/superadmin/organizations`)
- [ ] ไม่มี `console.log`/โค้ดทดสอบค้างในซอร์สโค้ด (`console.error` สำหรับ
      บันทึกข้อผิดพลาดฝั่งเซิร์ฟเวอร์ที่ไม่แสดงต่อผู้ใช้ ยอมรับได้)

## 11. ขั้นตอนเปิดใช้งาน Super Admin อย่างปลอดภัย

1. **อย่าเปิดเผยข้อมูลรับรอง (credentials) ของบัญชี Super Admin คนแรกผ่านช่องทาง
   ที่ไม่ปลอดภัย** (แชท, อีเมลไม่เข้ารหัส) — สร้างรหัสผ่านที่คาดเดายากจริง
   ไม่ใช่รหัสผ่านตัวอย่าง/ค่าเริ่มต้น
2. สร้างบัญชี Super Admin **คนแรกเท่านั้น** ตามขั้นตอนใน
   [`README.md`](../README.md#7-สร้างบัญชี-super-admin-คนแรก) — สมัครสมาชิก
   ปกติก่อน แล้วมอบบทบาทผ่าน SQL Editor ของ Supabase Dashboard (ไม่ใช่ผ่าน
   API สาธารณะใดๆ)
3. **มอบบทบาท Super Admin ให้อย่างน้อย 2 คน** หากเป็นไปได้ (ไม่ใช่แค่ 1 คน)
   เพื่อไม่ให้ระบบเสี่ยงต่อการล็อกตัวเองออกโดยไม่ได้ตั้งใจ (เช่น ลืมรหัสผ่าน
   บัญชีเดียวที่มีสิทธิ์นี้) — ระบบบังคับว่าต้องมีอย่างน้อย 1 คนเสมออยู่แล้ว
   แต่การมี 2 คนขึ้นไปช่วยเพิ่มความยืดหยุ่นในทางปฏิบัติ — **คนที่ 2 เป็นต้นไป
   มอบผ่าน UI ได้เลยที่ `/superadmin/users/[id]`** (ต้องพิมพ์ยืนยันก่อนเสมอ
   ตามหัวข้อ 3) ไม่ต้องใช้ SQL อีกต่อไป
4. แนะนำให้ Super Admin ทุกคนตั้งค่า MFA ที่ `/account` ทันทีหลังได้รับสิทธิ์
   (ดูหัวข้อ 7) — เป็นด่านป้องกันสุดท้ายหากรหัสผ่านรั่วไหล
5. ตรวจสอบว่า `SUPABASE_SERVICE_ROLE_KEY` ตั้งค่าไว้ในสภาพแวดล้อม production
   แล้ว (จำเป็นสำหรับฟีเจอร์ระงับบัญชีและอ่าน/ดาวน์โหลดไฟล์ PDF)
6. ทบทวนรายการในหัวข้อ 1-10 ด้านบนให้ครบก่อนประกาศเปิดใช้งานจริงกับผู้ใช้จริง
7. หลังเปิดใช้งานแล้ว ตรวจสอบ `/superadmin/audit-logs` เป็นระยะเพื่อติดตาม
   การกระทำสำคัญของ Super Admin ทุกคน (เป็นกลไกตรวจสอบซึ่งกันและกัน)

## 12. ความปลอดภัยไฟล์อัปโหลด (Magic-byte + สแกนมัลแวร์)

**สำคัญ**: ตั้งค่า `MALWARE_SCAN_PROVIDER` (และตัวแปรที่เกี่ยวข้อง — ดู
`.env.example`) ให้เรียบร้อย**ก่อน**เปิดใช้งานจริง — ไม่ตั้งค่าเลยใน production
จะทำให้ **การอัปโหลดไฟล์ทุกไฟล์ถูกปฏิเสธทั้งหมด** (ระบบ fail closed โดยเจตนา
ไม่ใช่บั๊ก ดู `docs/file-security.md` หัวข้อ 4)

- [ ] ตั้งค่า `MALWARE_SCAN_PROVIDER=clamav` (พร้อม `CLAMAV_HOST`/`CLAMAV_PORT`
      ชี้ไปยัง ClamAV daemon ที่เข้าถึงได้จริงจากเซิร์ฟเวอร์ที่รันแอป) หรือ
      `MALWARE_SCAN_PROVIDER=http` (พร้อม `MALWARE_SCAN_API_URL`/
      `MALWARE_SCAN_API_KEY` ชี้ไปยังบริการสแกนที่ตรงสัญญาที่กำหนด)
- [ ] ทดสอบส่งงานวิจัยพร้อมไฟล์ PDF จริง → บันทึกสำเร็จ, `scan_status` ในหน้า
      `/dashboard/approvals/[id]` แสดง "ตรวจสอบแล้ว ปลอดภัย"
- [ ] ทดสอบอัปโหลดไฟล์ที่เปลี่ยนนามสกุลหลอก (เช่น ไฟล์ข้อความธรรมดาเปลี่ยนชื่อ
      เป็น `.pdf`) → ต้องถูกปฏิเสธที่ฟอร์ม พร้อมข้อความชัดเจน และไฟล์ต้องไม่ค้าง
      อยู่ใน Storage bucket `research-documents` (ตรวจสอบใน Supabase Dashboard)
- [ ] หากมีไฟล์ทดสอบมัลแวร์แบบปลอดภัย (เช่น [EICAR test file](https://www.eicar.org/download-anti-malware-testfile/))
      ลองอัปโหลด → ต้องถูกปฏิเสธ และ `/superadmin/audit-logs` ต้องมีรายการ
      "ปฏิเสธไฟล์อัปโหลด" บันทึกไว้
- [ ] ปิด/ลบค่า `MALWARE_SCAN_PROVIDER` ชั่วคราวแล้วลองส่งงานวิจัย → ต้องถูก
      ปฏิเสธทุกไฟล์ (ยืนยันพฤติกรรม fail closed) แล้วตั้งค่ากลับคืนก่อนใช้งานจริง
- [ ] ตรวจสอบว่าเอกสารที่เผยแพร่อยู่ก่อนอัปเกรด (legacy) ยังอ่าน/ดาวน์โหลดได้
      ตามปกติ (ควรมี `scan_status = 'skipped'`, `scan_provider = 'legacy-pre-scan'`)

## 13. ค้นหาเนื้อหาภายในไฟล์ PDF

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`pdf-full-text-search.md`](pdf-full-text-search.md)

- [ ] อัปโหลดงานวิจัยใหม่พร้อม PDF ที่มีเลเยอร์ข้อความ (ไม่ใช่ไฟล์สแกน) →
      หลังบันทึกสำเร็จ สถานะการดึงข้อความที่หน้าแก้ไขงานวิจัยต้องกลายเป็น
      "สำเร็จ — ค้นหาเนื้อหาได้" ภายในไม่กี่วินาที
- [ ] ที่ `/research` เลือกโหมด "เนื้อหา PDF" ค้นหาคำที่อยู่ในเอกสารนั้น (ทั้ง
      คำไทยและอังกฤษ) → ต้องเจอผลลัพธ์พร้อม snippet ไฮไลต์คำที่ตรง
- [ ] อัปโหลด PDF ที่เป็นภาพสแกนล้วน (ไม่มีเลเยอร์ข้อความ) → สถานะต้องกลายเป็น
      "ไม่พบข้อความ (อาจเป็นไฟล์สแกน)" ไม่ใช่ error และหน้าอ่าน PDF ต้องแสดง
      ข้อความสุภาพว่าอาจเป็นไฟล์สแกน (OCR ต้องให้เจ้าหน้าที่สั่งแยกต่างหาก
      ไม่ทำอัตโนมัติ — ดูหัวข้อ 16)
- [ ] ทดสอบว่าผู้ใช้ที่ไม่มีสิทธิ์อ่านเอกสาร (เช่น `member_only` ที่ยังไม่ได้
      ล็อกอิน) ค้นหาด้วยคำที่อยู่ในเนื้อหาเอกสารนั้น → **ต้องไม่เจอ**
      ผลลัพธ์/snippet ของเอกสารนั้นเลย (RLS บังคับสิทธิ์เดียวกับตัวเอกสาร)
- [ ] กด "ประมวลผลข้อความใหม่" ที่หน้าแก้ไขงานวิจัย (Librarian ขึ้นไป) →
      ทำงานสำเร็จและมีบันทึกใน Audit Log (`research_text_reprocess`)

## 14. ขอสิทธิ์เข้าถึงเอกสาร และแจ้งงานวิจัยใหม่ตามหมวดหมู่

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`document-access-requests.md`](document-access-requests.md)

- [ ] Guest (ยังไม่ล็อกอิน) เปิดเอกสารที่ต้องขอสิทธิ์ → เห็นปุ่มพาไปเข้าสู่ระบบ
      ก่อน ไม่ใช่ฟอร์มขอสิทธิ์ตรงๆ
- [ ] Member ส่งคำขออ่าน/ดาวน์โหลดสำเร็จ → เห็นสถานะที่ `/access-requests`
      ส่งคำขอซ้ำสำหรับเอกสาร+ประเภทเดียวกันขณะยังรอตรวจสอบ → ต้องถูกปฏิเสธ
- [ ] Member คนอื่น (บัญชีที่ 2) มองไม่เห็นคำขอของ Member คนแรกที่
      `/access-requests` ของตัวเอง
- [ ] Librarian อนุมัติคำขอ "อ่าน" (ไม่ใช่ "ดาวน์โหลด") → ผู้ขอต้องอ่านออนไลน์
      ได้ทันที **แต่ดาวน์โหลดยังไม่ได้** จนกว่าจะขอ/อนุมัติสิทธิ์ดาวน์โหลดแยก
      ต่างหาก
- [ ] อนุมัติแบบกำหนดวันหมดอายุ → ปรับวันหมดอายุย้อนหลังในฐานข้อมูล (หรือรอถึง
      วันจริง) แล้วลองเข้าถึงไฟล์อีกครั้ง → ต้องถูกปฏิเสธทันที
- [ ] เพิกถอนสิทธิ์ที่เคยอนุมัติ (ต้องระบุเหตุผล) → ผู้ใช้เข้าถึงไฟล์ไม่ได้ทันที
      และได้รับการแจ้งเตือน
- [ ] ปฏิเสธคำขอโดยไม่ระบุเหตุผล → ต้องถูกปฏิเสธ (บังคับกรอกเหตุผลเสมอ)
- [ ] ผู้ใช้ rank ต่ำกว่า Librarian เรียก Server Action อนุมัติ/ปฏิเสธ/เพิกถอน
      ตรง (ไม่ผ่าน UI) → ต้องถูกปฏิเสธด้วยข้อความทั่วไป
- [ ] ที่ `/profile/notification-settings` ติดตามหมวดหมู่ไว้ → ให้ Librarian
      เผยแพร่งานวิจัยใหม่ในหมวดหมู่นั้น → ผู้ติดตามต้องได้รับแจ้งเตือนในระบบ
      (กระดิ่งแจ้งเตือน + `/notifications`) ทันที
- [ ] หากตั้งค่า `RESEND_API_KEY` ไว้: ทดสอบว่าอีเมลแจ้งเตือนส่งจริงเมื่อคำขอ
      ได้รับอนุมัติ/ปฏิเสธ และเมื่อมีงานวิจัยใหม่ในหมวดหมู่ที่ติดตาม (เฉพาะ
      ผู้ใช้ที่เปิดสวิตช์อีเมลไว้ที่ `/profile/notification-settings` เท่านั้น
      — ค่าเริ่มต้นปิดไว้)

## 15. คุณภาพข้อมูลและข้อมูลมาตรฐาน (ผู้วิจัย/หน่วยงาน/ORCID/งานวิจัยซ้ำ)

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`data-quality.md`](data-quality.md) และ
[`orcid-integration.md`](orcid-integration.md)

- [ ] ที่ `/dashboard/authors` เพิ่มผู้วิจัยใหม่พร้อม ORCID ที่ checksum ไม่
      ถูกต้อง (เช่นเปลี่ยนหลักสุดท้าย) → ต้องถูกปฏิเสธก่อนบันทึก
- [ ] เพิ่มผู้วิจัยด้วย ORCID ที่มีอยู่แล้วในระบบ (ของผู้วิจัยที่ยังไม่ถูกรวม/
      ปิดใช้งาน) → ต้องถูกปฏิเสธ (ORCID ซ้ำ)
- [ ] เพิ่มผู้วิจัยชื่อคล้ายกับที่มีอยู่แล้วมาก → ต้องเห็นคำเตือน "พบผู้วิจัยที่
      ชื่อคล้ายกัน" ก่อนบันทึก (แต่ยังบันทึกได้ ไม่ถูกบล็อก)
- [ ] รวมผู้วิจัย 2 คนที่มีงานวิจัยร่วมกันบางรายการ (ชนกัน) และแยกกันบางรายการ
      (ไม่ชนกัน) → หลังรวม งานวิจัยที่ชนกันต้องเหลือความสัมพันธ์เดียว (ไม่ซ้ำ)
      งานวิจัยที่ไม่ชนกันต้องย้ายไปอยู่กับผู้วิจัยหลักครบถ้วน ผู้วิจัยต้นทางต้อง
      ไม่ถูกลบ (แค่ปิดใช้งาน + `merged_into_author_id` ชี้ไปผู้วิจัยหลัก)
- [ ] สร้างหน่วยงานย่อยแล้วพยายามตั้งหน่วยงานหลักให้วนกลับมาเป็นหน่วยงานย่อย
      ของตัวเอง (circular reference) → ต้องถูกปฏิเสธเสมอ
- [ ] เพิ่ม/แก้ไขงานวิจัยให้ชื่อเรื่องคล้ายกับรายการที่มีอยู่แล้วมาก (ปีเดียวกัน
      ด้วยยิ่งดี) → ต้องปรากฏเป็นคำเตือนที่ `/dashboard/duplicate-reviews`
      พร้อมคะแนนความคล้ายและเหตุผล **ภายในคำขอเดียวกัน ไม่บล็อกการบันทึก**
- [ ] ที่ `/dashboard/duplicate-reviews/[id]` ทดสอบว่า Librarian ยืนยัน/
      ปฏิเสธว่าซ้ำได้ **แต่กดปุ่มรวมงานวิจัยจริงไม่ได้** (ต้อง Admin ขึ้นไป)
- [ ] Admin รวมงานวิจัย 2 รายการที่มีคนกดถูกใจ (favorites)/ประวัติการอ่านร่วมกัน
      บางส่วน → หลังรวม รายการโปรด/ประวัติ/คำขอเข้าถึงเอกสารต้องย้ายไปยัง
      รายการหลักครบถ้วนโดยไม่มีแถวซ้ำซ้อน แล้วเปิด URL เดิมของรายการที่ถูกรวม
      → ต้อง redirect ไปยังรายการหลักอัตโนมัติ (ไม่ใช่ 404)
- [ ] ที่ `/dashboard/data-quality` ตรวจสอบว่าตัวเลข/รายการที่แสดง (ไม่มีผู้วิจัย/
      ไม่มีหน่วยงาน/ไม่มี ORCID) ตรงกับข้อมูลจริงในฐานข้อมูล

## 16. ORCID OAuth และ OCR สำหรับ PDF เอกสารสแกน

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`orcid-integration.md`](orcid-integration.md)
และ [`ocr-operations.md`](ocr-operations.md)

- [ ] ไม่ได้ตั้งค่า `ORCID_CLIENT_ID`/`ORCID_CLIENT_SECRET` → ที่ `/account`
      ต้องเห็นกล่องคำแนะนำสีเหลืองแทนปุ่ม "เชื่อม ORCID" ไม่ใช่ปุ่มที่กดแล้ว
      error ลอยๆ
- [ ] บัญชีผู้ใช้ที่ยังไม่ถูกผูกกับผู้วิจัยคนไหนเลย (`authors.profile_id`)
      → ที่ `/account` ต้องเห็นข้อความแนะนำให้ติดต่อเจ้าหน้าที่ ไม่ใช่ปุ่มเชื่อม
      ORCID
- [ ] ที่ `/dashboard/authors/[id]` (Librarian ขึ้นไป) ผูกบัญชีผู้ใช้ให้ผู้วิจัย
      ด้วยอีเมล → บัญชีนั้นต้องเห็นปุ่ม/สถานะเชื่อม ORCID ที่ `/account` ทันที
      ลองผูกอีเมลเดียวกันกับผู้วิจัยคนที่สอง → ต้องถูกปฏิเสธ (บัญชีเดียวผูกกับ
      ผู้วิจัยได้แค่คนเดียว)
- [ ] ตั้งค่า `ORCID_CLIENT_ID`/`ORCID_CLIENT_SECRET` (แนะนำใช้ ORCID Sandbox
      ทดสอบก่อนเสมอ — `ORCID_OAUTH_ENV` ปล่อยว่างหรือ `sandbox`) → กดปุ่ม
      "เชื่อม ORCID" แล้วกด "ยกเลิก" ที่หน้า ORCID → ต้องกลับมาที่ `/account`
      พร้อมข้อความ "ยกเลิกการเชื่อมต่อ" ไม่มีข้อมูลใดถูกเปลี่ยน
  - [ ] ทำซ้ำแต่กด "อนุญาต" จริง → `orcid_oauth_verified_at` ต้องถูกบันทึก และ
        หน้า `/dashboard/authors/[id]` ต้องแสดงสถานะ "ยืนยันผ่าน ORCID OAuth
        จริง" แยกจากสถานะเจ้าหน้าที่ยืนยันด้วยตนเองเดิม
  - [ ] เชื่อม ORCID เดิมซ้ำกับบัญชีที่สอง (ORCID เดียวกัน คนละผู้วิจัย) → ต้อง
        ถูกปฏิเสธพร้อมข้อความให้ติดต่อเจ้าหน้าที่ ไม่ใช่เขียนทับข้อมูลเดิม
  - [ ] ก่อนขึ้นใช้งานจริง เปลี่ยนเป็น `ORCID_OAUTH_ENV=production` และแอป
        ORCID ที่ลงทะเบียน redirect URI ตรงกับโดเมนจริงแล้ว
- [ ] ยังไม่ได้ตั้งค่า `OCR_PROVIDER`/`OCR_PROVIDER_BASE_URL` → สั่ง OCR เอกสารที่
      `no_text_found` → งานต้องจบด้วยสถานะ "ล้มเหลว" พร้อมเหตุผลชัดเจนเสมอ
      **ต้องไม่มีข้อความ OCR ปลอมปรากฏขึ้นมา**
- [ ] ตั้งค่า `OCR_PROVIDER`/`OCR_PROVIDER_BASE_URL` ครบแล้วแต่ยังไม่ได้ตั้ง
      `OCR_ENABLED=true` → สั่ง OCR → ต้องยังคงล้มเหลวด้วย
      ข้อความ "องค์กรยังไม่ได้อนุมัติ..." (ไม่มีการส่งไฟล์ออกจริง)
- [ ] ตั้งค่าครบทั้งสามเงื่อนไข (provider + `OCR_ENABLED=true` +
      สวิตช์ `ocr_provider_enabled` ที่ `/superadmin/ocr`) → สั่ง OCR
      เอกสารสแกนจริง → สถานะต้องกลายเป็น "สำเร็จ" พร้อมข้อความที่อ่านได้ และ
      แสดงคำเตือน "อาจคลาดเคลื่อน" กำกับเสมอ
- [ ] ค้นหาคำที่อยู่ในข้อความ OCR ที่ `/research` → ต้องเจอผลลัพธ์พร้อมป้าย
      "จาก OCR อาจคลาดเคลื่อน" กำกับชัดเจน
- [ ] ทดสอบเอกสาร `staff_only`/`member_only` ที่มีข้อความ OCR แล้วค้นหาด้วย
      บัญชีที่ไม่มีสิทธิ์อ่าน → **ต้องไม่เจอ**ผลลัพธ์เลย (RLS บังคับสิทธิ์
      เดียวกับ PDF ปกติ)
- [ ] Super Admin สั่ง OCR เป็นชุดที่ `/superadmin/pdf-processing` แท็บ "OCR
      เอกสารสแกน" → ต้องกรองเฉพาะเอกสาร `no_text_found` ที่ยังไม่ `completed`
      เท่านั้น และมีบันทึกใน Audit Log (`ocr_bulk_process`)
- [ ] ผู้ใช้ rank ต่ำกว่า Librarian เรียก Server Action สั่ง OCR ตรง (ไม่ผ่าน
      UI) → ต้องถูกปฏิเสธด้วยข้อความทั่วไป

## 17. Worker หลาย process/instance และ Concurrency ของ Queue (ช่วงที่ 30)

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`background-jobs.md`](background-jobs.md)
หัวข้อ 11.5 และ 13 — ขั้นตอนเปิดใช้ worker มากกว่า 1 ตัวพร้อมกันจริงใน
production อยู่ที่หัวข้อ 13.5 ของเอกสารนั้นโดยตรง (ไม่ซ้ำในนี้)

- [ ] ตั้งค่า Cron/scheduler ให้เรียก `/api/jobs/process` พร้อม header
      `Authorization: Bearer $CRON_SECRET` เท่านั้น — เรียกโดยไม่มี header หรือ
      header ผิด → ต้องได้ `401`/`503` เสมอ ไม่มีทางเรียกแบบไม่ยืนยันตัวตนได้
- [ ] ตั้งค่าให้มีมากกว่าหนึ่งช่องทางเรียก endpoint นี้พร้อมกันได้จริง (เช่น
      Cron ภายนอก + ปุ่ม "ประมวลผลคิวเดี๋ยวนี้" ที่กดพร้อมกัน หรือตั้ง cron
      สองตัวที่คาบเกี่ยวเวลากัน) → เข้าไปดูที่ `/superadmin/jobs` หัวข้อ
      "สถานะ Queue โดยรวม" ระหว่างที่ทั้งสองกำลังทำงานพร้อมกัน — คอลัมน์
      "กำลังทำงานจริง" ของแต่ละประเภทงานต้อง **ไม่เกิน** ค่า Concurrency ที่
      ตั้งไว้เลย แม้จะมี worker/การเรียกพร้อมกันมากกว่าหนึ่งตัวก็ตาม
- [ ] ปรับค่า Concurrency ของประเภทงานใดประเภทหนึ่งลงต่ำ (เช่น 1) ที่
      `/superadmin/jobs` แล้วสร้างงานประเภทนั้นหลายรายการพร้อมกัน (เช่น
      bulk backfill) พร้อมเรียก worker endpoint ซ้อนกันหลายครั้ง → ยืนยันว่า
      ไม่มีทางเห็นงานประเภทนั้น "กำลังประมวลผล" มากกว่า 1 รายการพร้อมกันจริง
      ไม่ว่าจะเรียก worker กี่ครั้งซ้อนกันก็ตาม
- [ ] จำลอง worker ล่มกลางคัน (แก้ `lease_expires_at` ของงานหนึ่งให้เป็นอดีต
      ตรงในฐานข้อมูล) → รอบ claim ถัดไปต้องดึงงานนั้นกลับมาทำต่อเองอัตโนมัติ
      โดยไม่ต้องมีการแทรกแซงด้วยมือ และ "lease หมดอายุค้างอยู่" ที่หน้า
      `/superadmin/jobs` ต้องกลับมาเป็น 0 หลังรอบ claim ถัดไปสำเร็จ
- [ ] ทดสอบ retry (backoff)/dead-letter queue/idempotency key ยังทำงานถูกต้อง
      ตามปกติหลังเปิดใช้ worker หลายตัว (ไม่ใช่แค่ตอน worker ตัวเดียว) — ดู
      หัวข้อ 11.1/2.2/2.3 ของ `background-jobs.md`
- [ ] หมวดหมู่ที่มีผู้ติดตามอีเมลจำนวนมาก (หลักสิบ+) → เผยแพร่งานวิจัยใหม่ใน
      หมวดหมู่นั้นแล้วตรวจสอบว่าอีเมลถูกส่งครบทุกคนจริง (ไม่มีใครถูกข้าม) แม้จะ
      ส่งเป็นชุดจำกัดจำนวนพร้อมกันแทนที่จะยิงพร้อมกันทั้งหมดในครั้งเดียว

## 18. ตรวจสอบ Cron/Worker แบบอัตโนมัติ + แจ้งเตือน (ช่วงที่ 31)

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`background-jobs.md`](background-jobs.md)
หัวข้อ 14

### 18.1 Cron ที่ต้องตั้งค่าใน production (2 ตัว, ความถี่แนะนำ)

| Cron | Endpoint | ความถี่แนะนำ | หมายเหตุ |
| --- | --- | --- | --- |
| Queue worker | `/api/jobs/process` | ตามปริมาณงาน — เริ่มที่ทุก 5 นาที (`*/5 * * * *`) แล้วปรับตามจริง | ครอบคลุม `access_expiration`/`notification_delivery`/`maintenance_cleanup` ไปในตัว (self-seed) |
| Health monitoring (watchdog) | `/api/cron/health-check` | ทุก 5–15 นาที | **ต้องเป็น scheduler อิสระจากตัวแรก** (ดูหัวข้อ 8 ของ `background-jobs.md`) |
| ตรวจสอบสิทธิ์หมดอายุ | (ไม่มี endpoint แยก) | ทุก 15–60 นาที | ตั้งเป็นค่า `expected_frequency_minutes` ของ `access_expiration` ที่ `/superadmin/cron-monitoring` ให้ตรงกับความถี่จริงของ Queue worker ด้านบน (≥ ความถี่นั้นเสมอ) |

ทั้งสอง Cron ใช้ `CRON_SECRET` ตัวเดียวกัน (header
`Authorization: Bearer $CRON_SECRET`) — `vercel.json` มี entry ทั้งสองไว้แล้ว
(configuration-as-code เท่านั้น ยังไม่ได้ deploy จริง)

### 18.2 ทดสอบ

- [ ] เรียก `/api/jobs/process` จริงอย่างน้อยหนึ่งครั้ง → ที่
      `/superadmin/cron-monitoring` ต้องเห็น `queue_worker` heartbeat เป็น
      "ปกติ" พร้อมเวลารันล่าสุด/รอบถัดไปที่คาดว่าจะทำงาน
- [ ] เรียก `/api/cron/health-check` จริงอย่างน้อยหนึ่งครั้ง → เห็น
      `health_monitoring` heartbeat เป็น "ปกติ" เช่นกัน (ตรวจสุขภาพตัวเองด้วย
      กลไกเดียวกัน)
- [ ] ปรับ `next_expected_run_at` ของแถว `cron_runs` ล่าสุดย้อนหลังในฐานข้อมูล
      (จำลอง Cron หยุดทำงาน) แล้วเรียก `/api/cron/health-check` → ต้องเห็น
      heartbeat เปลี่ยนเป็น "เกินกำหนด" และมีแจ้งเตือน Super Admin ทั้ง in-app
      และอีเมล (ถ้าตั้งค่า Email Provider ไว้)
- [ ] เรียก `/api/cron/health-check` ซ้ำทันทีหลังจากเพิ่งแจ้งเตือนไป → **ต้อง
      ไม่**สร้างการแจ้งเตือนซ้ำ (cooldown 60 นาที) — ปรับเวลาที่แจ้งเตือนล่าสุด
      ย้อนหลังเกิน 60 นาทีในฐานข้อมูลแล้วเรียกใหม่ → ต้องแจ้งเตือนได้อีกครั้ง
- [ ] job ประเภทใดก็ได้เข้า Dead-letter Queue ครบ 5 รายการขึ้นไปโดยยังไม่ได้
      จัดการ → ต้องมีแจ้งเตือน "งานล้มเหลวถาวรสะสมมาก" แยกต่างหากจากแจ้งเตือน
      DLQ ต่อ job เดิม (ทั้งสองแบบต้องแจ้งได้พร้อมกัน ไม่ใช่แทนที่กัน)
- [ ] ปล่อยให้มีงาน `pending` ค้างเกิน 15 นาที (เช่น ปิด Cron ชั่วคราว) →
      `/api/cron/health-check` ต้องแจ้งเตือน "มีงานรอคิวนานผิดปกติ"
- [ ] `maintenance_cleanup` ทำงานจริงอย่างน้อยหนึ่งครั้ง → แถว
      `rate_limit_events` ที่เก่ากว่า 7 วันถูกลบ แถวที่ใหม่กว่ายังอยู่ครบ

- [ ] ผู้ใช้ rank ต่ำกว่า Super Admin เข้า `/superadmin/cron-monitoring` ตรงๆ
      → ต้องถูกปฏิเสธเหมือนหน้า `/superadmin/*` อื่นทุกหน้า
- [ ] ปรับค่า "ความถี่ที่คาดหวัง"/"เกณฑ์จำนวนงานล้มเหลว" ที่หน้า

## 19. OCR Provider Readiness และ Controlled Test (ช่วงที่ 32)

**ห้ามเปิด `OCR_ENABLED=true` ในสภาพแวดล้อม production จนกว่าจะทำตาม
Checklist เต็มใน [`ocr-provider-validation.md`](ocr-provider-validation.md)
หัวข้อ 6 ครบทุกข้อแล้วเท่านั้น** — รายการด้านล่างเป็นสรุปย่อสำหรับ QA รอบ
production เท่านั้น ไม่ใช่ตัวแทนของ Checklist เต็ม

- [ ] ที่ `/superadmin/ocr` ส่วน "OCR Readiness Check" แสดงสถานะครบทุกช่อง
      (เปิด/ปิด, provider, ความครบถ้วนของการตั้งค่า, timeout, เพดานขนาดไฟล์/
      หน้า/จำนวนงานต่อวัน, นโยบายเอกสาร private, โหมดทดสอบ) และ **ไม่แสดงค่า
      `OCR_PROVIDER_BASE_URL`/`OCR_PROVIDER_API_KEY` จริงที่ใดเลย**
      (เปิด DevTools Network tab ตรวจ response ของ Server Action ด้วย)
- [ ] กดปุ่ม "ตรวจสอบการเชื่อมต่อ" ขณะยังไม่ได้ตั้งค่า provider → แสดงผล
      "ยังไม่ได้ตั้งค่า" อย่างสุภาพ ไม่ error ดิบ และมีบันทึกใน Audit Log
      (`ocr_readiness_check`) ทุกครั้งที่กด
- [ ] ตั้งค่า provider จริงแล้วกดปุ่มเดิม → ต้องได้ผล "เชื่อมต่อได้"/
      "เชื่อมต่อไม่ได้" ตรงกับสถานะจริงของ endpoint **โดยไม่มีการสร้างงาน OCR
      หรือส่งไฟล์ใดๆ เกิดขึ้นเลย** (ตรวจสอบว่าไม่มีแถว `background_jobs`/
      `ocr_test_runs` ใหม่เกิดขึ้นจากการกดปุ่มนี้)
- [ ] ตั้ง `OCR_TEST_MODE=true` (โดยที่ `OCR_ENABLED` ยังเป็น `false` ก็ได้) →
      ส่วน "Controlled OCR Test" ปรากฏที่ `/superadmin/ocr` — เลือก fixture
      `english-sample`/`multipage-sample`/`no-text-scanned-sample` ทีละตัว
      แล้วกด "เริ่มทดสอบ" → เห็นสถานะ/จำนวนหน้า/เวลา/จำนวนตัวอักษรที่ดึงได้
      ครบถ้วน และมีบันทึกใน Audit Log (`ocr_test_run_triggered`)
- [ ] ทำตาม Test Checklist เต็มใน `ocr-provider-validation.md` หัวข้อ 6
      ให้ครบทุกข้อ (ไทย/อังกฤษ/หลายหน้า/ล้มเหลว/timeout/retry+DLQ/progress/
      บล็อกเอกสาร private/ค้นหาได้จริง) ก่อนพิจารณาเปิดใช้งานจริง
- [ ] หลังผ่าน Checklist แล้ว เปิด `OCR_ENABLED=true` และตรวจสอบว่าหัวข้อ 16
      ด้านบน (สั่ง OCR เอกสารจริง 1 รายการ) ยังคงผ่านทั้งหมด
