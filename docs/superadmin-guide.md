## 1. ภาพรวมและการเข้าถึง

Super Admin เป็นบทบาทสูงสุดในระบบ (rank 50 เหนือ Admin ที่ rank 40) เข้าถึงหน้า
`/superadmin/*` ได้เท่านั้น — Admin ปกติเข้าไม่ได้ ถูกพาไปหน้า `/403` เสมอ
(ป้องกันทั้งที่ `middleware.ts` และซ้ำอีกชั้นที่ `app/superadmin/layout.tsx`)

**วิธีสร้างบัญชี Super Admin คนแรก**: ไม่มีหน้า UI ให้ตั้งเอง (ระบบยังไม่มีใคร
เป็น Super Admin เลยในตอนเริ่มต้น จึงไม่มีใครมีสิทธิ์เข้าหน้า UI นี้ได้) ต้องทำ
ผ่าน SQL โดยตรงเสมอสำหรับคนแรกเท่านั้น — ดูขั้นตอนละเอียดในหัวข้อ "สร้างบัญชี
Super Admin คนแรก" ของ [`README.md`](../README.md#7-สร้างบัญชี-super-admin-คนแรก)

**คนถัดไป**: หลังมี Super Admin คนแรกแล้ว ให้มอบ/ถอดถอนสิทธิ์ Super Admin ให้
คนอื่นผ่านหน้า `/superadmin/users/[id]` ได้เลย (ดูหัวข้อ 2 ด้านล่าง) ไม่ต้องใช้
SQL อีกต่อไป

ระบบบังคับว่าต้องมี Super Admin เหลืออย่างน้อย 1 คนในระบบเสมอ (ป้องกันด้วย
database trigger ที่ครอบคลุมทุกเส้นทาง รวมถึง SQL โดยตรงและการลบบัญชีแบบ
cascade) — การมอบ/ถอดถอนบทบาทนี้ทำได้เฉพาะโดยผู้ที่เป็น Super Admin อยู่แล้ว
เท่านั้น (Admin ปกติทำไม่ได้แม้ผ่าน SQL โดยตรง เพราะถูกจำกัดด้วย RLS)

## 2. ผู้ใช้งาน (/superadmin/users)

- **ค้นหา/กรอง**: ค้นหาจากชื่อหรืออีเมล กรองตามสถานะ (ใช้งานได้/ถูกระงับ)
  และบทบาท
- **หลายบทบาทต่อคน**: กดเข้าไปที่ผู้ใช้แต่ละคน (`/superadmin/users/[id]`)
  แล้วติ๊ก/ถอนติ๊กบทบาทที่ต้องการได้อิสระ — ผู้ใช้หนึ่งคนมีได้หลายบทบาท
  พร้อมกัน (เช่น เป็นทั้ง Staff และ Librarian) ต่างจากหน้า `/dashboard/users`
  (Admin) ที่เลือกได้ทีละบทบาทเดียว — บทบาท member/staff/librarian/admin
  ติ๊กแล้วมีผลทันที (ไม่ต้องยืนยันซ้ำ)
- **มอบ/ถอดถอนสิทธิ์ Super Admin**: แถวบทบาท Super Admin แยกจากบทบาทอื่น —
  คลิกแล้วเปิดกล่องยืนยันเสมอ (ไม่เปลี่ยนสถานะทันทีเหมือนบทบาทอื่น) กล่อง
  ยืนยันแสดงชื่อ-อีเมลของผู้ใช้เป้าหมายชัดเจน ต้องพิมพ์คำว่า `CONFIRM` หรือ
  อีเมลของผู้ใช้เป้าหมายให้ตรงกันก่อนปุ่มยืนยันจะกดได้ พร้อมช่องกรอกเหตุผล
  (ไม่บังคับ) — ตรวจสอบข้อความยืนยันซ้ำอีกชั้นที่ฝั่งเซิร์ฟเวอร์เสมอ ไม่ใช่แค่
  ที่ฝั่ง client เท่านั้น
- **ประวัติการทำงาน**: แสดงรายการ `audit_logs` ที่ผู้ใช้คนนั้นเป็นผู้กระทำ
- **ประวัติที่ถูกดำเนินการกับบัญชีนี้**: แสดงรายการ `audit_logs` ที่ผู้ใช้คนนี้
  เป็น "เป้าหมาย" ของการกระทำ (เช่น ถูกมอบ/ถอดถอนบทบาท ถูกระงับ/เปิดใช้งาน
  บัญชี) พร้อมชื่อผู้กระทำและเหตุผล (ถ้ามี) — ช่วยตรวจสอบย้อนหลังว่าใครเปลี่ยน
  สิทธิ์ของบัญชีนี้เมื่อใดและทำไม
- **เปิด/ระงับบัญชี**: ระงับถาวรหรือระบุจำนวนวัน (ระงับชั่วคราว) — ใช้ Supabase
  Auth Admin API สั่งระงับจริง (`ban_duration`) เหมือนหน้า Admin เดิม
- **ป้องกัน Super Admin คนสุดท้าย**: การถอดถอนบทบาท Super Admin ออกจากผู้ใช้
  คนสุดท้ายที่มีบทบาทนี้จะถูกปฏิเสธเสมอ พร้อมข้อความอธิบายชัดเจน (บังคับด้วย
  database trigger — ปฏิเสธไม่ว่าจะเรียกผ่าน UI หรือ SQL โดยตรงก็ตาม)
- ทุกการเพิ่ม/ถอดถอนบทบาทและเปลี่ยนสถานะบัญชีบันทึกลง `audit_logs` อัตโนมัติ —
  การมอบ/ถอดถอน Super Admin บันทึกเพิ่มเติมด้วย: อีเมล/ชื่อผู้ถูกเปลี่ยน,
  บทบาทเดิมทั้งหมด, บทบาทใหม่ทั้งหมด, และเหตุผลที่ระบุ (ถ้ามี)
- **รีเซ็ต MFA**: หัวข้อ "ยืนยันตัวตนสองขั้นตอน (MFA)" ในหน้าเดียวกันแสดงสถานะ
  อุปกรณ์ MFA ของผู้ใช้ (ยืนยันแล้ว/ยังไม่ยืนยัน — ไม่แสดง secret/QR/recovery
  code) พร้อมปุ่ม "รีเซ็ต MFA" สำหรับกรณีทำอุปกรณ์หาย ดูรายละเอียดเต็มที่หัวข้อ
  14

> **สิทธิ์**: เฉพาะ Super Admin (rank ≥ 50) เท่านั้นที่เข้าหน้านี้และเรียก
> Server Action เหล่านี้ได้ — บังคับซ้ำ 3 ชั้น: `middleware.ts`,
> `app/superadmin/layout.tsx`, และ `requireMinRank(50)` ในทุก Server Action
> ส่วนการมอบ/ถอดถอนบทบาท `super_admin` โดยเฉพาะยังมี RLS Policy บนตาราง
> `user_roles` บังคับซ้ำอีกชั้นที่ฐานข้อมูลด้วย (ดู
> `supabase/migrations/20260802100100_super_admin_role.sql` ข้อ 3) — Admin
> ปกติ (rank 40) เขียนแถว `user_roles` ที่ชี้ไปบทบาท `super_admin` ไม่ได้แม้จะ
> พยายามเรียก API/SQL ตรงๆ ก็ตาม

## 3. บทบาทและสิทธิ์ (/superadmin/roles)

แสดง Role Matrix แบบ**อ่านอย่างเดียว** — ระบบสิทธิ์ปัจจุบันใช้ rank ตัวเลข
เปรียบเทียบ (`rank >= N`) ฝังอยู่ใน RLS Policies และ Route Guards หลายสิบจุด
ทั่วระบบ ยังไม่มีตารางสิทธิ์แบบละเอียดรายรายการ (fine-grained permissions)
ให้แก้ไขผ่าน UI ได้อย่างปลอดภัย — โดยเฉพาะการแก้ไขค่า `rank` ตรงๆ มีความเสี่ยง
สูงที่จะทำให้ลำดับชั้นสิทธิ์ทั้งระบบผิดพลาด (เช่น ถ้าปรับ rank ของ librarian
ให้สูงกว่า 40 โดยไม่ตั้งใจ จะทำให้ librarian ได้สิทธิ์ระดับ Admin ทันที) จึงไม่
เปิดให้แก้ไขจากหน้านี้ตามคำแนะนำของสเปกงานที่ให้ทำ Role Matrix แบบอ่านอย่าง
เดียวไว้ก่อนหากยังไม่รองรับสิทธิ์แบบละเอียด

## 4. ตั้งค่าระบบขั้นสูง (/superadmin/system-settings)

ครอบคลุมทั้งฟิลด์เดิมที่ Admin แก้ไขได้ที่ `/dashboard/settings` (ชื่อระบบ
ข้อมูลติดต่อ ข้อความลิขสิทธิ์ การแสดงผลหน้าแรก — **ยังแก้ไขได้จากทั้งสองหน้า
เหมือนเดิม ไม่มีอะไรเปลี่ยน**) และฟิลด์ใหม่ที่ Admin ปกติแก้ไขไม่ได้เลย:

- **โลโก้/Favicon**: อัปโหลดไฟล์ได้โดยตรง (ไม่ใช่กรอก URL อย่างเดียวอีกต่อไป)
  ไฟล์ถูกเก็บใน Storage bucket `site-assets` (public, สูงสุด 2 MB ต่อไฟล์)
- **Social Media**: Facebook, Twitter/X, LINE Official
- **เปิด/ปิดการสมัครสมาชิก และเปิด/ปิดการส่งงานวิจัย**: มีผลจริงทันที —
  `registerAction`/`submitResearchAction` ตรวจสอบค่านี้ก่อนทุกครั้ง
- **สถานะเริ่มต้นของงานวิจัยใหม่**: ใช้เมื่อฟอร์มส่งงานวิจัยไม่ได้ระบุ intent
  ชัดเจน (draft หรือ pending_review)
- **ขนาดไฟล์สูงสุด** (PDF/ภาพปก/เอกสารแนบ): แก้ไขแล้ว**มีผลจริงทันทีกับ
  Storage bucket** (ผ่านฟังก์ชัน `superadmin_update_bucket_limit`) — เป็น
  ขีดจำกัดที่ Supabase Storage บังคับจริง ไม่ใช่แค่ค่าที่แสดงผล ตัวเลข
  คำแนะนำที่แสดงในฟอร์มส่งงานวิจัยฝั่ง client (`SubmitResearchForm`) ดึงค่า
  จาก `getSettings()` แบบไดนามิกแล้วเช่นกัน จึงตรงกับค่าที่ตั้งไว้ที่นี่เสมอ
  (ค่าคงที่ใน `lib/storage/limits.ts` เหลือไว้เฉพาะเป็น fallback ปลอดภัย
  สำหรับตอนที่ยังไม่มีแถวการตั้งค่าในฐานข้อมูลเท่านั้น)

ฟิลด์ใหม่ทั้งหมดในหน้านี้ (ยกเว้นฟิลด์เดิม) แก้ไขได้เฉพาะ Super Admin เท่านั้น
บังคับด้วย database trigger — Admin ที่พยายามแก้ไขผ่าน API โดยตรงจะถูกปฏิเสธ

## 5. ความปลอดภัย (/superadmin/security)

### CAPTCHA

รองรับ [Cloudflare Turnstile](https://developers.cloudflare.com/turnstile/)
(มี free tier ไม่มีค่าใช้จ่าย) วิธีตั้งค่า:

1. สมัคร Cloudflare Turnstile แล้วสร้าง site key คู่กับ secret key
2. ใส่ค่าใน `.env.local`:
   ```
   NEXT_PUBLIC_TURNSTILE_SITE_KEY=...
   TURNSTILE_SECRET_KEY=...
   ```
3. รีสตาร์ท dev server (หรือ redeploy) เพื่อให้ env var ใหม่มีผล
4. เปิดสวิตช์ "เปิดใช้งาน CAPTCHA" ที่หน้านี้

widget ฝังจริงแล้วที่ฟอร์มสมัครสมาชิก (`/register`) และฟอร์มส่งงานวิจัยใหม่
(`/submit-research` เท่านั้น — ไม่รวมหน้าแก้ไข/เพิ่มงานวิจัยของ Librarian/Admin
ที่ใช้ component เดียวกัน) เมื่อเปิดสวิตช์และตั้งค่าคีย์ครบ ผู้ใช้ต้องผ่านการ
ยืนยัน Turnstile ก่อนจึงจะสมัครสมาชิก/ส่งงานวิจัยได้ — ตรวจสอบ token กับ
Cloudflare จริงฝั่งเซิร์ฟเวอร์เสมอ (`verifyCaptchaIfEnabled()` ใน
`lib/captcha.server.ts`) ไม่เชื่อผลจาก client เพียงอย่างเดียว

> **พฤติกรรมเมื่อเปิดสวิตช์แต่ตั้งค่าคีย์ไม่ครบ**: ระบบจะ **fail-open**
> (ไม่บล็อกผู้ใช้ ไม่แสดง widget ที่พัง) พร้อม log คำเตือนไว้ฝั่งเซิร์ฟเวอร์
> เท่านั้น — ป้ายกำกับ "เปิดไว้แต่ยังไม่ได้ตั้งค่าคีย์" ที่หน้านี้คือสัญญาณ
> เตือนสำหรับผู้ดูแลว่าสวิตช์ยังไม่มีผลจริงจนกว่าจะตั้งค่า environment
> variables ให้ครบ

### Rate Limit

จำกัดจำนวนครั้งต่อช่วงเวลาสำหรับฟอร์มสมัครสมาชิก (นับจาก IP) และฟอร์มส่ง
งานวิจัย (นับจาก IP หรือ user id) ทำงานจริงทันทีที่บันทึก — อิงฐานข้อมูล
ล้วน ไม่ต้องพึ่งบริการภายนอก (ตาราง `rate_limit_events` + ฟังก์ชัน
`check_rate_limit()`) ออกแบบให้ "fail-open" หากตรวจสอบไม่ได้ (เช่น DB error)
เพื่อไม่ให้ rate limiter เองกลายเป็นจุดที่ทำให้ฟีเจอร์หลักใช้งานไม่ได้

### นโยบายการยืนยันอีเมล

แสดงสถานะปัจจุบันจริง (ดึงจาก GoTrue endpoint `/auth/v1/settings` โดยตรง)
แบบ**อ่านอย่างเดียว** — ค่านี้ตั้งได้เฉพาะผ่าน Supabase Dashboard
(Authentication > Providers > Email) สำหรับ Cloud หรือ `supabase/config.toml`
หัวข้อ `[auth.email]` สำหรับ local เท่านั้น แอปไม่มีสิทธิ์เปลี่ยนค่านี้เอง

### บัญชีที่ถูกระงับ

แสดงรายชื่อผู้ใช้ที่ `is_active = false` ทั้งหมด กดชื่อเพื่อไปที่หน้า
รายละเอียด/เปิดใช้งานคืนได้ทันที

## 6. Storage (/superadmin/storage)

- **พื้นที่ใช้งาน**: ผลรวมขนาดไฟล์และจำนวนไฟล์ต่อ bucket ทั้ง 4 bucket
  (`research-documents`, `research-covers`, `submission-attachments`,
  `site-assets`)
- **ไฟล์ค้าง (orphaned files)**: ไฟล์ที่ไม่มีแถวข้อมูลใดในฐานข้อมูลอ้างอิง
  ถึงอีกต่อไป — ครอบคลุมทั้งไฟล์เก่าที่ถูกแทนที่ตอนแก้ไขงานวิจัย และไฟล์ที่
  อัปโหลดค้างไว้ระหว่างกรอกฟอร์มแต่ไม่เคยกดบันทึกสำเร็จ เป็นการประมาณการ
  แบบ best-effort (โดยเฉพาะ `research-covers` ที่เทียบจาก URL แบบ suffix
  match เนื่องจากคอลัมน์เก็บ URL เต็มไม่ใช่พาธดิบ)
- **ลบไฟล์ค้าง**: ต้องกดยืนยัน (confirm dialog) ก่อนทุกครั้ง ระบบตรวจสอบซ้ำ
  ว่าไฟล์ยังไม่มีการอ้างอิงจริงก่อนลบเสมอ (ป้องกัน race condition ที่มีคน
  เพิ่งบันทึกใช้งานไฟล์นี้ระหว่างที่หน้าเว็บกำลังแสดงผลอยู่) และบันทึก
  `audit_logs` ทุกครั้งที่ลบสำเร็จ
- ฟอร์มอัปโหลดไฟล์ใหม่ในระบบ (ส่งงานวิจัย/แก้ไข) อัปโหลดไฟล์ใหม่สำเร็จก่อน
  เสมอก่อนที่ไฟล์เก่าจะถูกแทนที่ในฐานข้อมูล (ไม่มีการลบไฟล์เก่าจนกว่าจะ
  บันทึกอ้างอิงไฟล์ใหม่สำเร็จ) — ไฟล์เก่าที่ถูกแทนที่จะกลายเป็น "ไฟล์ค้าง"
  ในหน้านี้ให้ Super Admin พิจารณาลบเองภายหลัง ไม่ได้ลบอัตโนมัติ

## 7. การแจ้งเตือน (/superadmin/notifications)

### การแจ้งเตือนในระบบ (in-app)

ใช้งานได้จริงทันที ไม่ต้องตั้งค่าเพิ่มเติม — เมื่อสถานะงานวิจัยเปลี่ยนแปลง
(อนุมัติ/ไม่อนุมัติ/ขอแก้ไข/เผยแพร่/เก็บถาวร) ระบบสร้างการแจ้งเตือนให้ผู้ส่ง
งานวิจัยโดยอัตโนมัติผ่าน database trigger เดียวกับที่บันทึก
`approval_logs`/`audit_logs` อยู่แล้ว (รับประกันว่าไม่มีการเปลี่ยนสถานะครั้ง
ใดหลุดการแจ้งเตือน) ผู้ใช้ดูและทำเครื่องหมายอ่านแล้วได้ที่ไอคอนกระดิ่งใน
Header

ปิดการแจ้งเตือนประเภทนี้ได้ที่สวิตช์ในหน้านี้

### การแจ้งเตือนทางอีเมล

รองรับ [Resend](https://resend.com) (มี free tier) วิธีตั้งค่า:

1. สมัคร Resend แล้วสร้าง API key
2. ยืนยันโดเมนผู้ส่ง (sender domain) ตามขั้นตอนของ Resend
3. ใส่ค่าใน `.env.local`:
   ```
   RESEND_API_KEY=...
   RESEND_FROM_EMAIL=notifications@your-domain.org
   ```
4. เปิดสวิตช์ "การแจ้งเตือนทางอีเมล" ที่หน้านี้

เมื่อเปิดและตั้งค่าคีย์ครบแล้ว ระบบจะส่งอีเมลจริงทุกครั้งที่สถานะงานวิจัย
เปลี่ยนแปลง (เรียกจาก Server Action ในหน้าอนุมัติงานวิจัยหลังบันทึกสถานะ
สำเร็จ) — เป็นการทำงานแบบ best-effort หากส่งอีเมลไม่สำเร็จจะไม่ทำให้การ
เปลี่ยนสถานะล้มเหลวไปด้วย (มีการแจ้งเตือนในระบบสำรองอยู่แล้วเสมอ)

หากยังไม่ได้ตั้งค่า `RESEND_API_KEY` หน้านี้จะแสดงสถานะ "ยังไม่ได้ตั้งค่า
ผู้ให้บริการอีเมล" อย่างชัดเจน และระบบจะไม่พยายามส่งอีเมลจริง (log แจ้งไว้
ฝั่งเซิร์ฟเวอร์เท่านั้น)

## 10. System Logs (/superadmin/system-logs)

รองรับ centralized logging ในตัวแล้ว (ดู [`lib/logging/`](../lib/logging/))
— ส่ง error ระดับแอปพลิเคชัน (ผ่านการตัดข้อมูลอ่อนไหวออกแล้ว) ไปยัง Sentry
หรือ Better Stack (Logtail) โดยอัตโนมัติผ่าน Next.js `instrumentation.ts` เมื่อ
ตั้งค่า `LOG_PROVIDER` + คีย์ที่เกี่ยวข้องใน environment variables (ดู
`.env.example`) **เฉพาะตอน production เท่านั้น** — dev ยัง log ผ่าน console
เสมอ ไม่ส่งออกนอกเครื่อง

หน้านี้แสดงสถานะการเชื่อมต่อจริง (เชื่อมต่อแล้ว/ยังไม่ได้ตั้งค่า) **ไม่ใช่ log
ปลอม** — หากยังไม่ได้ตั้งค่า `LOG_PROVIDER` จะแสดงคำแนะนำการเชื่อมต่อแทน (รวมถึง
ทางเลือกอื่นที่ไม่มี built-in support ในแอปนี้ เช่น Vercel Log Drains, Axiom)
แอปนี้ไม่มีสิทธิ์ดึงข้อมูล log ย้อนหลังจาก Sentry/Better Stack กลับมาแสดงในหน้า
นี้ (provider ไม่เปิด API แบบนั้นให้) — ต้องดูที่แดชบอร์ดของ provider โดยตรง

## 11. System Health (/superadmin/system-health)

ตรวจสอบสถานะ Database, Supabase Auth และ Supabase Storage แบบสด
(เรียก query/endpoint จริงทุกครั้งที่โหลดหน้า ไม่มีการแคช) แสดงเวลาที่ตรวจ
สอบล่าสุดกำกับไว้เสมอ — แต่ละบริการตรวจสอบอิสระต่อกัน หากยังไม่ได้ตั้งค่า
Supabase จะแสดง "ยังไม่สามารถตรวจสอบอัตโนมัติได้" พร้อมคำแนะนำตั้งค่า
`.env.local` ไม่มีการแสดง credentials หรือรายละเอียดการเชื่อมต่อใดๆ

มี endpoint สาธารณะ `/api/health` (ไม่ต้องยืนยันตัวตน) สำหรับเชื่อมต่อบริการ
Uptime Monitoring ภายนอก (UptimeRobot, Better Uptime, Cloudflare Health
Checks) เพื่อให้ได้ประวัติย้อนหลังและการแจ้งเตือนอัตโนมัติเมื่อระบบมีปัญหา —
แอปนี้เองให้ได้แค่สถานะ ณ ขณะนั้นเท่านั้น ดูขั้นตอนตั้งค่าละเอียดใน
[`docs/uptime-monitoring.md`](uptime-monitoring.md)

- การสแกนไฟล์ค้างในหน้า Storage เป็นการประมาณการแบบ best-effort ไม่ใช่การ

- ไม่มีการตรวจสอบเนื้อไฟล์จริง (magic-byte) หรือสแกนมัลแวร์สำหรับไฟล์ที่อัปโหลด
  (ดูหัวข้อ 15)

## 14. ยืนยันตัวตนสองขั้นตอน (MFA) สำหรับ Super Admin

รองรับ MFA แบบ TOTP (Google Authenticator, Authy ฯลฯ) ผ่านความสามารถในตัวของ
Supabase Auth (`supabase.auth.mfa.*`) ไม่ต้องเพิ่มตารางหรือ backend เอง

**MFA เป็นข้อบังคับสำหรับบทบาท Super Admin โดยเฉพาะ** — บัญชี Super Admin ที่
ยังไม่มี MFA factor ที่ verified แล้วจะเข้า `/superadmin` หรือเส้นทางย่อยใดๆ
ไม่ได้เลย (ถูกเด้งไปตั้งค่าที่ `/setup-mfa` ก่อนเสมอ) ส่วนบทบาทอื่น
(Member/Staff/Librarian/Admin) MFA ยังคงเป็น**ทางเลือก**เหมือนเดิมทุกประการ —
ไม่ได้รับผลกระทบจากการเปลี่ยนแปลงนี้เลย (ตั้งค่าได้ที่ [`/account`](/account)
ตามปกติ แต่ไม่มีการบังคับหรือเด้งไปหน้าใดๆ)

### วิธีตั้งค่า

- **Super Admin**: ถูกเด้งไปที่ [`/setup-mfa`](/setup-mfa) อัตโนมัติเมื่อพยายาม
  เข้า `/superadmin` ครั้งแรกโดยยังไม่มี MFA — สแกน QR โค้ดด้วยแอปยืนยันตัวตน
  แล้วกรอกรหัส 6 หลักที่แสดง เสร็จแล้วระบบพาไปหน้าที่ตั้งใจจะเข้าโดยอัตโนมัติ
  (ตั้งค่าล่วงหน้าเองที่ `/account` ก่อนก็ได้เช่นกัน ผลลัพธ์เหมือนกัน)
- **บทบาทอื่น (ทางเลือก)**: ไปที่ [`/account`](/account) → หัวข้อ "ความปลอดภัย
  บัญชี — ยืนยันตัวตนสองขั้นตอน (MFA)" → กด "เพิ่มอุปกรณ์ยืนยันตัวตน (TOTP)"
  → สแกน QR โค้ด → กรอกรหัส 6 หลักเพื่อยืนยันและเปิดใช้งาน

### สิ่งที่ต้องเปิดใช้งานฝั่ง Supabase ก่อนเสมอ

- **Local (Supabase CLI)**: เปิดไว้ให้แล้วที่ `supabase/config.toml` หัวข้อ
  `[auth.mfa.totp]` (`enroll_enabled = true`, `verify_enabled = true`) — ต้อง
  รัน `npx supabase stop` ตามด้วย `npx supabase start` หลังแก้ค่านี้เพื่อให้มีผล
- **Supabase Cloud**: **ต้องเปิดเองที่ Dashboard** (Authentication > Providers
  > Multi-Factor Authentication) **ก่อน deploy ฟีเจอร์นี้ขึ้น production เสมอ**
  — ไม่ได้เปิดอัตโนมัติเมื่อ deploy ขึ้น production หากยังไม่เปิด Super Admin
  ทุกคนที่ยังไม่มี MFA จะเข้า `/setup-mfa` ไม่ได้เลย (enroll ล้มเหลวด้วย error
  จาก GoTrue) **ซึ่งหมายถึงล็อกตัวเองออกจาก `/superadmin` ทั้งระบบ** — ดูหัวข้อ
  "ขั้นตอนเปิดใช้งานใน Production" ด้านล่างสำหรับลำดับขั้นตอนที่ปลอดภัย

### กลไกการบังคับใช้จริง (ไม่ใช่แค่ UI สวยงาม)

Supabase Auth ใช้ระบบ **AAL (Authenticator Assurance Level)** ฝังอยู่ใน JWT —
`aal1` คือยืนยันด้วยรหัสผ่านอย่างเดียว, `aal2` คือยืนยัน MFA สำเร็จแล้วในเซสชัน
นั้น บังคับซ้ำ **3 ชั้น** ไม่พึ่งชั้นใดชั้นหนึ่งเพียงอย่างเดียว:

1. **`middleware.ts`** (`lib/supabase/middleware.ts`) — ก่อนหน้าเว็บ render
   เรียก `supabase.auth.mfa.getAuthenticatorAssuranceLevel()` แล้วแยก 2 กรณี
   จากค่าเดียว (ตาม docstring ของ Supabase: มี verified factor แล้ว `nextLevel`
   จะเป็น `aal2` เสมอ มิเช่นนั้นเป็น `aal1`):
   - `nextLevel === "aal1"` (**ไม่มี verified factor เลย**) → เด้งไป
     `/setup-mfa?redirect=<หน้าที่ต้องการ>`
   - `currentLevel === "aal1" && nextLevel === "aal2"` (**มี factor แล้วแต่
     เซสชันนี้ยังไม่ยืนยันขั้นที่สอง**) → เด้งไป `/mfa-challenge` เหมือนเดิม
   - `currentLevel === "aal2"` → ผ่าน
2. **`app/superadmin/layout.tsx`** — ตรวจ `hasVerifiedMfa` ซ้ำอีกชั้น (เผื่อ
   กรณีมาถึง layout โดยไม่ผ่าน middleware) เด้งไป `/setup-mfa` เช่นกันหากไม่ผ่าน
3. **`requireMinRank()`** (`lib/data/admin-guard.server.ts`) — เมื่อเรียกด้วย
   `minRank >= 50` (ทุก Server Action ใน `app/superadmin/*/actions.ts`) จะตรวจ
   `currentLevel === "aal2"` ซ้ำอีกชั้นก่อนดำเนินการเสมอ **แม้ Server Action
   จะถูกเรียกโดยตรงโดยไม่ผ่านการนำทางหน้าปกติก็ตาม** — คืน error ที่ปลอดภัย
   หาก MFA assurance ไม่พอ ไม่ทำงานใดๆ ต่อ

**ทดสอบแล้วจริงผ่าน browser จริง + TOTP code ที่คำนวณจริงจาก secret** (ไม่ใช่
แค่ mock): บัญชีที่ไม่มี MFA เข้า `/superadmin` ไม่ได้ → ตั้งค่าที่ `/setup-mfa`
สำเร็จ → เซสชันใหม่ (ยังไม่ stepped up) ถูกเด้งไป `/mfa-challenge` → ยืนยันสำเร็จ
เข้า dashboard ได้จริง → เรียก Server Action ตรงตอน `aal1` ถูกปฏิเสธ ตอน `aal2`
ผ่าน → หลังถูก Super Admin คนอื่นรีเซ็ต MFA เซสชันที่แม้จะเป็น `aal2` อยู่ก่อน
แล้วก็ถูกเด้งกลับไป `/setup-mfa` ทันทีในคำขอถัดไป (ไม่มีช่องให้เห็นข้อมูลใน
dashboard หลุดออกมาแม้แต่ครั้งเดียว)

### แก้ปัญหา "ล็อกตัวเองออกจากระบบ" (chicken-and-egg lockout)

`/setup-mfa` (เหมือน `/mfa-challenge` และ `/login`) **ไม่ได้อยู่ภายใต้เงื่อนไข
การบังคับ MFA ข้างต้นเลย** — ต้องการแค่ล็อกอินแล้วเท่านั้น (ดู
`LOGIN_REQUIRED_PREFIXES` ใน `lib/supabase/middleware.ts`) จึงไม่มีทางเกิด
ลูปที่เข้าไปตั้งค่า MFA เองไม่ได้ Super Admin คนแรกที่เพิ่งสร้างผ่าน SQL (ดู
หัวข้อ 1) ยังคงเข้า `/setup-mfa` ได้เสมอแม้จะยังไม่มี MFA เลยสักตัว —
ต่างจากการออกแบบเดิม (ก่อนหน้านี้) ที่เลี่ยงปัญหานี้ด้วยการ**ไม่บังคับ MFA
เลย** ตอนนี้แก้ด้วยการ**เว้นเฉพาะหน้าตั้งค่าเองออกจากด่านตรวจสอบ** แทน

### กรณีทำอุปกรณ์ MFA หาย (กู้คืนฉุกเฉิน)

มีหน้า UI สำหรับ Super Admin คนอื่นช่วยรีเซ็ต MFA ให้ผู้ใช้ที่ทำอุปกรณ์หายแล้ว
ที่ `/superadmin/users/[id]` หัวข้อ "ยืนยันตัวตนสองขั้นตอน (MFA)" — ใช้
[Supabase Auth Admin API](https://supabase.com/docs/reference/javascript/auth-admin-mfa-deletefactor)
(`supabase.auth.admin.mfa.listFactors`/`deleteFactor`) ลบ factor จริง ไม่ใช่
รัน SQL ตรงอีกต่อไป (แต่ยังใช้วิธี SQL เดิมได้เช่นกันหากจำเป็น เช่น
Service Role Key ยังไม่ได้ตั้งค่า — ดูหมายเหตุท้ายหัวข้อนี้)

**ขั้นตอน**:
1. ไปที่ `/superadmin/users/[id]` ของผู้ใช้ที่ทำอุปกรณ์หาย → หัวข้อ "ยืนยันตัวตน
   สองขั้นตอน (MFA)" จะแสดงรายการอุปกรณ์ปัจจุบัน (ชื่อ, สถานะยืนยันแล้ว/ยังไม่
   ยืนยัน — ไม่แสดง secret/QR/recovery code ใดๆ เนื่องจาก Admin API เองก็ไม่คืน
   ข้อมูลเหล่านี้กลับมาอยู่แล้ว)
2. กด "รีเซ็ต MFA" → **ขั้นที่ 1**: พิมพ์อีเมลของผู้ใช้เป้าหมายให้ตรงกันเพื่อ
   ยืนยันตัวตนก่อน
3. **ขั้นที่ 2**: กรอกเหตุผล (บังคับ) แล้วพิมพ์ `RESET MFA` ให้ตรงกันทุกตัวอักษร
   เพื่อยืนยันการกระทำ
4. ระบบลบอุปกรณ์ MFA ทั้งหมดของผู้ใช้ทันที, บันทึก `audit_logs`
   (`action: "mfa_reset"` พร้อมผู้กระทำ/เป้าหมาย/เหตุผล/ผลลัพธ์), ส่ง in-app
   notification และอีเมล (ถ้าเปิดใช้งานที่ `/superadmin/notifications`) แจ้ง
   เจ้าของบัญชีว่า MFA ถูกรีเซ็ต
5. ผู้ใช้กลับไปอยู่ที่สถานะ "ยังไม่ได้ตั้งค่า MFA" ทันที — **เนื่องจาก MFA เป็น
   ข้อบังคับสำหรับ Super Admin (ดูหัวข้อด้านบน) ผู้ใช้จะถูกเด้งไป `/setup-mfa`
   โดยอัตโนมัติทันทีที่พยายามเข้า `/superadmin` ครั้งถัดไป** (ต่างข้อสำคัญจาก
   ก่อนหน้านี้ ตอนที่ MFA ยังเป็นทางเลือก) — **หากอุปกรณ์เดิมเคยยืนยันแล้ว
   (`verified`) ผู้ใช้จะถูกออกจากระบบทันทีในทุกเซสชัน/อุปกรณ์ที่ล็อกอินค้างอยู่**
   (พฤติกรรมของ Supabase Auth Admin API เอง ไม่ใช่โค้ดที่แอปนี้เขียนเพิ่ม) —
   ทดสอบแล้วจริงว่าแม้เซสชันเดิมจะยืนยัน MFA ไว้แล้ว (`aal2`) ก่อนถูกรีเซ็ต ก็ยัง
   ถูกเด้งกลับไป `/setup-mfa` ทันทีในคำขอถัดไป ไม่มีช่องให้เข้าถึง dashboard ต่อ
   ด้วยเซสชันเก่าได้เลย

**กฎความปลอดภัยที่บังคับจริง** (ตรวจซ้ำฝั่งเซิร์ฟเวอร์ทุกข้อ ไม่พึ่ง UI อย่าง
เดียว — ทดสอบแล้วจริงผ่านการเรียก Server Action ตรงด้วย session จริงของบัญชี
ระดับต่างๆ):
- ต้องมีสิทธิ์ Super Admin (rank ≥ 50) เท่านั้น — Admin/Librarian/Staff/Member
  เรียกไม่ได้แม้จะพยายามเรียก Server Action ตรงๆ ก็ตาม (`requireMinRank(50)`)
- **Super Admin ห้ามรีเซ็ต MFA ของตัวเอง** — ต้องให้ Super Admin คนอื่นเป็นผู้
  ดำเนินการเสมอ (ปุ่มถูกซ่อนที่ UI และ Server Action ปฏิเสธซ้ำอีกชั้นหาก
  `userId` เป้าหมายตรงกับผู้เรียก)
- ต้องพิมพ์ `RESET MFA` ให้ตรงกันทุกตัวอักษรและระบุเหตุผล (ทั้งสองอย่างบังคับ
  ตรวจซ้ำฝั่งเซิร์ฟเวอร์) มิฉะนั้นปฏิเสธการทำรายการ

**ข้อจำกัด**:
- ต้องตั้งค่า `SUPABASE_SERVICE_ROLE_KEY` ไว้ก่อนเสมอ (Admin API ทำงานผ่าน
  Service Role เท่านั้น) — ไม่ได้ตั้งค่าไว้จะแสดงข้อความแจ้งเตือนชัดเจนแทนการ
  error แบบไม่ทราบสาเหตุ ไม่ใช่ตกไปใช้ SQL อัตโนมัติ (ยังต้องรัน SQL ด้วยมือ
  ตามที่แสดงด้านล่างหากจำเป็นเร่งด่วนจริงๆ)
- Admin API สำหรับ MFA (`auth.admin.mfa.*`) เป็น `@experimental` ใน supabase-js
  ปัจจุบัน — เป็น REST endpoint จริงของ GoTrue ไม่ใช่ฟีเจอร์ที่แอปนี้จำลองขึ้นเอง
  แต่ยังควรทดสอบซ้ำหลังอัปเดต Supabase/supabase-js เวอร์ชันใหม่เสมอ
- ผู้ใช้ที่ถูกรีเซ็ต MFA ต้องตั้งค่าใหม่ที่ `/setup-mfa` (ถูกเด้งไปอัตโนมัติ)
  ก่อนจึงจะเข้า `/superadmin` ได้อีกครั้ง — ไม่มีทางเข้าถึงส่วนจัดการระบบด้วย
  สถานะ "ยังไม่ได้ตั้งค่า MFA" อีกต่อไป (ต่างจากพฤติกรรมเดิมก่อนหน้านี้)

**วิธี SQL เดิม** (ยังใช้ได้ กรณี Service Role Key ยังไม่พร้อมหรือต้องการรีเซ็ต
เร่งด่วนโดยตรงที่ฐานข้อมูล):

```sql
-- แทน 'locked-out-user@example.com' ด้วยอีเมลบัญชีที่ทำอุปกรณ์ MFA หาย
delete from auth.mfa_factors
where user_id = (select id from auth.users where email = 'locked-out-user@example.com');
```

ไม่ว่าจะรีเซ็ตผ่าน UI หรือ SQL วิธีนี้ก็ตาม ผลลัพธ์เหมือนกันทุกประการ: กลับไปอยู่
สถานะ "ไม่มี verified factor" แล้วถูกด่านบังคับ MFA (หัวข้อด้านบน) เด้งไปตั้งค่า
ใหม่ที่ `/setup-mfa` โดยอัตโนมัติในการเข้า `/superadmin` ครั้งถัดไปเหมือนกัน

### ขั้นตอนเปิดใช้งานใน Production

ต้องทำตามลำดับนี้เสมอเพื่อไม่ให้ Super Admin ที่มีอยู่ถูกล็อกออกจากระบบโดยไม่
ตั้งใจ:

1. เปิด TOTP MFA ที่ Supabase Dashboard (Authentication > Providers >
   Multi-Factor Authentication) **ก่อน** deploy โค้ดฟีเจอร์นี้เสมอ (ดูหัวข้อ
   "สิ่งที่ต้องเปิดใช้งานฝั่ง Supabase ก่อนเสมอ" ด้านบน)
2. แจ้ง Super Admin ทุกคนล่วงหน้าว่าเข้าครั้งถัดไปจะถูกบังคับตั้งค่า MFA ก่อน
   เพื่อไม่ให้ตกใจเมื่อถูกเด้งไป `/setup-mfa`
3. Deploy โค้ด แล้วให้ Super Admin แต่ละคนล็อกอินและตั้งค่า MFA ที่
   `/setup-mfa` ด้วยตนเองทันทีที่สะดวก (ระบบเด้งไปให้อัตโนมัติอยู่แล้ว ไม่ต้อง
   ทำอะไรเพิ่มฝั่งแอป)
4. ตรวจสอบที่ **`/superadmin/mfa-status`** (เพิ่มในช่วงที่ 22 — ดูหัวข้อ 19)
   เพื่อยืนยันว่า Super Admin ทุกคนตั้งค่าสำเร็จในหน้าเดียว แทนการดูทีละคนที่
   `/superadmin/users/[id]` แบบเดิม

### วิธีทดสอบ

**Development** (local, ไม่มีแอปยืนยันตัวตนจริงในมือก็ทดสอบได้):
1. ล็อกอินด้วยบัญชี Super Admin ที่ยังไม่มี MFA แล้วพยายามเข้า
   `/superadmin/overview` ตรงๆ → ต้องถูกเด้งไป `/setup-mfa`
2. ที่ `/setup-mfa` กด "สแกนไม่ได้? กรอกรหัสด้วยตนเอง" เพื่อดู secret (base32)
   แล้วคำนวณรหัส TOTP 6 หลักด้วยเครื่องมือ/สคริปต์ที่รองรับ RFC 6238 (หรือใช้
   แอปยืนยันตัวตนจริงสแกน QR ก็ได้) กรอกยืนยัน → ต้องเข้า `/superadmin` ได้ทันที
3. ล็อกเอาต์แล้วล็อกอินใหม่ (เซสชันใหม่) → พยายามเข้า `/superadmin` อีกครั้ง
   ต้องถูกเด้งไป `/mfa-challenge` (ไม่ใช่ `/setup-mfa` อีกแล้ว เพราะมี MFA แล้ว)
   ให้กรอกรหัส 6 หลักจากอุปกรณ์เดิม
4. ทดสอบว่าเรียก Server Action ของ `/superadmin/*` โดยตรง (ไม่ผ่านการนำทางหน้า
   ปกติ) ตอนเซสชันยังเป็น `aal1` ถูกปฏิเสธด้วยข้อความ "ต้องยืนยันตัวตนสองขั้น
   ตอน..." เสมอ
5. ให้ Super Admin อีกคนรีเซ็ต MFA ของบัญชีทดสอบ (ดูหัวข้อ "กรณีทำอุปกรณ์ MFA
   หาย" ด้านบน) แล้วลองเข้า `/superadmin` ด้วยเซสชันเดิม (แม้จะเคยเป็น `aal2`
   มาก่อน) → ต้องถูกเด้งไป `/setup-mfa` ทันที

**Production**: ทำตามลำดับใน "ขั้นตอนเปิดใช้งานใน Production" ด้านบนก่อนเสมอ
แล้วให้ Super Admin จริงอย่างน้อย 1 คนทดสอบ enroll ด้วยแอปยืนยันตัวตนจริง
(Google Authenticator/Authy) ยืนยันว่า QR โค้ดสแกนได้จริงและรหัส 6 หลักที่แอป
สร้างได้รับการยอมรับ ก่อนประกาศให้ Super Admin คนอื่นทำตาม

## 15. ความปลอดภัยของไฟล์อัปโหลด

ตรวจสอบชนิด/นามสกุล/ขนาดไฟล์ทั้งฝั่ง client และ server แล้ว (รวมถึงตรวจว่า
นามสกุลไฟล์ตรงกับ MIME type ที่ตรวจพบหรือไม่ — กันไฟล์เปลี่ยนนามสกุลหลอกลวง
แบบพื้นฐาน) **แต่ยังไม่มีการตรวจสอบเนื้อไฟล์จริง (magic-byte) หรือสแกนมัลแวร์**
เนื่องจากสถาปัตยกรรมอัปโหลดไฟล์ตรงจาก Browser ไปยัง Storage โดยไม่ผ่าน
เซิร์ฟเวอร์ของแอป — ดูรายละเอียดชั้นการตรวจสอบทั้งหมดและคำแนะนำการเชื่อมต่อ
บริการสแกนมัลแวร์ก่อนเปิดใช้งานจริงที่ [`docs/file-security.md`](file-security.md)

## 16. จัดลำดับหมวดหมู่/หน่วยงาน (/superadmin/categories, /superadmin/organizations)

ลากวางเพื่อจัดลำดับการแสดงผลของหมวดหมู่งานวิจัยและหน่วยงาน — มีผลกับลำดับที่
แสดงในหน้าเว็บสาธารณะ (หน้าแรก, `/research`, ตัวกรองค้นหา) และตัวเลือกในฟอร์ม
ส่งงานวิจัยทันที **การเพิ่ม/แก้ไขชื่อ/ปิดใช้งาน/ลบยังทำที่
`/dashboard/categories` และ `/dashboard/organizations` เหมือนเดิมทุกประการ**
(Librarian/Admin rank ≥ 30 จัดการได้เหมือนเดิม ไม่กระทบสิทธิ์เดิม) — สองหน้านี้
เป็นแค่การ**จัดลำดับ**เพิ่มเติมเท่านั้น

### วิธีใช้

- **ลากวาง**: จับที่ไอคอน `⠿` (ซ้ายสุดของแต่ละแถว) แล้วลากขึ้น/ลงเพื่อจัดลำดับ
  ภายในกลุ่มเดียวกัน — หมวดหมู่ย่อยลากข้ามไปวางในหมวดหมู่หลักอื่นได้โดยตรง
- **ปุ่มเลื่อนขึ้น/ลง**: ลูกศรข้างไอคอนลาก ใช้แทนการลากได้ทั้งหมด (สำหรับจอสัมผัส/
  คีย์บอร์ด/กรณีลากไม่สะดวก) — เลื่อนได้เฉพาะภายในกลุ่มเดียวกัน
- **ย้ายหมวดหมู่ย่อยข้ามหมวดหมู่หลักแบบไม่ต้องลาก**: แต่ละแถวหมวดหมู่ย่อยมีเมนู
  เลือกหมวดหมู่หลักปลายทางอยู่ด้านขวา เลือกแล้วย้ายทันทีโดยไม่ต้องลาก
- ทุกการเปลี่ยนแปลงบันทึกทันทีที่ปล่อยเมาส์/กดปุ่ม (ไม่มีปุ่ม "บันทึก" แยก) —
  แถบสถานะด้านบนแสดง "กำลังบันทึก...", "บันทึกสำเร็จ" หรือข้อความ error ที่
  ชัดเจน หากบันทึกไม่สำเร็จ ลำดับจะคืนกลับเป็นค่าก่อนหน้าอัตโนมัติ

### พฤติกรรมของระบบหลังจัดลำดับ

- หน้าเว็บสาธารณะที่แสดงหมวดหมู่ (หน้าแรก, `/research`, ตัวกรองค้นหา, ฟุตเตอร์)
  และตัวเลือกหน่วยงานในฟอร์มส่งงานวิจัย จะเรียงตามลำดับใหม่ทันทีในการโหลดหน้า
  ถัดไป (ผ่าน `revalidatePath`)
- หมวดหมู่เรียงแบบ **ต้นไม้แบนราบ**: หมวดหมู่หลักเรียงตามลำดับของตัวเองก่อน
  แล้วตามด้วยหมวดหมู่ย่อยของมันตามลำดับของมันเอง ก่อนขึ้นหมวดหมู่หลักถัดไป (ไม่ใช่
  เรียงลำดับแบบผสมข้ามกลุ่ม)
- หมวดหมู่/หน่วยงานที่สร้างใหม่ (ผ่าน `/dashboard/categories`,
  `/dashboard/organizations`) จะถูกจัดให้อยู่ **ท้ายกลุ่มของตัวเองโดยอัตโนมัติ**
  เสมอ (บังคับด้วย database trigger ไม่ต้องแก้ฟอร์มเพิ่มข้อมูลเดิม)

### สิทธิ์และความปลอดภัย

- **เฉพาะ Super Admin (rank ≥ 50) เท่านั้นที่จัดลำดับได้** — ตรวจสอบซ้ำ 2 ชั้น:
  `requireMinRank(50)` ใน Server Action และ database trigger บนคอลัมน์
  `sort_order` เอง (ปฏิเสธแม้เรียกผ่าน API/SQL โดยตรงข้ามหน้าเว็บ) — Librarian/
  Admin (rank ≥ 30) ยังแก้ไขฟิลด์อื่น (ชื่อ, คำอธิบาย, สถานะเปิด/ปิด) ได้ตามเดิม
  ที่ `/dashboard/categories`/`/dashboard/organizations` ไม่ถูกจำกัดเพิ่ม
- **ป้องกันความสัมพันธ์วนซ้ำ (circular reference)**: database trigger ปฏิเสธ
  การกำหนดหมวดหมู่หลักที่จะทำให้เกิดวงวน (เช่น A เป็นหลักของ B แล้ว B ถูกกำหนด
  เป็นหลักของ A) ทำงานทั้งจากหน้านี้และ dropdown เดิมที่ `/dashboard/categories`
- **ใช้ transaction**: การจัดลำดับ/ย้ายแต่ละครั้งเรียกผ่าน RPC function เดียว
  (`superadmin_reorder_categories`, `superadmin_move_category`,
  `superadmin_reorder_organizations`) ซึ่งเป็น transaction เดียวจบในตัวตาม
  ธรรมชาติของ Postgres function call — ถ้าบันทึกแถวใดล้มเหลวระหว่างทาง ทุกแถว
  ในคำสั่งเดียวกันจะ rollback ทั้งหมด ไม่มีสถานะครึ่งๆ กลางๆ ค้างอยู่
- ทุกการจัดลำดับ/ย้ายบันทึก `audit_logs` (`category_reorder`,
  `category_move_parent`, `organization_reorder`) พร้อมผู้กระทำและรายการ id
  ที่เปลี่ยนแปลง
- **ห้ามลบหมวดหมู่/หน่วยงานที่มีงานวิจัยอ้างอิงอยู่** (ตรวจสอบที่
  `/dashboard/categories`/`/dashboard/organizations` เดิมอยู่แล้ว — ปฏิเสธและ
  แนะนำให้ปิดใช้งานแทนหากมีงานวิจัยผูกอยู่) หน้าจัดลำดับนี้ไม่มีปุ่มลบ ไม่กระทบ
  พฤติกรรมเดิม

## 17. งานพื้นหลัง (/superadmin/pdf-processing, /superadmin/file-security, /superadmin/jobs)

เพิ่มในช่วงที่ 20 — งานประมวลผลหนัก (ดึงข้อความ PDF, สแกนมัลแวร์, หมดอายุสิทธิ์
เข้าถึง, แจ้งเตือนผู้ติดตามหมวดหมู่) รันเป็น background job ผ่าน persistent
queue ในฐานข้อมูลเดิม แทนการรันแบบ synchronous ในคำขออัปโหลด/แก้ไข/เผยแพร่:

- **`/superadmin/pdf-processing`**: สั่ง backfill/ประมวลผลข้อความ PDF ใหม่เป็น
  ชุด กรองตามสถานะการดึงข้อความ (ยังไม่มีข้อความ/ล้มเหลว/ไม่พบข้อความ/ไฟล์ถูก
  แทนที่) — มีแท็บ "OCR เอกสารสแกน" เพิ่มในช่วงที่ 23 สำหรับสั่ง OCR เป็นชุด
  เฉพาะเอกสารที่ดึงข้อความปกติแล้วได้ "ไม่พบข้อความ" (ต้องตั้งค่า OCR provider
  และได้รับอนุมัติส่งข้อมูลออกก่อนจึงจะสำเร็จจริง — ดู
  [`docs/ocr-operations.md`](ocr-operations.md))
- **`/superadmin/file-security`**: สั่งสแกนความปลอดภัยไฟล์ PDF เดิมซ้ำเป็นชุด
  กรองตามสถานะสแกน — ไฟล์ที่เผยแพร่อยู่ยังใช้งานได้ปกติระหว่างรอคิว หากพบว่า
  ไม่ปลอดภัยจะปิดการเข้าถึงอัตโนมัติทันทีที่สแกนเสร็จ
- ทั้งสองหน้ามีปุ่ม "ประมวลผลคิวเดี๋ยวนี้" (เร่งประมวลผลโดยไม่ต้องรอรอบ Cron)
  แสดงประวัติชุดงานล่าสุดพร้อม progress (รีเฟรชอัตโนมัติทุก 5 วินาทีตั้งแต่
  ช่วงที่ 25 พร้อมเวลาประมาณที่เหลือ) และปุ่มลองใหม่สำหรับ job ที่ล้มเหลวถาวร
  — ตั้งแต่ช่วงที่ 25 ทั้งสองหน้า (และแท็บ OCR) มีปุ่มเพิ่มเติม **"ประมวลผล
  ทั้งหมดตามตัวกรอง (ไม่จำกัด 500 รายการ)"** สำหรับกรณีรายการเกินขีดจำกัดของ
  หน้าเว็บ — ไม่ใช่ทุกตัวกรองรองรับ (ดู
  [`docs/background-jobs.md`](background-jobs.md) หัวข้อ 11.4)
- ตั้งค่า Cron สำหรับ Production ที่ `/api/jobs/process` (ป้องกันด้วย
  `CRON_SECRET`) — รายละเอียดเต็มดูที่
  [`docs/background-jobs.md`](background-jobs.md)
- การหมดอายุสิทธิ์เข้าถึงเอกสาร (ทั้ง `access_requests` และ
  `document_access_grants`) และการแจ้งเตือนตอนเผยแพร่งานวิจัย ก็ใช้
  โครงสร้าง background job เดียวกันนี้ — ดู
  [`docs/document-access-requests.md`](document-access-requests.md)
- **`/superadmin/jobs`** (เพิ่มในช่วงที่ 25) — Dead-letter Queue กลาง รวมงาน
  ที่ล้มเหลวถาวรทุกประเภทงานในหน้าเดียว (ต่างจากรายการ "งานที่ล้มเหลวถาวร" ที่
  หน้า pdf-processing/file-security/data-quality ซึ่งกรองแค่ประเภทงานของหน้า
  นั้นๆ) ลองใหม่/ยกเลิก/ทำเครื่องหมายว่าแก้ไขแล้วได้ ทุกการดำเนินการบันทึก
  Audit Log เสมอ Super Admin จะได้รับแจ้งเตือน in-app และอีเมล (ถ้าตั้งค่า
  provider ไว้) ทันทีที่มี job เข้า DLQ — หน้าเดียวกันนี้ยังใช้ปรับ **concurrency**
  (จำนวนงานสูงสุดที่ประมวลผลพร้อมกัน) แยกตามประเภทงานได้ด้วย ดู
  [`docs/background-jobs.md`](background-jobs.md) หัวข้อ 11

## 18. คุณภาพข้อมูล (/superadmin/data-quality)

เพิ่มในช่วงที่ 22 — ต่อยอดระบบตรวจงานวิจัยซ้ำเดิม (ช่วงที่ 19) ด้วยการตรวจสอบ
ย้อนหลังทั้งระบบแบบ batch และเกณฑ์ที่ปรับน้ำหนักได้ **ยังคงหลักการ "ไม่มีการ
รวมข้อมูล (merge) อัตโนมัติ" เดิมทุกประการ** — เป็นแค่การตรวจสอบและบันทึกคู่ที่
น่าสงสัยเพิ่มเติมเท่านั้น การรวมข้อมูลจริงยังต้องยืนยันด้วยตนเองที่
`/dashboard/duplicate-reviews` เหมือนเดิม

### `/superadmin/data-quality` — ตรวจสอบย้อนหลังทั้งระบบ

1. กรองรายการที่ต้องการตรวจสอบด้วยปี/หมวดหมู่/สถานะเผยแพร่/เฉพาะที่แก้ไข
   ล่าสุด (30 วัน)
2. เลือกหลายรายการพร้อมกัน กำหนด "ขนาด batch สูงสุดต่อครั้ง" (กันสร้าง job
   จำนวนมากเกินไปในคำสั่งเดียว) แล้วกด "ตรวจสอบที่เลือก"
3. ระบบสร้าง background job หนึ่งงานต่อหนึ่งงานวิจัย — ดูความคืบหน้าที่ "ชุดงาน
   ล่าสุด" (จำนวนที่ตรวจแล้ว/กำลังตรวจ/ล้มเหลว) กดปุ่ม "ประมวลผลคิวเดี๋ยวนี้"
   เพื่อเร่งได้โดยไม่ต้องรอรอบ Cron
4. งานที่ล้มเหลวถาวร (ครบจำนวนครั้งลองใหม่แล้ว) มีปุ่ม "ลองใหม่" ให้แต่ละรายการ
5. ผลลัพธ์ทั้งหมดไปปรากฏเป็นคู่ที่น่าสงสัยที่ `/dashboard/duplicate-reviews`
   ตามปกติ — เจ้าหน้าที่ต้องตรวจสอบและยืนยันเองเสมอ ไม่มีการรวมอัตโนมัติ
6. ทุกการสั่งตรวจสอบเป็นชุดบันทึก Audit Log

### `/superadmin/data-quality/settings` — เกณฑ์การตรวจสอบ

ปรับน้ำหนักที่ใช้คำนวณคะแนนความคล้าย 5 อย่าง (ความคล้ายชื่อเรื่อง, ผู้วิจัย
หลัก, ปีเผยแพร่, DOI/ISBN/เลขอ้างอิง, hash ของไฟล์) — **ผลรวมต้องเท่ากับ 100
พอดี** (มีตัวช่วยแสดงผลรวมสดๆ ขณะพิมพ์ ปุ่มบันทึกถูกปิดใช้งานจนกว่าผลรวมจะถูก
ต้อง) พร้อมเกณฑ์ระดับความเชื่อมั่นต่ำ/กลาง/สูง (ต่ำ = คะแนนขั้นต่ำที่จะบันทึก
เป็นคู่น่าสงสัย)

- **การแก้ไขแต่ละครั้งสร้างเป็นเวอร์ชันใหม่เสมอ ไม่ทับของเดิม** — ตรวจสอบ
  ย้อนหลังได้เสมอว่าคู่ที่บันทึกไว้เกิดจากเกณฑ์เวอร์ชันใด (ตารางประวัติด้าน
  ล่างฟอร์มแสดงทุกเวอร์ชันที่เคยใช้)
- ปุ่ม "คืนค่าเริ่มต้น" สร้างเวอร์ชันใหม่ด้วยค่าเดิมตอนติดตั้งระบบ (title
  50/author 20/year 10/identifier 15/file_hash 5, threshold 35/60/85)
- ทุกการเปลี่ยนแปลงบันทึก Audit Log พร้อมค่าที่ตั้งใหม่ทั้งหมด
- เฉพาะ Super Admin (rank ≥ 50) เท่านั้นที่แก้ไขได้ — บังคับทั้งชั้น RLS และใน
  ฟังก์ชัน SQL เอง (RBAC สองชั้นตามธรรมเนียมเดิม)

รายละเอียดสถาปัตยกรรมเต็มดูที่ [`docs/data-quality.md`](data-quality.md)

## 19. สถานะ MFA (/superadmin/mfa-status)

เพิ่มในช่วงที่ 22 — ภาพรวมสถานะ MFA ของ Super Admin ทุกคนในหน้าเดียว (แทนการ
ดูทีละคนที่ `/superadmin/users/[id]` แบบเดิม) แสดง:

- ชื่อและอีเมล
- สถานะ MFA: **ตั้งค่าแล้ว** (มีอุปกรณ์ที่ verified) / **ยังไม่ได้ตั้งค่า** /
  **ถูกรีเซ็ต ต้องตั้งค่าใหม่** (เคยตั้งค่าแล้วถูก Super Admin คนอื่นรีเซ็ตไป
  ยังไม่ได้ตั้งค่าใหม่ — แยกจาก "ยังไม่ได้ตั้งค่า" โดยตรวจ Audit Log เหตุการณ์
  `mfa_reset` ที่สำเร็จของผู้ใช้คนนั้น)
- วันที่ยืนยัน MFA ล่าสุด (จาก `last_challenged_at` ของอุปกรณ์ที่ verified —
  ไม่มีค่านี้แสดง "—")
- สถานะบัญชี (ใช้งานได้/ถูกระงับ)
- ลิงก์ไปยัง `/superadmin/users/[id]` สำหรับจัดการ/รีเซ็ต MFA ตามสิทธิ์เดิม
  ทุกประการ (ไม่มีปุ่มรีเซ็ตตรงในหน้านี้ — ต้องไปทำที่หน้าเดิมเสมอ)

**แสดงคำเตือนชัดเจน** (แถบสีแดง) หากมี Super Admin ที่ยังไม่ได้ตั้งค่า MFA หรือ
ถูกรีเซ็ตค้างอยู่ — ทั้งสองสถานะแปลว่าบัญชีนั้นเข้า `/superadmin/*` ไม่ได้จนกว่า
จะตั้งค่าที่ `/setup-mfa` (บังคับอัตโนมัติโดยระบบเดิม ไม่ใช่ช่องโหว่ — ดูหัวข้อ
14)

**ไม่แสดง recovery code, secret, QR code หรือรายละเอียด factor เชิงลึกใดๆ
เลย** — ใช้ข้อมูลเดียวกับที่หน้า `/superadmin/users/[id]` แสดงอยู่แล้ว (status/
วันที่เท่านั้น) เข้าถึงได้เฉพาะ Super Admin เท่านั้น (rank ≥ 50 + MFA aal2 —
บังคับที่ `middleware.ts` และ `app/superadmin/layout.tsx` เหมือนทุกหน้าใน
`/superadmin/*`)
