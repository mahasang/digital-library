# แนวทางสำรองข้อมูลและการกู้คืน (Backup & Recovery)

เอกสารนี้อธิบายว่าระบบมีข้อมูลอะไรที่ต้องสำรอง เก็บไว้ที่ไหน และจะกู้คืนอย่างไร
หากเกิดเหตุข้อมูลสูญหาย/เสียหาย **ไม่มีขั้นตอนใดในเอกสารนี้ที่เปิดใช้บริการ
แบบมีค่าใช้จ่ายให้อัตโนมัติ — การเปิดใช้ฟีเจอร์ backup แบบชำระเงินของ Supabase
(ถ้าต้องการ) เป็นการตัดสินใจที่ผู้ดูแลระบบต้องทำเองในแดชบอร์ด**

> หน้า `/superadmin/backups` ในแอปแสดงเฉพาะสถานะ (ซึ่งจะเป็น "ไม่พร้อมใช้งาน"
> เสมอ เนื่องจาก Supabase ไม่มี API ให้แอปภายนอกอ่านสถานะ/สั่งสำรองข้อมูลได้)
> พร้อมลิงก์มาที่เอกสารฉบับนี้ — ไม่มีปุ่ม "สำรองข้อมูลตอนนี้" ในแอปโดยเจตนา
> เพราะไม่มี API รองรับจริง การสำรองข้อมูลทั้งหมดต้องทำตามขั้นตอนด้านล่างเอง

## 1. ข้อมูลที่ต้องสำรอง

ระบบมีข้อมูล 2 ส่วนที่แยกจากกันและต้องสำรองแยกกัน:

| ส่วนข้อมูล | อยู่ที่ไหน | ความสำคัญ |
| --- | --- | --- |
| ฐานข้อมูล PostgreSQL (ตารางทั้งหมด, RLS policies, functions, triggers) | Supabase Database | สูงสุด — เมทาดาทางานวิจัย, บัญชีผู้ใช้, บทบาท, ประวัติการอนุมัติ |
| ไฟล์ใน Supabase Storage (`research-documents`, `research-covers`, `submission-attachments`, `site-assets`) | Supabase Storage (S3-compatible) | สูงสุด — ไฟล์ PDF ต้นฉบับ, โลโก้/favicon ที่ metadata ในฐานข้อมูลอ้างอิงถึง |

**ข้อควรระวัง**: การสำรองเฉพาะฐานข้อมูลโดยไม่สำรองไฟล์ใน Storage (หรือกลับกัน)
จะทำให้กู้คืนแล้วข้อมูลไม่ตรงกัน (เช่น แถวใน `research_items` ชี้ไปยัง `pdf_file`
ที่ไม่มีไฟล์จริงอยู่แล้ว) จึงต้องสำรองทั้งสองส่วนพร้อมกันและเก็บคู่กันเสมอ

**ตารางที่ไม่จำเป็นต้องสำรองอย่างเข้มงวด**: `rate_limit_events` เก็บข้อมูลชั่วคราว
สำหรับจำกัดอัตราการใช้งานเท่านั้น (ลบตัวเองอัตโนมัติเมื่อพ้นช่วงเวลาที่กำหนด)
ไม่มีคุณค่าระยะยาว ไม่จำเป็นต้องรวมอยู่ใน backup ก็ได้ — ส่วน `notifications`
(การแจ้งเตือนในระบบ) เป็นข้อมูลผู้ใช้ตามปกติ ควรสำรองเช่นเดียวกับตารางอื่น

## 2. ทางเลือกการสำรองข้อมูล

### 2.1 Supabase Automatic Backups (ในตัว, ตามแผนราคาโปรเจกต์)

Supabase มีระบบสำรองฐานข้อมูลอัตโนมัติในตัวอยู่แล้ว (ความถี่และระยะเวลาเก็บ
ย้อนหลังขึ้นกับแผนราคาของโปรเจกต์ — บางแผนมีค่าใช้จ่ายเพิ่มเติม) ตรวจสอบและ
จัดการได้ที่ **Supabase Dashboard > Database > Backups**

- แผนฟรี (Free tier): โดยทั่วไปไม่มี automatic backup แบบเก็บย้อนหลังยาว —
  ควรใช้วิธี manual backup ในข้อ 2.2 แทนหรือเสริม
- แผนที่มีค่าใช้จ่าย: มี daily backups และบางแผนมี Point-in-Time Recovery (PITR)
  **การอัปเกรดแผนหรือเปิดใช้ฟีเจอร์เหล่านี้มีค่าใช้จ่าย ต้องได้รับอนุมัติจาก
  ผู้ดูแลงบประมาณก่อนเปิดใช้งาน**

### 2.2 Manual Database Backup ด้วย `pg_dump` (ไม่มีค่าใช้จ่ายเพิ่ม)

ใช้ connection string จาก **Project Settings > Database > Connection string**
(เลือกแบบ URI, ใส่รหัสผ่านฐานข้อมูล — คนละตัวกับ API keys)

```bash
# สำรองทั้งฐานข้อมูล (schema + ข้อมูล) เป็นไฟล์เดียว
pg_dump "postgresql://postgres:<password>@<host>:5432/postgres" \
  --format=custom --file=backup-$(date +%Y%m%d).dump

# หรือสำรองเป็น SQL แบบอ่านได้ (ใหญ่กว่าแต่ตรวจสอบเนื้อหาด้วยตาได้ง่ายกว่า)
pg_dump "postgresql://postgres:<password>@<host>:5432/postgres" \
  --format=plain --file=backup-$(date +%Y%m%d).sql
```

**ควรรันคำสั่งนี้ผ่านเครื่องที่ปลอดภัย (ไม่ใช่เครื่องส่วนตัวที่แชร์กับคนอื่น)
และเก็บไฟล์ backup ไว้ในที่ที่เข้ารหัส/จำกัดสิทธิ์การเข้าถึง เนื่องจากไฟล์นี้
มีข้อมูลผู้ใช้ทั้งหมดรวมถึงอีเมล**

แนะนำให้ตั้งเป็น cron job/scheduled task รันอัตโนมัติตามความถี่ที่เหมาะสม
(เช่น รายวันหรือรายสัปดาห์ ขึ้นกับความถี่ในการเปลี่ยนแปลงข้อมูลจริง) แล้วอัปโหลด
ไฟล์ backup ไปเก็บที่ปลายทางอื่นที่ไม่ใช่เครื่องเดียวกับที่รันคำสั่ง (เช่น
พื้นที่เก็บไฟล์ขององค์กรที่มีอยู่แล้ว)

### 2.3 Storage Files Backup

Supabase Storage รองรับ S3-compatible API จึงใช้เครื่องมือ sync มาตรฐานได้
(เช่น `rclone`, `aws s3 sync` โดยตั้งค่า endpoint ให้ชี้มาที่ Supabase Storage)
คัดลอกไฟล์ทั้ง 4 buckets (`research-documents`, `research-covers`,
`submission-attachments`, `site-assets`) ไปยังปลายทางสำรองตามรอบเวลาเดียวกับ
ฐานข้อมูล เพื่อให้ backup ทั้งสองส่วนสอดคล้องกัน (ดูคำเตือนในข้อ 1) —
`site-assets` (โลโก้/favicon) มีขนาดเล็กและเปลี่ยนแปลงไม่บ่อย แต่ยังควรสำรอง
เช่นเดียวกับ bucket อื่น

รายละเอียดการเชื่อมต่อ S3-compatible endpoint ดูได้ที่
**Supabase Dashboard > Project Settings > Storage**

### 2.4 การสำรอง Environment Variables อย่างปลอดภัย

Environment Variables (`SUPABASE_SERVICE_ROLE_KEY`, `TURNSTILE_SECRET_KEY`,
`RESEND_API_KEY`, `SENTRY_DSN`/`LOGGING_BETTERSTACK_SOURCE_TOKEN` ฯลฯ) **ไม่ใช่
ข้อมูลที่กู้คืนได้จาก `pg_dump` หรือ Storage backup** — หากลืมสำรองแล้ว Vercel
project หาย จะต้องไปสร้างคีย์ใหม่ทั้งหมดจากทุกบริการ (Supabase, Cloudflare
Turnstile, Resend, ผู้ให้บริการ logging ฯลฯ) ซึ่งอาจทำให้ลิงก์/การเชื่อมต่อเดิม
ใช้ไม่ได้ชั่วคราว

**วิธีสำรองที่แนะนำ**:

1. **ห้าม commit ค่า secret ลงใน Git โดยเด็ดขาด** (`.env.local` อยู่ใน
   `.gitignore` อยู่แล้ว — ตรวจสอบว่ายังเป็นเช่นนั้นเสมอ)
2. ใช้ตัวจัดการรหัสผ่าน/secret ขององค์กรที่มีอยู่แล้ว (เช่น 1Password,
   Bitwarden, Vault) เก็บสำเนาค่าจริงของทุกตัวแปรใน `.env.example` ที่มีการตั้ง
   ค่าจริงไว้ — จำกัดสิทธิ์เข้าถึงเฉพาะผู้ดูแลระบบที่จำเป็นเท่านั้น
3. Vercel เองมีสำเนาค่าที่ตั้งไว้อยู่แล้วใน **Project Settings > Environment
   Variables** — ถือเป็นแหล่งอ้างอิงหลักสำหรับค่าที่ใช้งานจริงบน production
   (แต่ไม่ควรเป็นสำเนาเดียวที่มี เผื่อบัญชี Vercel มีปัญหา)
4. เมื่อหมุนเวียน (rotate) คีย์ใดๆ ตามนโยบายความปลอดภัย ให้อัปเดตสำเนาที่เก็บไว้
   ในข้อ 2 ทันที ไม่ให้ค่าที่เก็บไว้ล้าสมัย

## 3. ความถี่และระยะเวลาเก็บย้อนหลังที่แนะนำ

ระบบนี้เป็นห้องสมุดงานวิจัยที่ข้อมูลเปลี่ยนแปลงไม่บ่อยมาก (ส่งงานวิจัยใหม่/
อนุมัติเป็นครั้งคราว ไม่ใช่ transaction ต่อวินาที) จึงไม่จำเป็นต้องสำรองถี่มาก
— ข้อเสนอแนะเบื้องต้น (ปรับตามนโยบายองค์กรจริง):

- **ฐานข้อมูล**: สำรองอย่างน้อยสัปดาห์ละ 1 ครั้ง หรือถี่กว่านั้นหากมีการ
  อนุมัติ/เผยแพร่งานวิจัยบ่อย เก็บย้อนหลังอย่างน้อย 4 รอบล่าสุด
- **Storage**: สำรองพร้อมกับฐานข้อมูลทุกครั้ง (ตามข้อ 1)
- **ก่อนการเปลี่ยนแปลงใหญ่** (เช่น รัน migration ใหม่, อัปเกรดเวอร์ชัน
  Supabase CLI/Postgres): สำรองทันทีก่อนดำเนินการเสมอ ไม่ว่าจะถึงรอบตามกำหนด
  หรือไม่

## 4. การกู้คืนข้อมูล (Recovery)

### 4.1 กู้คืนฐานข้อมูลทั้งหมดจากไฟล์ `pg_dump`

```bash
# จากไฟล์ custom format
pg_restore --clean --if-exists \
  --dbname="postgresql://postgres:<password>@<host>:5432/postgres" \
  backup-YYYYMMDD.dump

# จากไฟล์ SQL แบบ plain
psql "postgresql://postgres:<password>@<host>:5432/postgres" -f backup-YYYYMMDD.sql
```

**คำเตือน**: `--clean` จะลบ object เดิมก่อน restore ทับ — ควรทำกับฐานข้อมูล
ใหม่/ว่างเปล่า หรือฐานข้อมูลที่ยืนยันแล้วว่าต้องการเขียนทับทั้งหมดเท่านั้น
ห้ามรันกับฐานข้อมูล production ที่ยังมีผู้ใช้งานอยู่โดยไม่ได้แจ้งล่วงหน้า

### 4.2 กู้คืนเฉพาะบางตาราง (Partial Recovery)

หากต้องการกู้คืนเฉพาะบางตาราง (เช่น `research_items` ถูกลบผิดพลาด) ให้ใช้
`pg_restore` พร้อม flag `--table=<ชื่อตาราง>` กับไฟล์ custom format แทนการ
restore ทั้งฐานข้อมูล — ควรทดสอบใน environment แยกก่อนเสมอเพื่อตรวจสอบว่า
Foreign Key ที่เกี่ยวข้อง (เช่น `research_authors`, `research_categories`)
ยังสอดคล้องกันหลัง restore

### 4.3 กรณี "ลบงานวิจัยผิดพลาด" — ใช้สถานะ `archived` แทนการกู้คืนจาก backup

ระบบออกแบบมาให้ librarian/admin ใช้สถานะ `archived` แทนการลบถาวรอยู่แล้ว
(ดู workflow ในหัวข้อ "สถาปัตยกรรมสิทธิ์การเข้าถึง" ใน [`README.md`](../README.md))
ดังนั้นกรณีส่วนใหญ่ที่ต้องการ "เอาออกจากหน้าเว็บ" ไม่จำเป็นต้องกู้คืนจาก backup
เลย — เปลี่ยนสถานะกลับจาก `/dashboard/research` ได้โดยตรง การกู้คืนจาก backup
จำเป็นเฉพาะกรณี **ลบแถวข้อมูลจริงออกจากฐานข้อมูล** (hard delete) เท่านั้น
เช่น เมื่อ admin ใช้ปุ่มลบในหน้าจัดการหมวดหมู่/หน่วยงาน/ผู้ใช้

### 4.4 กู้คืนไฟล์ใน Storage

อัปโหลดไฟล์กลับเข้า bucket เดิมด้วยพาธเดิม (`{uid}/{draftKey}/{filename}`)
ผ่านเครื่องมือ sync เดียวกับที่ใช้สำรอง (ข้อ 2.3) — ต้องกู้คืนพาธให้ตรงกับค่า
`pdf_file`/`cover_image`/`attachment_file` ที่บันทึกไว้ในฐานข้อมูลเป๊ะ มิเช่นนั้น
Signed URL ที่สร้างจาก `lib/storage/signed-url.server.ts` จะชี้ไปยังไฟล์ที่ไม่มีอยู่จริง

## 5. การทดสอบแผนกู้คืน

แผนสำรองข้อมูลที่ไม่เคยทดสอบกู้คืนจริง ถือว่ายังพิสูจน์ไม่ได้ว่าใช้งานได้จริง
แนะนำให้ทดสอบกู้คืน**อย่างน้อยทุก 6 เดือน** (หรือถี่กว่านั้นตามความเสี่ยงที่ยอมรับได้
— ผูกกับรอบตรวจสอบความปลอดภัยประจำปี/ทุกครึ่งปีขององค์กรถ้ามีอยู่แล้ว เพื่อไม่
ต้องตั้งระบบเตือนแยกต่างหาก) โดยกู้คืนไฟล์ backup ล่าสุดขึ้น Supabase project
ทดสอบแยกต่างหาก (ไม่ใช่ production) แล้วตรวจสอบตาม checklist ด้านล่าง —
**บันทึกผลการทดสอบแต่ละครั้งไว้เป็นลายลักษณ์อักษร** (วันที่ทดสอบ, ผู้ทดสอบ,
ผ่าน/ไม่ผ่านข้อไหนบ้าง) เพื่อให้ตรวจสอบย้อนหลังได้ว่าแผนกู้คืนยังใช้งานได้จริง
อยู่เสมอ ไม่ใช่แค่ทดสอบครั้งเดียวตอนสร้างระบบแล้วไม่เคยทวนซ้ำ

### Checklist การทดสอบกู้คืน

- [ ] กู้คืนฐานข้อมูลจากไฟล์ `pg_dump` ล่าสุดขึ้น Supabase project ทดสอบสำเร็จ
      โดยไม่มี error
- [ ] กู้คืนไฟล์ Storage ทั้ง 4 bucket ขึ้น project ทดสอบสำเร็จ
- [ ] จำนวนแถวในตารางหลัก (`research_items`, `profiles`, `user_roles`) ตรงกับ
      ที่คาดไว้ (เทียบกับตัวเลขก่อนสำรอง)
- [ ] Signed URL ของไฟล์ PDF ตัวอย่างเปิดได้จริงหลังกู้คืนทั้งฐานข้อมูลและ Storage
      (พิสูจน์ว่าพาธไฟล์ในฐานข้อมูลกับไฟล์จริงใน Storage ยังตรงกันหลังกู้คืน)
- [ ] ภาพปกงานวิจัยตัวอย่าง (public bucket `research-covers`) แสดงผลได้ปกติ
- [ ] RLS Policies ยังทำงานถูกต้อง (ทดสอบด้วยบัญชีทดสอบแต่ละบทบาทตามที่ทำใน
      การตรวจสอบก่อน deploy จริง — อย่างน้อย member/staff/librarian/admin/super_admin)
- [ ] ตรวจสอบว่า database trigger สำคัญยังทำงานอยู่หลังกู้คืน (เช่น กันถอดถอน
      Super Admin คนสุดท้าย, บันทึก `approval_logs` อัตโนมัติเมื่อเปลี่ยนสถานะงานวิจัย,
      ป้องกัน parent_id วนซ้ำของ `categories`/`organizations`)
- [ ] ทดสอบเรียกฟังก์ชัน merge อย่างน้อย 1 ตัว (`merge_authors`,
      `merge_organizations`, หรือ `merge_research_items` — ดู
      [`data-quality.md`](data-quality.md)) กับข้อมูลทดสอบเพื่อยืนยันว่า
      security definer function เหล่านี้ยังทำงานได้ปกติหลังกู้คืน (ตรวจสิทธิ์
      rank ภายในถูกต้อง ไม่ throw error ผิดปกติ)
