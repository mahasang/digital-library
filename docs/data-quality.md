## 1. หลักการออกแบบสำคัญ: Merge ไม่ใช่ Delete

ทั้งสามกลไก (`merge_authors`, `merge_organizations`, `merge_research_items`)
ใช้รูปแบบเดียวกัน:

1. ย้ายความสัมพันธ์ (research_authors, research_items.organization_id,
   favorites, ฯลฯ) จากรายการต้นทางไปยังรายการหลักอย่างปลอดภัย — ตรวจสอบ
   unique constraint ที่มีอยู่ก่อนเสมอ (ถ้าปลายทางมีความสัมพันธ์แบบเดียวกัน
   อยู่แล้ว จะลบของต้นทางทิ้งแทนการย้ายซ้ำ ไม่ใช่ error)
2. ตั้งค่ารายการต้นทางเป็น "ถูกรวมแล้ว" (`merged_into_author_id`/
   `merged_into_organization_id`/`merged_into_research_item_id` +
   `is_active = false` หรือ `status = 'merged'` แล้วแต่ตาราง) — **ไม่มีการ
   hard delete รายการต้นทางเลย** เพื่อรักษาความสัมพันธ์เชิงประวัติศาสตร์
   (ใครอ้างอิงถึงรายการนี้ในอดีตยังตรวจสอบย้อนหลังได้)
3. บันทึก `audit_logs` ในธุรกรรมเดียวกับการย้ายข้อมูล (atomic — ถ้าฐานข้อมูล
   ล้มเหลวระหว่างทาง จะไม่มีทั้งการย้ายข้อมูลและ audit log ค้างอยู่ครึ่งๆ กลางๆ)

ทั้งสามฟังก์ชันเป็น PostgreSQL function (`security definer`) ไม่ใช่ TypeScript
หลายคำสั่งต่อกัน — เพื่อรับประกันความเป็น atomic transaction จริง และเพราะ
การย้ายความสัมพันธ์ต้องจัดการ unique constraint ของหลายตารางพร้อมกันซึ่งทำได้
ปลอดภัยกว่ามากในฐานข้อมูลโดยตรง แต่ละฟังก์ชัน **ตรวจสอบสิทธิ์ rank ซ้ำในตัวเอง
เสมอ** (ไม่เชื่อว่า Server Action ตรวจแล้วเพียงชั้นเดียว) ตามรูปแบบ "RBAC สอง
ชั้น" เดิมของโปรเจกต์

| การรวมข้อมูล | สิทธิ์ขั้นต่ำ | เหตุผล |
|---|---|---|
| ผู้วิจัย (`merge_authors`) | Librarian (rank ≥ 30) | กระทบแค่ `research_authors` |
| หน่วยงาน (`merge_organizations`) | Librarian (rank ≥ 30) | กระทบ `authors.organization_id`/`research_items.organization_id`/โครงสร้างหลัก-ย่อย |
| งานวิจัย (`merge_research_items`) | Admin (rank ≥ 40) | กระทบความสัมพันธ์กว้างที่สุด (favorites, ประวัติการอ่าน, ดาวน์โหลด, คำขอเข้าถึงเอกสาร, สิทธิ์ที่อนุมัติแล้ว, ข้อความ PDF ที่ดึงไว้) |

## 2. ผู้วิจัยมาตรฐาน (`authors`)

ต่อยอดจากตาราง `authors` เดิม (Phase 3) **ไม่สร้างคอลัมน์ซ้ำ**:

- คอลัมน์ `name` เดิมยังคงทำหน้าที่ "ชื่อแสดงผลภาษาไทย" เหมือนเดิมทุกประการ
  (โค้ดทั้งระบบอ้างอิง `authors.name` อยู่แล้ว) — **ไม่เพิ่ม `display_name_th`
  แยกต่างหาก** เพราะจะซ้ำซ้อนกับ `name` โดยตรง มีแต่เพิ่ม `display_name_en`
  ใหม่สำหรับชื่ออังกฤษ
- คอลัมน์ใหม่: `display_name_en`, `normalized_name_th`/`normalized_name_en`
  (คำนวณอัตโนมัติผ่าน trigger ทุกครั้งที่ `name`/`display_name_en` เปลี่ยน),
  `title_prefix_th`/`title_prefix_en`, `orcid`, `orcid_verified_at`,
  `biography`, `is_active`, `merged_into_author_id`
- **`email` ไม่ได้เพิ่มเข้ามาโดยตั้งใจ** — ตาราง `authors` มี `profile_id`
  (FK ไปยัง `profiles` ซึ่งมี `email` อยู่แล้ว) สำหรับกรณีผู้วิจัยเป็นผู้ใช้ที่
  ลงทะเบียนในระบบ ส่วนผู้วิจัยภายนอกที่ไม่มีบัญชี ระบบยังไม่มีความต้องการเก็บ
  อีเมลแยกต่างหากในฟีเจอร์นี้ (เพิ่มได้ในอนาคตหากจำเป็นจริง)
- **การ normalize ชื่อเป็นแบบ heuristic เท่านั้น** (`normalize_person_name()`
  ตัดช่องว่างซ้ำ + คำนำหน้าที่พบบ่อย เช่น "ดร.", "ผศ.", "Dr.", "Prof." + แปลง
  เป็นตัวพิมพ์เล็ก) ใช้สำหรับคำนวณความคล้าย (`pg_trgm`) เพื่อแสดง **คำเตือน**
  เท่านั้น **ไม่เคยใช้ตัดสินว่าเป็นคนเดียวกันโดยอัตโนมัติ** — เจ้าหน้าที่ต้อง
  ตรวจสอบและกดยืนยันการรวมข้อมูลเองทุกครั้งที่ `/dashboard/authors/[id]`
- **บทบาทผู้วิจัยต่องานวิจัย** (`research_authors.author_role`):
  `principal_investigator` (ผู้วิจัยหลัก) / `co_investigator` (ผู้ร่วมวิจัย)
  — กำหนดอัตโนมัติจากลำดับผู้วิจัยในฟอร์มส่งงานวิจัย (**คนแรกในรายการ = ผู้วิจัย
  หลักเสมอ** ไม่มีการเพิ่มช่องเลือกบทบาทแยกต่างหากในฟอร์มสาธารณะ เพื่อไม่ต้อง
  แก้ไข UI ฟอร์มส่งงานวิจัยเดิม — เจ้าหน้าที่ปรับลำดับผู้วิจัยตอนแก้ไขงานวิจัย
  ได้ตามปกติ ซึ่งจะคำนวณบทบาทใหม่ตามลำดับที่ปรับ)

## 3. หน่วยงานมาตรฐาน (`organizations`)

- เพิ่มโครงสร้างหลัก/ย่อยด้วยคอลัมน์ **`parent_id`** (ไม่ใช้ชื่อ
  `parent_organization_id` ตามที่ระบุในโจทย์ตรงๆ — ตั้งใจใช้ชื่อเดียวกับ
  `categories.parent_id` ที่มีอยู่แล้วตั้งแต่ Phase 12 เพื่อความสอดคล้องของ
  ชื่อคอลัมน์ในระบบ) พร้อม trigger ป้องกัน cycle
  (`prevent_organization_cycle()`) โครงสร้างเดียวกับที่ใช้กับ `categories`
  ทุกประการ — ทดสอบแล้วว่ากันได้ทั้ง self-parent และ cycle 2 ระดับขึ้นไป
- คอลัมน์ใหม่อื่นๆ: `normalized_name_th`/`normalized_name_en` (auto-maintain
  ผ่าน trigger เหมือน authors), `organization_code`, `website_url`,
  `merged_into_organization_id`
- เมื่อรวมหน่วยงาน หน่วยงานย่อยของต้นทางจะถูกย้ายไปเป็นหน่วยงานย่อยของ
  หน่วยงานหลักแทนโดยอัตโนมัติ (`parent_id` ของหน่วยงานย่อยเหล่านั้นชี้ไปที่
  หน่วยงานหลักใหม่)

## 4. การตรวจสอบงานวิจัยซ้ำ

### เกณฑ์เปรียบเทียบและคะแนน (ปรับได้ตั้งแต่ช่วงที่ 22)

ฟังก์ชัน SQL `find_similar_research_items(p_research_item_id)` หา "แคนดิเดต"
ที่อาจซ้ำ (ผ่าน `pg_trgm` similarity บนชื่อเรื่องที่ normalize แล้ว + ตรวจ
ISBN/DOI/PDF hash ตรงกัน + ผู้วิจัยหลักคนเดียวกัน) **ไม่เปลี่ยนแปลงเลยตั้งแต่
ช่วงที่ 19** — ยังส่งสัญญาณดิบชุดเดิมกลับมาให้ฝั่งแอปพลิเคชัน
(`lib/data/duplicate-research.server.ts`) คำนวณคะแนนรวมและเหตุผลเป็นภาษาไทย

**สิ่งที่เปลี่ยน**: น้ำหนักที่ใช้คำนวณคะแนนไม่ใช่ค่าคงที่ตายตัวในโค้ดอีกต่อไป
— อ่านจากตาราง `duplicate_detection_rules` (แถวที่ `is_active = true`)
ทุกครั้งที่ตรวจสอบ ปรับได้ที่ `/superadmin/data-quality/settings`:

- ห้าน้ำหนัก (`weight_title`, `weight_author`, `weight_year`,
  `weight_identifier` — รวม ISBN+DOI เป็นหมวดเดียวกัน, `weight_file_hash`)
  แต่ละตัว 0–100 **รวมกันต้องเท่ากับ 100 พอดี** (บังคับด้วย CHECK constraint
  ของตาราง ไม่ใช่แค่ validation ฝั่งแอป)
- `คะแนน = (ความคล้ายชื่อเรื่อง × weight_title + ปีเดียวกัน × weight_year +
  ผู้วิจัยหลักคนเดียวกัน × weight_author + ISBN/DOI ตรงกัน × weight_identifier +
  PDF hash ตรงกัน × weight_file_hash) ÷ 100` — **เปลี่ยนจากเดิมที่ ISBN/DOI/PDF
  hash ตรงกันให้คะแนนเต็ม 100% ทันที** มาเป็นน้ำหนักของตัวเองเหมือนปัจจัยอื่น
  (ยังคงมีน้ำหนักสูงสุดในกลุ่มโดยค่าเริ่มต้น แต่ปรับลดได้หากต้องการ)
- บันทึกเฉพาะคู่ที่คะแนน ≥ `threshold_low ÷ 100` ของเกณฑ์ที่ active ลงตาราง
  `duplicate_research_reviews` (แทน `MIN_SCORE_TO_RECORD = 0.35` ค่าคงที่เดิม
  — ค่าเริ่มต้นยังคงเป็น 35 เท่าเดิมทุกประการ) พร้อมบันทึก `rule_version_id`
  อ้างอิงกลับไปยังเกณฑ์ที่ใช้จริงตอนนั้นเสมอ (ตรวจสอบย้อนหลังได้ว่าผลลัพธ์คู่
  ใดเกิดจากเกณฑ์เวอร์ชันใด — แถวเก่าก่อนช่วงที่ 22 มีค่านี้เป็น `null`)
- `threshold_medium`/`threshold_high` ใช้แบ่งระดับความเชื่อมั่นตอนแสดงผลที่
  `/dashboard/duplicate-reviews` เท่านั้น ไม่กระทบว่าจะบันทึกคู่นั้นหรือไม่
- เก็บคู่แบบ canonical เสมอ (`research_item_id < candidate_research_item_id`
  ตามลำดับ uuid) กันแถวซ้ำซ้อนสำหรับคู่เดียวกันเมื่อตรวจสอบจากทั้งสองด้าน

### เวอร์ชันของเกณฑ์ (`duplicate_detection_rules`)

แต่ละการแก้ไขที่ `/superadmin/data-quality/settings` **สร้างแถวใหม่เสมอ
ไม่เคย update ทับของเดิม** — ผ่านฟังก์ชัน SQL
`create_duplicate_detection_rule_version()` (`security definer`, ตรวจ rank ≥
50 ในตัวเอง) ที่ปิดใช้งานเวอร์ชันเดิม (`is_active = false`) แล้วสร้างเวอร์ชัน
ใหม่ในธุรกรรมเดียว (atomic — partial unique index บน `is_active` อนุญาตแค่
แถวเดียวที่ active พร้อมกันเสมอ) มีปุ่ม "คืนค่าเริ่มต้น" ที่สร้างเวอร์ชันใหม่
ด้วยค่าเดิมตอน seed (title 50/author 20/year 10/identifier 15/file_hash 5,
threshold 35/60/85) ทุกการเปลี่ยนแปลงบันทึก `audit_logs`
(`action: "duplicate_detection_rules_update"`) พร้อมค่าที่ตั้งใหม่ทั้งหมด

**(ใหม่ในช่วงที่ 26) บันทึกแล้วสแกนใหม่ทั้งระบบได้ทันที** — ฟอร์มที่หน้า
settings มีปุ่ม submit สองปุ่ม (`name="intent"` คนละ `value` ในฟอร์มเดียวกัน
ไม่ต้องมี state/JS เพิ่มเติม เป็น HTML มาตรฐาน):

- **"บันทึกอย่างเดียว"** — พฤติกรรมเดิมทุกประการ สร้างเวอร์ชันใหม่ ไม่แตะ
  ข้อมูลเก่า
- **"บันทึกและสแกนใหม่ทั้งระบบ"** — สร้างเวอร์ชันใหม่แล้ว enqueue
  `bulk_enqueue` coordinator (โครงสร้างเดิมจากช่วงที่ 25 — ดู
  [docs/background-jobs.md](./background-jobs.md) หัวข้อ 11.4) ด้วย filter
  ว่างเปล่า (`{}` = ทุกรายการที่ไม่ถูกรวมไปแล้ว ไม่จำกัด 500 รายการ) ผูก
  `filter_snapshot` ของ `job_batches` กับ `{ruleVersionId, ruleVersion}` ของ
  เวอร์ชันที่เพิ่งสร้าง — มี `window.confirm()` ยืนยันก่อนเสมอ (ไม่ใช่ modal
  เต็มรูปแบบแบบ MFA reset/มอบสิทธิ์ Super Admin เพราะการสแกนซ้ำเป็นแค่การ
  ตรวจสอบเพิ่มเติม ไม่ลบ/แก้ไข/รวมข้อมูลใดๆ) บันทึก `audit_logs` แยกต่างหาก
  (`action: "duplicate_scan_rescan_after_rule_change"`) เพื่อให้ตรวจสอบย้อนหลัง
  ได้ว่าทำไม batch นี้ถึงถูกสร้าง โดยไม่ต้องเปิดดู `filter_snapshot`
- ทั้งสองปุ่มแสดงข้อความเตือนถาวรกำกับไว้เสมอ: "การเปลี่ยนเกณฑ์นี้จะไม่ตรวจสอบ
  ข้อมูลเก่าซ้ำโดยอัตโนมัติ"
- **ผลตรวจเดิมจากเวอร์ชันก่อนหน้าไม่ถูกลบเลย** — `detectDuplicatesForResearchItem()`
  ยัง `upsert()` เหมือนเดิมทุกประการ (ไม่มีการเปลี่ยน logic การตรวจ) คู่ที่ยัง
  ผ่านเกณฑ์ใหม่จะได้ `rule_version_id`/คะแนนอัปเดตเป็นของเวอร์ชันใหม่ คู่ที่ไม่
  ถูกแตะ (เพราะไม่ได้อยู่ในรายการที่สแกนซ้ำ หรือคะแนนใหม่ต่ำกว่า threshold)
  ยังคง `rule_version_id`/คะแนนของเวอร์ชันเดิมไว้เป็นประวัติ
- **"ผลเก่าล้าสมัย" คำนวณตอน query เสมอ ไม่ใช่คอลัมน์ที่เก็บไว้ล่วงหน้า** —
  `getDuplicateReviews()`/`getDuplicateReviewDetail()`
  (`lib/data/duplicate-research.server.ts`) join กับ
  `duplicate_detection_rules.is_active` สดทุกครั้ง ได้ `staleRuleVersion:
  boolean` (true เมื่อเกณฑ์ที่ใช้ตรวจคู่นี้ไม่ใช่เวอร์ชัน active ปัจจุบันแล้ว)
  แสดงเป็น Badge สีเหลือง "เกณฑ์เก่ากว่าปัจจุบัน" ที่
  `/dashboard/duplicate-reviews` คู่กับ Badge เทา "เกณฑ์ v{N}" บอกเวอร์ชันที่
  ใช้จริง — **เลือกวิธีนี้แทนคอลัมน์ `is_stale` ที่เก็บไว้ล่วงหน้าโดยตั้งใจ**
  เพราะคอลัมน์เก็บไว้ล่วงหน้าต้องมี job กวาดอัปเดตทุกครั้งที่เปลี่ยนเกณฑ์ (จุด
  ล้มเหลว/race condition เพิ่มขึ้น) ในขณะที่คำนวณตอน query ถูกต้องเสมอโดยไม่
  ต้องดูแลรักษาโค้ดเพิ่มเติมเลย

### รายงาน "การสแกนซ้ำล่าสุด" ที่หน้า settings

### 4.1 ตรวจสอบย้อนหลังทั้งระบบ — `/superadmin/data-quality`

Super Admin เลือกงานวิจัยหลายรายการพร้อมกัน (กรองด้วยปี/หมวดหมู่/สถานะเผยแพร่/
เฉพาะที่แก้ไขล่าสุด 30 วัน) แล้วกด "ตรวจสอบที่เลือก" — enqueue background job
`duplicate_scan` หนึ่งงานต่อหนึ่งงานวิจัย (รูปแบบเดียวกับ `pdf_text_extraction`/
`file_security_rescan` ของช่วงที่ 20 ทุกประการ — ดู
[docs/background-jobs.md](./background-jobs.md)) แต่ละ job เรียก
`detectDuplicatesForResearchItem()` ตัวเดียวกับที่ใช้ตอนส่ง/แก้ไขงานวิจัยเดี่ยว
ทุกประการ ผ่าน Service Role **ไม่มีการรวมข้อมูล (merge) อัตโนมัติเกิดขึ้นเลย**
— ผลลัพธ์เป็นแค่คู่ที่บันทึกลง `duplicate_research_reviews` เหมือนเดิม

- job ที่มี entity เดียวกัน active อยู่แล้วถูกข้ามเงียบๆ (idempotency key
  `duplicate_scan:{research_item_id}`) — กดปุ่มซ้ำไม่สร้าง job ซ้ำซ้อน
- แสดง "ชุดงานล่าสุด" (progress ต่อ batch: จำนวนที่ตรวจแล้ว/กำลังตรวจ/ล้มเหลว)
  และ "งานที่ล้มเหลวถาวร" พร้อมปุ่มลองใหม่รายตัว (คอมโพเนนต์ร่วมกับหน้า
  pdf-processing/file-security ของช่วงที่ 20)
- ทุกการสั่งตรวจสอบเป็นชุดบันทึก `audit_logs`
  (`action: "duplicate_scan_bulk"`, metadata: จำนวนที่ขอ/สร้างจริง/ข้าม)
- `find_similar_research_items()` เดิมตรวจสิทธิ์ผ่าน `user_max_role_rank()`
  ซึ่งอ่านจาก `auth.uid()` ของผู้เรียก — ไม่มีความหมายเมื่อเรียกผ่าน Service
  Role (ไม่มี `auth.uid()` ของผู้ใช้คนใดคนหนึ่ง) จึงเพิ่มเงื่อนไขให้ข้ามการ
  ตรวจ rank เมื่อผู้เรียกคือ `service_role` โดยตรง (`auth.role() =
  'service_role'`) **เฉพาะ job handler ฝั่งเซิร์ฟเวอร์ที่เชื่อถือได้เท่านั้น**
  (ป้องกันด้วย `SUPABASE_SERVICE_ROLE_KEY` อยู่แล้ว) ไม่กระทบการตรวจสอบสิทธิ์
  ของผู้ใช้ทั่วไปเลยแม้แต่จุดเดียว — logic การหาแคนดิเดตภายในฟังก์ชันไม่มีการ
  แก้ไขเลย

### พฤติกรรม — ไม่เคยบล็อกการบันทึก

`detectDuplicatesForResearchItem()` ทำงานหลังบันทึกงานวิจัยสำเร็จเสมอ
(ไม่ใช่ก่อนบันทึก) และไม่ throw error ออกไปหา caller — **การส่ง/แก้ไขงานวิจัย
ไม่มีวันล้มเหลวเพราะตรวจพบว่าอาจซ้ำ** ผลลัพธ์เป็นแค่คำเตือนที่ปรากฏใน
`/dashboard/duplicate-reviews` ให้เจ้าหน้าที่ตรวจสอบภายหลังเท่านั้น

### สถานะการตรวจสอบ

`pending` (ยังไม่ตรวจ) → `confirmed_duplicate` (ยืนยันว่าซ้ำ, ยังไม่รวม) /
`not_duplicate` (ไม่ซ้ำ, ปิดเคส) / `merged` (รวมข้อมูลแล้วผ่านปุ่มในหน้าเดียวกัน)
— การยืนยัน/ปฏิเสธใช้สิทธิ์ Librarian ขึ้นไป (rank ≥ 30) ส่วนการรวมจริง
(`merge_research_items`) ใช้สิทธิ์ Admin ขึ้นไป (rank ≥ 40) เท่านั้น

## 5. รายการที่ถูกรวม (merged) ยังเข้าถึง URL เดิมได้

เมื่องานวิจัยถูกรวม (`status = 'merged'`) หน้า `/research/[slug]` และ
`/research/[slug]/read` เดิมจะ **redirect อัตโนมัติ** ไปยัง slug ของรายการหลัก
แทนการแสดง 404 — ใช้ฟังก์ชัน `getMergedRedirectSlug()` เรียกเฉพาะตอนหา
งานวิจัยที่ status ปกติ (published) ไม่เจอเท่านั้น (ไม่กระทบ query หลักที่ใช้
ทั่วทั้งระบบ) RLS ของ `research_items` เปิดให้แถวที่ `status = 'merged'`
มองเห็นได้ทุกคนเพิ่มขึ้นมาหนึ่งเงื่อนไข (เดิมมองเห็นเฉพาะ `published` +
เงื่อนไข access_level, หรือเป็นเจ้าของ/staff) — **เห็นได้แค่ข้อมูล metadata
พอสำหรับ redirect เท่านั้น ไม่ได้เปิดสิทธิ์อ่าน/ดาวน์โหลดไฟล์เพิ่มขึ้นเลย**
(สิทธิ์ไฟล์ยังคุมที่ `access_level` + grant ของรายการหลักตามปกติทุกประการ)

## 6. ข้อจำกัดของระบบตรวจข้อมูลซ้ำ (ตรงไปตรงมา — ไม่ปกปิด)

- **(แก้ไขแล้วในช่วงที่ 22)** เดิมไม่มีปุ่ม "ตรวจสอบย้อนหลังทั้งระบบ" —
  ตอนนี้มีที่ `/superadmin/data-quality` (bulk scan เป็นชุด) ดูหัวข้อ 4.1
- **(แก้ไขแล้วในช่วงที่ 22)** เดิมเกณฑ์คะแนน/น้ำหนักเป็นค่าคงที่ตายตัว —
  ตอนนี้ Super Admin ปรับได้เองที่ `/superadmin/data-quality/settings` แบบ
  versioned ดูหัวข้อ 4
- **การเปรียบเทียบชื่อเรื่องเป็นแบบ substring/trigram เท่านั้น** (เหมือนระบบ
  ค้นหาเนื้อหา PDF จาก Phase 17) ไม่มีการตัดคำหรือ semantic matching — ชื่อ
  เรื่องที่ความหมายเดียวกันแต่คำต่างกันมาก (เช่น แปลจากอังกฤษเป็นไทยคนละสำนวน)
  อาจตรวจไม่พบ
- **ไม่มีการเปรียบเทียบเนื้อหาบทคัดย่อ** — เกณฑ์ใช้แค่ชื่อเรื่อง/ผู้วิจัยหลัก/
  ปี/ISBN/DOI/PDF hash เท่านั้น ตามที่ระบุในขอบเขตงาน
- **ผู้วิจัยหลักต้องตรงกัน "ทุกตัวอักษร" ในระดับ author_id เดียวกัน** ไม่ใช่
  แค่ชื่อคล้ายกัน — ถ้าผู้วิจัยคนเดียวกันถูกบันทึกเป็นสองแถวใน `authors` ที่
  ยังไม่ได้รวมกัน ระบบจะไม่นับว่า "ผู้วิจัยหลักคนเดียวกัน" จนกว่าจะรวมผู้วิจัย
  ก่อน (จุดนี้ทำให้การรวมผู้วิจัยและตรวจงานวิจัยซ้ำส่งเสริมกันและกัน — ยิ่ง
  ข้อมูลผู้วิจัยสะอาดเท่าไหร่ การตรวจงานวิจัยซ้ำก็แม่นยำขึ้นเท่านั้น)
- **การเลือกรายการด้วยตนเอง ("ตรวจสอบที่เลือก") ยังจำกัดสูงสุด 500 รายการต่อ
  การเรียกหน้าเว็บหนึ่งครั้ง** — ห้องสมุดที่มีงานวิจัยมากกว่านี้ต้องกรองด้วย
  ตัวกรอง (ปี/หมวดหมู่/สถานะ) ให้แคบลงก่อนเลือกทั้งหมด **หรือใช้ปุ่ม
  "ประมวลผลทั้งหมดตามตัวกรอง" แทน (ไม่จำกัด 500 รายการ, รองรับทุกตัวกรองรวม
  หมวดหมู่แล้วตั้งแต่ช่วงที่ 28 — ดู `docs/background-jobs.md` หัวข้อ 11.6)**
- **(แก้ไขแล้วในช่วงที่ 26)** เดิมเปลี่ยนน้ำหนัก/เกณฑ์แล้วไม่ตรวจสอบซ้ำ
  งานวิจัยเดิมที่เคยตรวจไปแล้วโดยอัตโนมัติ ต้องสั่ง "ตรวจสอบย้อนหลังทั้งระบบ"
  แยกต่างหากเองที่หน้าอื่น — ตอนนี้หน้า `/superadmin/data-quality/settings`
  มีปุ่ม "บันทึกและสแกนใหม่ทั้งระบบ" ในตัวเลย (ดูหัวข้อ 4) **ยังคงหลักการเดิม
  ทุกประการ**: คู่ที่เคยบันทึกไว้ก่อนเปลี่ยนเกณฑ์ไม่ถูกลบ ยังคงคะแนนและ
  `rule_version_id` เดิมไว้เป็นประวัติเสมอ ไม่มีการคำนวณใหม่ย้อนหลังแบบ
  overwrite และไม่มีการรวม/แก้ไขงานวิจัยอัตโนมัติใดๆ เพิ่มเติม
