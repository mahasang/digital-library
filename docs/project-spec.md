# ข้อกำหนดโครงการ: ห้องสมุดดิจิทัลเพื่อเผยแพร่งานวิจัยขององค์กร

## 1. ภาพรวมระบบ

ระบบเผยแพร่งานวิจัยขององค์กรในรูปแบบ PDF/eBook ผ่านเว็บไซต์ เพื่อให้บุคลากรและบุคคลทั่วไป
สามารถค้นหา อ่าน และดาวน์โหลดงานวิจัยได้ตามสิทธิ์การเข้าถึงที่กำหนด พร้อมรองรับกระบวนการ
ส่งงานวิจัยเข้าระบบ ตรวจสอบ และอนุมัติเผยแพร่โดยเจ้าหน้าที่ห้องสมุด

## 2. กลุ่มผู้ใช้งาน (User Roles)

| บทบาท | คำอธิบาย |
| --- | --- |
| **Guest** | ผู้เยี่ยมชมทั่วไป ยังไม่ได้เข้าสู่ระบบ ดูข้อมูลเมทาดาต้าและงานวิจัยสาธารณะได้ |
| **Member** | สมาชิกที่ลงทะเบียนแล้ว อ่าน/ดาวน์โหลดงานวิจัยระดับสมาชิกได้ บันทึกรายการโปรดได้ |
| **Staff** | บุคลากรขององค์กร เข้าถึงงานวิจัยระดับ staff_only และส่งงานวิจัยเข้าระบบได้ |
| **Librarian** | บรรณารักษ์ ตรวจสอบ/อนุมัติ/ขอแก้ไข/ปฏิเสธงานวิจัยที่ส่งเข้ามา จัดการเผยแพร่ |
| **Admin** | ผู้ดูแลระบบ จัดการผู้ใช้ สิทธิ์ หมวดหมู่ และดูรายงานภาพรวมทั้งหมด |
| **Super Admin** | ผู้ดูแลระบบสูงสุด มีสิทธิ์ทุกอย่างของ Admin บวกกับสิทธิ์จัดการลำดับชั้นบทบาท (ตาราง `roles`) และมอบ/ถอดถอนบทบาท Super Admin เอง เข้าถึงหน้า `/superadmin` ได้เฉพาะบทบาทนี้เท่านั้น ต้องมี Super Admin เหลืออย่างน้อย 1 คนในระบบเสมอ |

## 3. ฟังก์ชันหลักของระบบ

1. **ค้นหา (Search)** — ค้นหางานวิจัยจากชื่อเรื่อง ผู้วิจัย คำสำคัญ หมวดหมู่
2. **ดูรายละเอียด (View Detail)** — แสดงบทคัดย่อ ผู้วิจัย หน่วยงาน ปี คำสำคัญ สิทธิ์การเข้าถึง
3. **อ่านออนไลน์ (Read Online)** — เปิดอ่านเอกสารผ่าน PDF Viewer ภายในเว็บไซต์
4. **ดาวน์โหลดตามสิทธิ์ (Download by Permission)** — ดาวน์โหลดไฟล์ตามระดับสิทธิ์ของผู้ใช้
5. **รายการโปรด (Favorites)** — บันทึกงานวิจัยที่สนใจไว้ดูภายหลัง (สำหรับ Member ขึ้นไป)
6. **ส่งงานวิจัย (Submit Research)** — บุคลากรส่งงานวิจัยเข้าสู่ระบบเพื่อรอตรวจสอบ
7. **อนุมัติ (Approval Workflow)** — บรรณารักษ์ตรวจสอบและเปลี่ยนสถานะเอกสาร
8. **รายงาน (Reports)** — สถิติการเข้าชม ดาวน์โหลด และภาพรวมคลังงานวิจัยสำหรับผู้ดูแลระบบ

> หมายเหตุ: ในช่วงพัฒนาแรก (Phase 1) จะพัฒนาเฉพาะฝั่งการแสดงผลสาธารณะ (ค้นหา ดูรายละเอียด
> อ่าน/ดาวน์โหลดจำลอง) ด้วยข้อมูลตัวอย่าง (Mock Data) เท่านั้น ยังไม่เชื่อมต่อฐานข้อมูลจริง
> ระบบล็อกอินจริง แดชบอร์ด หรือระบบอัปโหลดไฟล์

## 4. โครงสร้างข้อมูลงานวิจัย (Research Item)

| ฟิลด์ | คำอธิบาย |
| --- | --- |

| `titleEn` | ชื่อเรื่องภาษาอังกฤษ |
| `researchers` | รายชื่อผู้วิจัย (หนึ่งคนขึ้นไป) |
| `organization` | หน่วยงาน/ภาควิชาเจ้าของผลงาน |
| `year` | ปีที่เผยแพร่ (พ.ศ.) |
| `category` | หมวดหมู่งานวิจัย |
| `keywords` | คำสำคัญ (Tags) |
| `abstract` | บทคัดย่อ |
| `coverImage` | ภาพหน้าปก |
| `pdfFile` | ไฟล์เอกสาร PDF/eBook |
| `accessLevel` | ระดับสิทธิ์การเข้าถึง |
| `status` | สถานะการเผยแพร่ |
| `views` / `downloads` | สถิติยอดเข้าชม/ดาวน์โหลด (ใช้จัดอันดับความนิยม) |

## 5. ระดับสิทธิ์การเข้าถึง (Access Level)

| ระดับ | คำอธิบาย |
| --- | --- |
| `public` | เข้าถึงได้ทุกคน (Guest ขึ้นไป) ทั้งอ่านและดาวน์โหลด |
| `member_only` | ต้องเป็นสมาชิก (Member ขึ้นไป) จึงจะอ่าน/ดาวน์โหลดได้ |
| `staff_only` | เฉพาะบุคลากรขององค์กร (Staff ขึ้นไป) |
| `read_only` | อ่านออนไลน์ได้เท่านั้น ไม่อนุญาตให้ดาวน์โหลด |
| `metadata_only` | แสดงเฉพาะข้อมูลเมทาดาต้า (ชื่อเรื่อง บทคัดย่อ ผู้วิจัย) ไม่สามารถอ่านฉบับเต็ม |

## 6. สถานะเอกสาร (Document Status)

| สถานะ | คำอธิบาย |
| --- | --- |
| `draft` | ฉบับร่าง ยังไม่ส่งตรวจสอบ |
| `pending_review` | ส่งเข้าระบบแล้ว รอบรรณารักษ์ตรวจสอบ |
| `revision_requested` | บรรณารักษ์ขอให้แก้ไขก่อนอนุมัติ |
| `approved` | ผ่านการตรวจสอบแล้ว รอเผยแพร่ |
| `published` | เผยแพร่บนเว็บไซต์แล้ว |
| `rejected` | ถูกปฏิเสธการเผยแพร่ |
| `archived` | จัดเก็บถาวร ไม่แสดงในหน้าเว็บสาธารณะ |

## 7. ขอบเขตช่วงพัฒนาที่ 1 (Phase 1 Scope)

### สิ่งที่พัฒนา
- โครงสร้างโปรเจกต์ Next.js (App Router) + TypeScript + Tailwind CSS
- ข้อมูลตัวอย่างงานวิจัยอย่างน้อย 8 รายการ (Local Mock Data)
- หน้า: `/`, `/research`, `/research/[id]`, `/research/[id]/read`, `/about`, `/contact`, `/login`, `/register`
- Header, Footer, Card, Search & Filter, และ UI Component ที่ใช้ซ้ำได้
- PDF Viewer แบบ Placeholder (ยังไม่เชื่อมไฟล์จริง)

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 2+)
- การเชื่อมต่อฐานข้อมูล Supabase
- ระบบล็อกอิน/สมัครสมาชิกจริง (Authentication/Authorization)
- Dashboard สำหรับ Staff/Librarian/Admin
- ระบบอัปโหลดไฟล์และกระบวนการอนุมัติจริง
- ระบบรายงานสถิติเชิงลึก

## 8. ขอบเขตช่วงพัฒนาที่ 2 (Phase 2 Scope)

### สิ่งที่พัฒนา
- เชื่อมต่อ Supabase (PostgreSQL + Auth + Row Level Security) — ฐานข้อมูลจริง
  15 ตารางตามหัวข้อ 4-6 ข้างต้น พร้อม RLS Policy ตามระดับสิทธิ์ผู้ใช้
- ระบบสมัครสมาชิก, เข้าสู่ระบบ, ออกจากระบบ, ลืมรหัสผ่าน, ตั้งรหัสผ่านใหม่,
  แก้ไขโปรไฟล์ ผ่าน Supabase Auth จริง (ไม่เก็บรหัสผ่านเอง)
- Middleware ตรวจสอบสิทธิ์ฝั่งเซิร์ฟเวอร์ก่อนเข้าถึงหน้าที่ต้องล็อกอิน
- เชื่อมหน้ารายการ/รายละเอียดงานวิจัยเข้ากับ Supabase จริง พร้อม Mock Data
  เป็น fallback อัตโนมัติเมื่อยังไม่ได้ตั้งค่า `.env.local`

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **บทบาทผู้ใช้แทนด้วย rank ตัวเลข** (`member`=10, `staff`=20, `librarian`=30,
  `admin`=40) เก็บในตาราง `roles`/`user_roles` แทนการ hardcode enum
  เพื่อให้ RLS Policy เปรียบเทียบสิทธิ์แบบ "ขั้นต่ำ" ได้ง่าย (`rank >= N`)
- **`categories` และ `organizations` เป็นข้อมูลอ้างอิงคงที่** (seed ผ่าน
  migration ไม่ใช่ mock data) แต่หน้าเว็บสาธารณะยังคงอ่านหมวดหมู่จาก
  `data/categories.ts` (static) เพื่อลดจำนวนจุดที่ต้อง fetch แบบ async
  โดยไม่จำเป็น — ตาราง `categories` ในฐานข้อมูลใช้สำหรับความสัมพันธ์เชิง
  โครงสร้าง (research_categories) และ RLS/reporting เป็นหลัก

## 9. ขอบเขตช่วงพัฒนาที่ 3 (Phase 3 Scope)

### สิ่งที่พัฒนา
- **Supabase Storage** 3 buckets: `research-documents` (private, PDF),
  `research-covers` (public, ภาพปก), `submission-attachments` (private,
  เอกสารประกอบ) พร้อม Storage RLS Policies
- ระบบส่งงานวิจัย (`/submit-research`), ดูงานวิจัยของฉัน (`/my-submissions`)
  และแก้ไขได้เฉพาะตอนยังไม่ผ่านการตรวจสอบ (Staff ขึ้นไป)
- ระบบอนุมัติงานวิจัย (`/dashboard/approvals`) สำหรับ Librarian/Admin:
  อนุมัติ, ไม่อนุมัติ (พร้อมเหตุผล), ขอแก้ไข (พร้อมรายละเอียด), เผยแพร่,
  จัดเก็บถาวร
- ตาราง `approval_logs` (ใหม่) บันทึกประวัติการเปลี่ยนสถานะทุกครั้งโดย
  อัตโนมัติผ่าน database trigger ร่วมกับ `audit_logs`
- PDF Viewer จริง (แทน Placeholder) แสดงผลผ่าน Signed URL ที่หมดอายุอัตโนมัติ
- Server Action ตรวจสอบสิทธิ์ตาม `access_level` ก่อนออก Signed URL สำหรับ
  อ่าน/ดาวน์โหลดไฟล์ทุกครั้ง พร้อมบันทึก `download_logs`
- รายการโปรด (`/favorites`) และประวัติการอ่าน (`/reading-history`) สำหรับ
  Member ขึ้นไป

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไฟล์ PDF ทั้งหมดอยู่ใน private bucket เสมอ ไม่มี public URL** การเข้าถึง
  ของผู้อ่านทั่วไปทำผ่าน Signed URL ที่สร้างฝั่งเซิร์ฟเวอร์ด้วย Service Role
  หลังตรวจสอบ `access_level`/`status` แล้วเท่านั้น (ลิงก์อ่านอายุ 30 นาที
  ลิงก์ดาวน์โหลดอายุ 1 นาที) — เลือกวิธีนี้แทนการเปิด Storage RLS ให้ทุกคน
  อ่านไฟล์ public-tier ได้ตรงๆ เพราะทำให้ควบคุมจุดตรวจสอบสิทธิ์ได้ที่เดียว
  (โค้ดแอป ไม่ใช่ policy expression ที่ซับซ้อนขึ้นเรื่อยๆ) และเปิดทางให้
  บันทึก `download_logs` ได้ในจังหวะเดียวกับการอนุมัติเข้าถึง
- **รูปแบบพาธไฟล์ `{uid}/{draftKey}/{filename}`**: ใช้ uid ของผู้อัปโหลด
  เป็น root ของ Storage RLS (ตรวจสอบความเป็นเจ้าของไฟล์ได้ง่ายด้วย
  `storage.foldername(name)[1]`) โดยไม่ผูกกับ research_items.id เนื่องจาก
  ต้องอัปโหลดไฟล์ก่อนที่แถว research_items จะถูกสร้าง (client สร้าง
  draftKey แบบสุ่มเองก่อนอัปโหลด)
- **ประวัติการอนุมัติบันทึกผ่าน trigger ไม่ใช่โค้ดแอป**: `approval_logs`
  ไม่มีสิทธิ์ INSERT ให้ role ใดๆ เลยนอกจาก database trigger (ทำงานในฐานะ
  เจ้าของตารางซึ่งข้าม RLS) เพื่อรับประกันว่าไม่มีการเปลี่ยนสถานะครั้งใด
  หลุดการบันทึก ไม่ว่าจะเปลี่ยนผ่านหน้าเว็บหรือ SQL โดยตรง
- **การลบงานวิจัยใช้สถานะ `archived` แทน hard delete**: ไม่มีปุ่มลบถาวร
  สำหรับเอกสารที่ผ่านการส่งเข้าระบบแล้วในหน้าเว็บ (RLS ยังอนุญาตให้ admin
  ลบถาวรได้ในระดับฐานข้อมูลสำหรับกรณีจำเป็นจริงๆ เท่านั้น)
- **`authors.organization_name`** (ข้อความอิสระ) เพิ่มเข้ามาคู่กับ
  `organization_id` (FK) เดิม เนื่องจากฟอร์มส่งงานวิจัยให้กรอกหน่วยงานของ
  ผู้วิจัยร่วมเป็นข้อความอิสระ (ไม่บังคับเลือกจากรายการ) เพื่อความรวดเร็ว
  ในการกรอกฟอร์มเมื่อมีผู้วิจัยหลายคน

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 4+)
- Dashboard สำหรับ Admin จัดการผู้ใช้/บทบาท/หมวดหมู่/หน่วยงานผ่าน UI
- ระบบรายงานสถิติเชิงลึก (กราฟแนวโน้ม, รายงานตามหมวดหมู่/หน่วยงาน)
- การแจ้งเตือนอัตโนมัติเมื่อสถานะงานวิจัยเปลี่ยนแปลง
- การลบไฟล์เก่าใน Storage อัตโนมัติเมื่อมีการแทนที่ไฟล์ตอนแก้ไขงานวิจัย
- Rate limiting / CAPTCHA สำหรับฟอร์มสาธารณะ

## 10. ขอบเขตช่วงพัฒนาที่ 4 (Phase 4 Scope)

### สิ่งที่พัฒนา
- **Dashboard** (`/dashboard`) สำหรับ Librarian/Admin: สถิติภาพรวม (สมาชิก,
  งานวิจัยทั้งหมด, รอตรวจสอบ, ยอดเข้าชม, ยอดดาวน์โหลด, งานวิจัยยอดนิยม) และ
  สถิติแบบเลือกช่วงวันที่ได้
- **จัดการงานวิจัย** (`/dashboard/research`, `/new`, `/[id]/edit`): ค้นหา
  กรอง แก้ไข เปลี่ยนสิทธิ์ ปิดเผยแพร่ และเก็บถาวร — เฉพาะ Librarian/Admin
- **จัดการผู้ใช้** (`/dashboard/users`): ดูรายชื่อผู้ใช้ กำหนดบทบาท
  Member/Staff/Librarian/Admin เปิด/ปิดสถานะบัญชีโดยไม่ลบข้อมูล — Admin เท่านั้น
- **จัดการหมวดหมู่และหน่วยงาน** (`/dashboard/categories`,
  `/dashboard/organizations`): เพิ่ม แก้ไข ปิดใช้งาน ลบอย่างปลอดภัย
  รองรับหมวดหมู่หลัก/ย่อย
- **รายงาน** (`/dashboard/reports`): การเข้าชม การดาวน์โหลด งานวิจัยยอดนิยม
  สมาชิก ส่งออก CSV กรองตามวันที่/หมวดหมู่/ประเภทผู้ใช้
- **Audit Log** (`/dashboard/audit-logs`): ผู้กระทำ รายการที่เปลี่ยนแปลง
  วันเวลา รายละเอียด — Admin เท่านั้น
- **Settings** (`/dashboard/settings`): ชื่อองค์กร โลโก้ ข้อมูลติดต่อ
  ข้อความลิขสิทธิ์ การแสดงผลพื้นฐานของหน้าแรก — Admin เท่านั้น

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **RBAC สองชั้นเสมอ**: middleware.ts ป้องกันตาม rank ระดับ route (เลือก
  prefix ที่เจาะจงที่สุดเมื่อซ้อนกัน เช่น `/dashboard/users` ต้อง rank ≥ 40
  แม้ `/dashboard` ทั่วไปจะพอแค่ rank ≥ 30) และทุก Server Component/Server
  Action ยังตรวจสอบ rank ซ้ำด้วยตนเองผ่าน `requireMinRank()`/
  `getCurrentUserRoleRank()` — ไม่พึ่งพา middleware เพียงจุดเดียว
- **เปิด/ปิดบัญชีใช้ Supabase Auth Admin API จริง** (`ban_duration`) ไม่ใช่
  แค่ปรับ flag `profiles.is_active` เพื่อบล็อกการเข้าสู่ระบบได้จริงโดยไม่ลบ
  ข้อมูลใดๆ ของผู้ใช้ (governance ต้องใช้ Service Role — ถ้ายังไม่ตั้งค่า
  จะแสดงข้อความแจ้งเตือนแทนการ error)
- **หมวดหมู่/หน่วยงานย้ายจาก Mock Data ไปเป็นข้อมูลจริงจาก Supabase**
  (พร้อม fallback เดิมเมื่อยังไม่เชื่อมต่อ) เนื่องจากการจัดการผ่าน Dashboard
  ต้องมีผลจริงกับเว็บสาธารณะ — ยกเว้นป้ายหมวดหมู่ขนาดเล็กบนการ์ดผลงาน
  (ResearchCard) ที่ยังอ้างอิง Mock Data แบบ static เพื่อจำกัดขอบเขตการแก้ไข
- **ลบหมวดหมู่/หน่วยงานอย่างปลอดภัย**: ตรวจสอบที่ Server Action ก่อนลบจริง
  ว่ามีงานวิจัยหรือหมวดหมู่ย่อยผูกอยู่หรือไม่ ถ้ามีจะบล็อกและแนะนำให้ปิดใช้งาน
  (`is_active = false`) แทน — ไม่ได้ใช้ FK constraint กันการลบตรงๆ
- **audit_logs มีสองเส้นทางการบันทึก**: การเปลี่ยนสถานะงานวิจัยบันทึกอัตโนมัติ
  ผ่าน database trigger (ตั้งแต่ Phase 3) ส่วนการกระทำอื่น (จัดการหมวดหมู่/
  หน่วยงาน/ผู้ใช้/ตั้งค่า) บันทึกผ่านฟังก์ชัน `logAudit()` ที่เรียกจาก
  Server Action โดยตรง เนื่องจากไม่มี "การเปลี่ยนสถานะ" ให้ trigger ดักจับ

- **แก้บั๊กที่บล็อกการ deploy จริง**: `generateStaticParams` ของหน้า

  พัฒนาเพราะใช้ Mock Data fallback อยู่ตลอด) — ลบออกเนื่องจากทั้งสองหน้าเป็น

- **ปิดช่องโหว่ secret รั่วไหลใน source control**: กัน `supabase/.temp/` และ
  `supabase/.branches/` (มี project ref, pooler URL, local secrets ของ
  Supabase CLI) ไม่ให้เข้า Git
- **ลดข้อมูลภายในที่รั่วผ่าน error message**: ฟีเจอร์ที่ผู้ใช้ทั่วไปเข้าถึงได้

- ตรวจสอบ RLS Policies และสิทธิ์ตามบทบาททั้ง 5 บทบาทแบบทำงานจริงบน

  ตรงตามหัวข้อ 5-6 ทุกกรณี)
- จัดทำเอกสารสำหรับใช้งานจริง: ขั้นตอน deploy บน Vercel, checklist ก่อน/
  หลัง deploy, แนวทางสำรอง/กู้คืนข้อมูล, คู่มือผู้ใช้แยกตามบทบาท

ตรวจสอบความพร้อม ไม่ใช่รอบพัฒนาฟีเจอร์) เพิ่มเติมด้วย:

  เป็นข้อเสนอสำหรับ Phase ถัดไป

  "สมาชิก") และเพื่อความชัดเจนว่าการจัดการ Super Admin ไม่ได้อยู่ในหน้านี้

  ต่างหาก เพราะ `storage.objects` อยู่นอก schema `public` ที่ PostgREST
  client เข้าถึงตรงๆ ไม่ได้ ให้เฉพาะผลรวมขนาดไฟล์ต่อ bucket ไม่มีชื่อไฟล์/

## 13. ขอบเขตช่วงพัฒนาที่ 7 (Phase 7 Scope)

### สิ่งที่พัฒนา
- **`/superadmin/users` + `/superadmin/users/[id]`**: ค้นหา/กรองผู้ใช้ตามชื่อ
  อีเมล สถานะ บทบาท, กำหนดได้หลายบทบาทต่อผู้ใช้หนึ่งคน (เพิ่ม/ถอดถอนทีละ
  บทบาทอิสระต่อกัน ต่างจาก `/dashboard/users` ที่แทนที่ทั้งชุด), ดูประวัติ
  การทำงานจาก `audit_logs`, เปิด/ระงับบัญชีถาวรหรือชั่วคราว (ระบุจำนวนวัน)
- **`/superadmin/roles`**: Role Matrix แบบอ่านอย่างเดียว 5 บทบาท
- **`/superadmin/system-settings`**: ขยายตาราง `settings` เดิม — อัปโหลด
  โลโก้/favicon ไฟล์จริง (bucket `site-assets` ใหม่), Social Media, เปิด/ปิด
  การสมัครสมาชิก-การส่งงานวิจัย, สถานะเริ่มต้นงานวิจัยใหม่, ขนาดไฟล์สูงสุด
  ต่อ bucket (sync กับ `storage.buckets.file_size_limit` จริง)
- **`/superadmin/security`**: CAPTCHA (Cloudflare Turnstile — โครงสร้าง/

  Rate Limit แบบอิงฐานข้อมูล (ตาราง `rate_limit_events` + ฟังก์ชัน
  `check_rate_limit()`), นโยบายยืนยันอีเมล (อ่านจาก GoTrue endpoint
  `/auth/v1/settings` โดยตรง แบบอ่านอย่างเดียว), รายชื่อบัญชีที่ถูกระงับ
- **`/superadmin/storage`**: พื้นที่ใช้งานต่อ bucket, สแกนไฟล์ที่ไม่มีการ
  อ้างอิงในฐานข้อมูล (ฟังก์ชัน `superadmin_orphaned_storage_objects()`),
  ลบได้หลังยืนยันเท่านั้นพร้อมตรวจสอบซ้ำก่อนลบจริงและบันทึก audit log
- **`/superadmin/notifications`**: ตาราง `notifications` ใหม่ + ขยาย
  `log_research_status_change()` (trigger เดิมตั้งแต่ Phase 3) ให้สร้างการ
  แจ้งเตือนในระบบให้ผู้ส่งงานวิจัยทุกครั้งที่สถานะเปลี่ยน แสดงผลผ่าน
  NotificationBell ใน Header, อีเมลแจ้งเตือนผ่าน Resend (best-effort เรียก
  จาก Server Action ในหน้าอนุมัติงานวิจัยหลังบันทึกสถานะสำเร็จ)

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **คีย์ลับของบริการภายนอก (Turnstile/Resend) เก็บเป็น environment variable
  เท่านั้น ไม่เก็บในตาราง `settings`** — ตาราง `settings` มี RLS
  `for select using (true)` (ทุกคนอ่านได้ รวม guest) เพื่อให้หน้าเว็บ
  สาธารณะแสดงชื่อองค์กร/โลโก้ได้ หากเก็บ secret key ไว้ในแถวเดียวกันจะรั่ว
  ไหลไปกับทุก query ที่ select settings — สอดคล้องกับรูปแบบเดิมที่ใช้กับ
  `SUPABASE_SERVICE_ROLE_KEY` อยู่แล้ว
- **CAPTCHA ยังไม่บังคับตรวจสอบจริงในฟอร์ม แม้จะมีสวิตช์เปิด/ปิดแล้ว** —
  ตั้งใจไม่ผูก enforcement กับสวิตช์ในรอบนี้ เพราะฟอร์มยังไม่ได้ฝัง Turnstile
  widget จริง การผูก enforcement ไว้ก่อนจะทำให้ super_admin เปิดสวิตช์แล้ว
  ปิดกั้นผู้ใช้ทุกคนโดยไม่ได้ตั้งใจ (ไม่มี token ให้ verify เลย) เลือกความ
  ปลอดภัยของระบบสมัครสมาชิกเป็นหลักมากกว่าความสมบูรณ์ของฟีเจอร์นี้ในรอบเดียว
- **Rate limiting เลือกอิงฐานข้อมูล (ตาราง + ฟังก์ชัน) แทนบริการภายนอกอย่าง
  Redis** — เข้ากับสเกลของระบบห้องสมุดนี้ (ฟอร์มสมัครสมาชิก/ส่งงานวิจัย ไม่ใช่
  endpoint ที่มี traffic สูง) และไม่เพิ่มบริการภายนอกที่อาจมีค่าใช้จ่าย
  ออกแบบให้ fail-open เมื่อตรวจสอบไม่ได้ เพื่อไม่ให้ rate limiter เองกลาย
  เป็นจุดที่ทำให้ฟีเจอร์หลักใช้งานไม่ได้
- **`superadmin_orphaned_storage_objects()`/`superadmin_storage_usage()`/
  `superadmin_update_bucket_limit()` เป็น SQL function แบบ security definer**
  เพราะ `storage.objects`/`storage.buckets` อยู่นอก schema `public` ที่
  PostgREST client เข้าถึงตรงๆ ไม่ได้ — การลบไฟล์จริงใช้ Storage RLS ปกติ
  ผ่าน client ธรรมดา (ไม่ใช้ service role) เพราะ super_admin (rank 50) ผ่าน
  เกณฑ์ rank ≥ 40 ที่ policy ลบไฟล์ทุก bucket กำหนดไว้อยู่แล้ว
- **ฟิลด์ใหม่ทั้งหมดในตาราง `settings` (ยกเว้นฟิลด์เดิมจาก Phase 4) แก้ไขได้
  เฉพาะ super_admin** — บังคับด้วย trigger ที่เปรียบเทียบ NEW/OLD เฉพาะ
  คอลัมน์ที่เพิ่มใหม่ ไม่กระทบสิทธิ์เดิมของ admin ในการแก้ไขฟิลด์เดิม
  (site_name, logo_url, contact_*, copyright_text, homepage_*_count) ผ่าน
  `/dashboard/settings` แต่อย่างใด

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 8)
- ฝัง Cloudflare Turnstile widget จริงในฟอร์มสมัครสมาชิก/ส่งงานวิจัย และผูก
  การบังคับตรวจสอบ token เข้ากับ Server Action
- ตัวเลขคำแนะนำขนาดไฟล์ฝั่ง client (`lib/storage/limits.ts`) ยังเป็นค่าคงที่
  ไม่ได้ดึงจากการตั้งค่าแบบไดนามิก
- หน้า UI สำหรับมอบ/ถอดถอนบทบาท Super Admin ให้ผู้ใช้อื่น (ปัจจุบันทำผ่าน SQL
  โดยตรงเท่านั้นสำหรับบัญชีแรก)
- แดชบอร์ดกราฟ/แนวโน้มเชิงภาพ, การจัดการหมวดหมู่/หน่วยงานแบบลากวาง, หน้า
  dashboard ภายในยังแสดงข้อความ error ดิบจาก Postgres (รายการเดิมจาก Phase 6)

- **`docs/production-checklist.md`**: รายการตรวจสอบเชิงฟังก์ชัน/ความปลอดภัย

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไม่มีการเปลี่ยนแปลง schema ฐานข้อมูลในรอบนี้เลย** — ทุกหน้าใหม่และกราฟ

  `profiles`, `reading_history`, `download_logs`, `research_categories`,
  `superadmin_storage_usage()`) จึงไม่ต้องรัน migration ใหม่สำหรับ Phase นี้
- **กราฟข้อมูลรวมกลุ่มฝั่งแอปพลิเคชัน (JavaScript) แทน SQL** (`date_trunc`
  ฯลฯ) — สอดคล้องกับรูปแบบเดิมที่ใช้ทั่วทั้งโปรเจกต์ (เช่น popularResearch ใน
  `admin-stats.server.ts`) เหมาะกับสเกลข้อมูลของระบบห้องสมุดนี้ที่ไม่ใหญ่มาก
- **System Health ตรวจสอบแบบสดเท่านั้น ไม่มีการเก็บประวัติ** — หลีกเลี่ยงความ
  ซับซ้อนของการสร้างระบบเก็บ time-series สถานะเอง ซึ่งซ้ำซ้อนกับสิ่งที่บริการ
  Uptime Monitoring ภายนอกทำได้ดีกว่าอยู่แล้ว
- **หน้า Backups ไม่มีปุ่มสั่งสำรองข้อมูล** — Supabase ไม่เปิด API สาธารณะให้
  แอปภายนอกสั่งสำรอง/อ่านสถานะได้ การสร้างปุ่มที่ไม่ทำงานจริงจะขัดกับ
  ข้อกำหนดห้ามแสดงข้อมูลปลอม/ทำให้เข้าใจผิด

## 15. ขอบเขตช่วงพัฒนาที่ 9 (Phase 9 Scope)

รอบตรวจสอบความปลอดภัยและความถูกต้องของการตั้งค่า (ไม่ใช่รอบพัฒนาฟีเจอร์ใหม่)
— ปิดรายการค้างจาก Phase 8 backlog เรื่อง CAPTCHA/ขนาดไฟล์ไดนามิก/error ดิบ

### สิ่งที่พัฒนา
- **Cloudflare Turnstile ฝังจริง**: `components/auth/TurnstileWidget.tsx`
  (client component โหลดสคริปต์ Cloudflare, ส่ง token ผ่าน hidden input
  `turnstileToken`) ใช้ที่ฟอร์มสมัครสมาชิก (`RegisterForm`) และฟอร์มส่งงาน
  วิจัยใหม่ (`SubmitResearchForm` เฉพาะหน้า `/submit-research`) ตรวจสอบ
  token กับ Cloudflare REST API จริงฝั่งเซิร์ฟเวอร์เสมอผ่าน
  `verifyCaptchaIfEnabled()` (`lib/captcha.server.ts`) ก่อน `signUp()`/
  insert `research_items` ทุกครั้ง — ไม่เชื่อผลจาก client
- **ขนาดไฟล์แบบไดนามิกฝั่ง client**: ทั้ง 4 หน้าที่ใช้ `SubmitResearchForm`
  (`/submit-research`, `/my-submissions/[id]`, `/dashboard/research/new`,
  `/dashboard/research/[id]/edit`) ดึง `maxPdfSizeMb`/`maxCoverSizeMb`/
  `maxAttachmentSizeMb` จาก `getSettings()` แล้วส่งเป็น prop `fileLimits`
  ให้ฟอร์มแสดงคำแนะนำ/ตรวจสอบไฟล์ตรงกับค่าจริงที่ปรับใน
  `/superadmin/system-settings` เสมอ
- **utility แปลง error ให้ปลอดภัย**: `toSafeErrorMessage()`
  (`lib/errors/safe-message.server.ts`) ใช้แทนการต่อ string
  `` `...: ${error.message}` `` เดิมในทุก Server Action ของหน้า
  `/dashboard/categories`, `/dashboard/organizations`, `/dashboard/settings`,
  `/dashboard/research/new`, `/dashboard/research/[id]/edit`,
  `/submit-research`, `/my-submissions/[id]`

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไม่มีการเปลี่ยนแปลง schema ฐานข้อมูลในรอบนี้เลย** — คอลัมน์
  `captcha_enabled`/`max_pdf_size_mb`/`max_cover_size_mb`/
  `max_attachment_size_mb` มีอยู่แล้วตั้งแต่ Phase 7 (`superadmin_phase2.sql`)
  รอบนี้เป็นการ "ต่อสาย" ฝั่งแอปพลิเคชันให้ค่าที่มีอยู่แล้วมีผลจริงเท่านั้น
- **CAPTCHA บังคับเฉพาะฟอร์มส่งงานวิจัย "ใหม่" ที่ `/submit-research`** — แม้
  `SubmitResearchForm` ใช้ร่วมกัน 4 หน้า แต่ตั้งใจไม่เปิด widget/บังคับ
  ตรวจสอบที่หน้าแก้ไขของเจ้าของงาน (`/my-submissions/[id]`) หรือหน้า
  เพิ่ม/แก้ไขของ Librarian/Admin (`/dashboard/research/*`) เพราะเป็นการ
  แก้ไขข้อมูลเดิมหรือจำกัดสิทธิ์ผู้ใช้ภายในไว้แล้ว ความเสี่ยงต่ำกว่าจุดที่
  เปิดให้สร้างข้อมูลใหม่จากฟอร์มสาธารณะ
- **CAPTCHA fail-open เมื่อเปิดสวิตช์แต่ตั้งค่าคีย์ไม่ครบ** — เหมือนรูปแบบ
  `checkRateLimit()` เดิม (fail-open เมื่อตรวจสอบไม่ได้) เพื่อไม่ให้
  super_admin เปิดสวิตช์โดยยังตั้งค่า environment variables ไม่ครบแล้วปิดกั้น
  ผู้ใช้ทุกคนโดยไม่ได้ตั้งใจ — log คำเตือนไว้ฝั่งเซิร์ฟเวอร์แทน
- **`toSafeErrorMessage()` แยกแยะด้วย Postgres error code (`P0001`) ไม่ใช่
  substring matching** — `P0001` คือ error code มาตรฐานของ
  `raise exception ... using errcode = 'P0001'` ที่แอปเขียนขึ้นเองในฝั่ง
  ฐานข้อมูล (เช่น กันถอดถอน Super Admin คนสุดท้ายจาก Phase 6) จึงเป็นข้อความ
  ภาษาไทยที่ปลอดภัยอยู่แล้ว ส่วน error code อื่นทั้งหมด (constraint
  violation, connection error ฯลฯ) ถูกแทนที่ด้วยข้อความทั่วไปเสมอ และ log
  รายละเอียดจริงไว้ฝั่งเซิร์ฟเวอร์เท่านั้น — แม่นยำกว่าการเดาจากข้อความที่ใช้
  ใน `friendlyRoleChangeError()` เดิม (ปรับให้ใช้ utility เดียวกันด้วย)

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 10)
รายการเดิมจาก Phase 8 backlog ที่ยังไม่ได้ทำ (ลบข้อ CAPTCHA/ขนาดไฟล์ไดนามิก/
error ดิบออกแล้วเนื่องจากทำเสร็จในรอบนี้):
- การจัดการหมวดหมู่/หน่วยงานแบบลากวาง (drag-and-drop)
- หน้า UI สำหรับมอบ/ถอดถอนบทบาท Super Admin ให้ผู้ใช้อื่น
- ระบบ log รวมศูนย์ (centralized logging) ที่เชื่อมต่อจริง
- Uptime Monitoring ระยะยาวแบบอัตโนมัติ

### สิ่งที่พัฒนา
- **`/superadmin/users/[id]` มอบ/ถอดถอนสิทธิ์ Super Admin ผ่าน UI**: แถวบทบาท

- **`grantSuperAdminAction`/`revokeSuperAdminAction`** (ใหม่ใน

  `getAuditLogs()`)
- **`docs/superadmin-guide.md`/`README.md`**: อัปเดตขั้นตอนสร้าง Super Admin
  คนแรก (SQL, จำเป็นเฉพาะบัญชีแรก) ต่อด้วยการจัดการคนถัดไปผ่าน UI

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไม่มีการเปลี่ยนแปลง schema/RLS/trigger ใดๆ ในรอบนี้เลย** — มาตรการความ
  ปลอดภัยหลัก (RLS บนตาราง `user_roles` จำกัดการเขียนแถวที่ชี้ไปบทบาท
  `super_admin` ให้ rank ≥ 50 เท่านั้น + trigger กันถอดถอน Super Admin คน
  สุดท้าย) มีอยู่แล้วตั้งแต่ Phase 6 (`20260802100100_super_admin_role.sql`)
  ตรวจสอบซ้ำด้วยการจำลอง RLS จริงผ่าน PostgreSQL (rank 40 ถูกปฏิเสธ, rank 50
  มอบ/ถอดถอนได้ปกติ, ถอดถอนคนสุดท้ายถูกปฏิเสธด้วย error code `P0001` เดิม)
  รอบนี้เป็นการเพิ่มชั้น UX ยืนยันตัวตนและ audit log ละเอียดขึ้นที่แอปพลิเคชัน
  เท่านั้น
- **กล่องยืนยัน (พิมพ์ CONFIRM/อีเมล) เป็นด่านป้องกันการคลิกพลาด ไม่ใช่ด่าน
  อนุญาตสิทธิ์** — สิทธิ์จริงมาจาก `requireMinRank(50)` + RLS เท่านั้น
  ตรวจสอบข้อความยืนยันซ้ำที่ฝั่งเซิร์ฟเวอร์ด้วย (ไม่เชื่อ client อย่างเดียว)
  แต่ไม่ใช่กลไกจำกัดสิทธิ์ (คล้ายรูปแบบ "type repo name to delete" ทั่วไป)
- **แยก `addUserRoleAction`/`removeUserRoleAction` เดิมออกจาก super_admin
  โดยสิ้นเชิง** (`GENERIC_ASSIGNABLE_ROLES` ปฏิเสธ `role=super_admin`) —
  ปิดทางลัดที่อาจข้ามกล่องยืนยันได้แม้เรียก action เดิมตรงๆ
- **`getAuditLogs()` เพิ่ม filter `entityId` แทนการสร้างฟังก์ชันใหม่** — ใช้
  ซ้ำโค้ดแบ่งหน้า/resolve ชื่อผู้กระทำ/ไม่ throw raw error ที่ทดสอบแล้วจาก
  Phase 8

## 17. ขอบเขตช่วงพัฒนาที่ 11 (Phase 11 Scope)

รอบตรวจสอบความพร้อมใช้งานจริงด้านการเฝ้าระวังและความปลอดภัย (ไม่ใช่รอบพัฒนา
ฟีเจอร์ใหม่) — ปิดรายการค้าง "ระบบ log รวมศูนย์" และ "Uptime Monitoring" จาก
Phase 10 backlog พร้อมเพิ่ม MFA และความปลอดภัยของไฟล์อัปโหลด

### สิ่งที่พัฒนา
- **Centralized Logging** (`lib/logging/`): abstraction เชื่อมต่อ Sentry
  (Envelope API) หรือ Better Stack/Logtail (HTTP ingestion) เลือกผ่าน
  `LOG_PROVIDER` ไม่ติดตั้ง SDK เพิ่ม ส่ง error ที่ผ่านการตัดข้อมูลอ่อนไหว
  (`redactSecrets()`) ออกอัตโนมัติเฉพาะตอน production ผ่าน Next.js
  `instrumentation.ts` (`onRequestError` hook) ไม่มีคีย์ก็ยัง log ผ่าน
  console ได้ปกติ — `/superadmin/system-logs` แสดงสถานะเชื่อมต่อจริง
- **Uptime Monitoring**: endpoint สาธารณะใหม่ `/api/health` ตรวจ
  application/database/storage แบบปลอดภัย ไม่เปิดเผย secret คืน HTTP 503
  เมื่อฐานข้อมูลเชื่อมต่อไม่ได้ พร้อมเอกสารตั้งค่า UptimeRobot/Better
  Uptime/Cloudflare Health Checks ใน `docs/uptime-monitoring.md` (ใหม่)
- **MFA สำหรับ Super Admin**: ใช้ TOTP MFA ในตัวของ Supabase Auth เต็ม
  รูปแบบ — `/account` มี UI enroll/list/unenroll factor
  (`components/account/MfaSettings.tsx`) เปิดให้ผู้ใช้ทุกบทบาทตั้งค่าได้
  `middleware.ts` บังคับ step-up (aal1→aal2) จริงก่อนเข้า `/superadmin/*`
  ทุกเซสชันใหม่สำหรับผู้ที่ตั้งค่าไว้แล้ว (เด้งไปหน้า `/mfa-challenge` ใหม่)
  ผู้ที่ยังไม่ได้ตั้งค่าเห็นแบนเนอร์เตือนทุกหน้า `/superadmin/*` และที่
  `/account` แทนการถูกบล็อก
- **ความปลอดภัยของไฟล์**: ตรวจนามสกุลไฟล์ตรงกับ MIME type ที่ตรวจพบทั้งฝั่ง
  client (`lib/storage/limits.ts`) และ server (Zod `.refine()` ใน

  `docs/file-security.md` (ใหม่) สรุปชั้นการตรวจสอบทั้งหมดอย่างตรงไปตรงมา
  รวมถึงข้อจำกัด (ไม่มี magic-byte/malware scanning ในโค้ดปัจจุบัน) พร้อม
  คำแนะนำเชื่อมต่อบริการสแกนมัลแวร์ก่อนเปิดใช้งานจริง

  (ทุก 6 เดือน)

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไม่ติดตั้ง `@sentry/nextjs` SDK** — ส่งผ่าน Sentry Envelope API ตรงๆ ด้วย
  `fetch` แทน เพื่อลดความเสี่ยงจากการเปลี่ยนแปลงโครงสร้างโปรเจกต์ใหญ่
- **MFA step-up บังคับเฉพาะผู้ที่ตั้งค่าไว้แล้ว ไม่บังคับก่อนใช้งานครั้งแรก** —
  ป้องกันปัญหา "ล็อกตัวเองออกจากระบบ" (Super Admin คนแรกที่สร้างผ่าน SQL จะ
  เข้า `/superadmin` ไม่ได้เลยถ้าบังคับ MFA ทันทีโดยยังไม่มีใครตั้งค่าไว้ก่อน)
  — ใช้กลไก AAL (Authenticator Assurance Level) ของ Supabase Auth เอง
  ไม่ได้สร้างระบบ session ขนานเพิ่ม
- **`/api/health` แยก matcher ออกจาก middleware หลัก** — เพื่อไม่ให้ทุกการ
  เรียกจาก uptime monitor (ทุก 1-5 นาที) ต้องผ่าน Supabase Auth session
  refresh ซึ่งไม่จำเป็นสำหรับ endpoint สาธารณะที่ไม่ต้องใช้ session
- **ไม่ implement การตรวจเนื้อไฟล์จริง (magic-byte) หรือสแกนมัลแวร์ในรอบนี้** —
  สถาปัตยกรรมอัปโหลดไฟล์ตรงจาก Browser ไปยัง Storage (ตั้งใจออกแบบไว้ตั้งแต่
  Phase 3 เพื่อประสิทธิภาพ) ทำให้เซิร์ฟเวอร์ของแอปไม่เคยเห็นเนื้อไฟล์จริงเลย —
  เลือกเขียนเอกสารคำแนะนำที่ตรงไปตรงมาแทนการอ้างว่าปลอดภัยแล้วทั้งที่ยังไม่ได้ทำ

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 12)
- การจัดการหมวดหมู่/หน่วยงานแบบลากวาง (drag-and-drop)
- ไม่มีการตรวจสอบเนื้อไฟล์จริง (magic-byte) หรือสแกนมัลแวร์สำหรับไฟล์อัปโหลด

  `getCategories()`/`getOrganizations()` เปลี่ยนจากเรียงตาม `name_th` เป็น

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **จัดลำดับเป็นฟีเจอร์แยกจาก CRUD เดิมโดยสิ้นเชิง** — `/dashboard/categories`/

  เท่านั้น
- **ใช้ RPC function (security definer) แทนการอัปเดตหลายแถวจาก client
  โดยตรง** — เพื่อให้การจัดลำดับ/ย้ายทั้งกลุ่มเป็น transaction เดียวจริง
  ป้องกันสถานะครึ่งๆ กลางๆ หากบันทึกล้มเหลวกลางทาง
- **จำกัดสิทธิ์ `sort_order` ด้วย column-specific trigger

- **`prevent_category_cycle()` เป็น database trigger ระดับตาราง** ไม่ใช่แค่

- **ทดสอบ RLS/RPC จริงผ่าน PostgREST HTTP endpoint โดยตรง** — เรียก

## 19. ขอบเขตช่วงพัฒนาที่ 13 (Phase 13 Scope)

หน้าอ่านออนไลน์แบบ flipbook (เปิดสมุดเสมือนจริง) แทนที่ตัวอ่าน PDF แบบ
`<iframe>` เดิมจาก Phase 3

### สิ่งที่พัฒนา
- **`FlipbookViewer`** (`components/research/`): render แต่ละหน้า PDF เป็นภาพ
  จริงด้วย react-pdf (ครอบ pdfjs-dist) แล้วส่งให้ react-pageflip จัดการ

  ปัจจุบัน คงปุ่ม "เปิดในแท็บใหม่"/ดาวน์โหลดเดิมไว้ครบ
- **Windowed rendering** (`RENDER_WINDOW = 2`): render เนื้อหาจริงเฉพาะหน้าที่
  อยู่ในช่วง ±2 จากหน้าปัจจุบัน หน้านอกช่วงแสดงกรอบเปล่าไปก่อน กันหน้าเว็บหน่วง
  ตอนเปิดเอกสารยาวๆ
- **`FlipbookViewerLoader`**: โหลด `FlipbookViewer` ผ่าน
  `next/dynamic(..., { ssr: false })` เพราะ pdfjs-dist/react-pageflip อ้างอิง
  API ของเบราว์เซอร์โดยตรง
- **`scripts/copy-pdf-worker.js`** + `postinstall` script: คัดลอก
  `pdf.worker.min.mjs` จาก `pdfjs-dist` ไปไว้ที่ `public/` อัตโนมัติทุกครั้งหลัง
  `npm install` เสิร์ฟเป็น static asset ของเว็บเราเอง ไม่พึ่ง CDN ภายนอก

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ใช้ `react-pdf@9.2.1` (พึ่ง `pdfjs-dist@4.8.69`) แทนเวอร์ชันล่าสุด
  (`react-pdf@10.x`/`pdfjs-dist@5.x`)** — ทดสอบจริงด้วย headless browser พบว่า
  `pdfjs-dist@5.4.296` มีปัญหา ESM/webpack interop จริงกับ Next.js 15.5.x
  (`TypeError: Object.defineProperty called on non-object` ตอนโหลดโมดูลใน
  เบราว์เซอร์ ไม่ว่า import ผ่านทางไหน) ลดเวอร์ชันแก้ปัญหาได้สมบูรณ์โดยไม่ต้อง
  แก้ webpack config เพิ่ม
- **`size="fixed"` + `autoSize={false}`** ไม่ใช่ `size="stretch"` + `autoSize`
  — ค่าเริ่มต้นทั้งสองขัดแย้งกันเอง (`stretch` ให้หนังสือปรับขนาดตาม parent,
  `autoSize` ให้ parent ปรับขนาดตามหนังสือ) ทำให้ขนาดจริงไม่ตรงกับ `pageWidth`
  ที่ส่งให้ react-pdf จนเนื้อหาถูกตัดขอบ แก้โดยให้โค้ดควบคุมขนาดเองทั้งหมด
- **ทดสอบด้วยไฟล์ PDF จริงที่อัปโหลดผ่าน Supabase Storage จริง** ทั้งใน
  `next dev` และ production build ยืนยันด้วยภาพหน้าจอจริงจาก headless browser

## 20. ขอบเขตช่วงพัฒนาที่ 14 (Phase 14 Scope)

ปิดรายการค้างข้อแรกจาก Phase 13 backlog — magic-byte validation และสแกน
มัลแวร์สำหรับไฟล์อัปโหลด (ดูรายละเอียดเต็มที่ `docs/file-security.md`)

### สิ่งที่พัฒนา
- **`lib/security/file-signature.server.ts`**: ตรวจ magic bytes ของเนื้อไฟล์
  จริงเทียบกับ MIME ที่ประกาศและรายการที่อนุญาตของแต่ละฟิลด์ (PDF/ภาพปก/
  เอกสารแนบ) — รองรับ PDF, PNG, JPEG, WebP, ICO, DOC, DOCX (ZIP-based), SVG
  (ตรวจโครงสร้างข้อความแทน เนื่องจากไม่มี binary signature)
- **`lib/security/malware-scanner.server.ts`**: abstraction เชื่อมต่อ ClamAV
  (เขียน client เชื่อม clamd ด้วยโปรโตคอล INSTREAM ผ่าน Node `net` โดยตรง) หรือ
  บริการสแกนภายนอกผ่าน HTTP ตามสัญญาที่กำหนด เลือกผ่าน Environment Variables
  ทั้งหมด ไม่ hard-code secret ใดๆ — มีโหมดจำลอง (mock) เฉพาะนอก production
  พร้อมคำเตือนชัดเจน
- **`lib/security/validate-upload.server.ts`**: ดาวน์โหลดไฟล์ที่เพิ่งอัปโหลด
  กลับมาด้วย Service Role ตรวจสอบ+สแกน **ก่อน insert/update แถว
  `research_items` เสมอ** ที่ทั้ง 4 จุดที่รับไฟล์ — ไฟล์ไม่ผ่านจะถูกลบออกจาก
  Storage ทันที ไม่มีแถวถูกสร้าง/แก้ไข และไม่ดาวน์โหลด/สแกนซ้ำไฟล์ที่ path
  ไม่เปลี่ยน (แก้ไขแล้วไม่ได้แทนที่ไฟล์)
- **คอลัมน์ใหม่ใน `research_items`**: `scan_status`/`scanned_at`/
  `scan_provider`/`scan_reason` — แถวเดิมก่อน migration นี้ backfill เป็น
  `skipped`/`legacy-pre-scan` อัตโนมัติ ไม่กระทบข้อมูล/สถานะเผยแพร่เดิม
- **Trigger `prevent_publish_unscanned_file()`** (ใหม่): กันเผยแพร่เอกสารที่
  `scan_status` เป็น `infected`/`error` เป็นด่านสำรองระดับฐานข้อมูล
- **`audit_logs`** บันทึกการอัปโหลดที่ถูกปฏิเสธทุกครั้ง
  (`action: "file_upload_rejected"`) โดยไม่มีเนื้อไฟล์/ชื่อไวรัส/ข้อมูลอ่อนไหว
- **`SubmissionDetailView`** แสดงผลตรวจสอบไฟล์ให้ผู้ส่ง/ผู้ตรวจสอบเห็น

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ตรวจสอบแบบ synchronous ก่อน insert/update แถวเสมอ ไม่สร้าง background job
  queue ใหม่** — โปรเจกต์นี้ไม่มีโครงสร้าง queue อยู่แล้ว การตรวจสอบทันทีใน
  คำขอเดียวกันเพียงพอสำหรับเป้าหมาย (ไม่มีไฟล์ที่ยังไม่ผ่านการตรวจสอบมีแถว
  `research_items` อยู่ได้เลยในสภาวะปกติ)
- **ใช้ Service Role ดาวน์โหลดไฟล์กลับมาตรวจ** (ไม่ใช่ session ผู้ใช้) —
  สอดคล้องกับรูปแบบเดิมของ Signed URL (`lib/supabase/service.ts`)
- **เขียน ClamAV INSTREAM client เองด้วย Node `net`** แทนติดตั้ง library —
  โปรโตคอลไม่ซับซ้อน หลีกเลี่ยง dependency เพิ่มโดยไม่จำเป็น
- **ทดสอบด้วยไฟล์จริงผ่าน Storage จริง** ทั้งไฟล์ถูกต้องและไฟล์ปลอม (เปลี่ยน
  นามสกุลไฟล์ข้อความธรรมดาเป็น `.pdf`) ยืนยันไฟล์ปลอมถูกลบจาก Storage จริงและ
  ไม่มีแถวถูกสร้าง ทดสอบโปรโตคอล ClamAV/HTTP ทั้ง clean/infected ด้วยเซิร์ฟเวอร์
  จำลองจริงในเครื่อง

  `requireMinRank(50)`, ปฏิเสธการรีเซ็ตของตัวเอง, ตรวจข้อความยืนยัน/เหตุผล
  ซ้ำฝั่งเซิร์ฟเวอร์ทุกครั้ง, บันทึก `audit_logs` (`action: "mfa_reset"`),
  ส่ง in-app notification และอีเมลแจ้งเจ้าของบัญชี

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ใช้ Supabase Auth Admin API แทนการรัน SQL ลบ `auth.mfa_factors` ตรงๆ** —
  เป็นความสามารถที่ Supabase Auth รองรับอยู่แล้วจริง (`@experimental` ใน
  supabase-js แต่เป็น REST endpoint จริงของ GoTrue) ได้ผลข้างเคียงที่ต้องการ
  เพิ่มเติมฟรี (ออกจากระบบทุกเซสชันหาก factor เดิมยืนยันแล้ว)
- **Super Admin ห้ามรีเซ็ต MFA ของตัวเอง** — บังคับซ้ำทั้ง UI (ซ่อนปุ่ม) และ
  Server Action (ปฏิเสธหาก `userId` เป้าหมายตรงกับผู้เรียก)
- **พบและแก้ปัญหา `service_role` insert `notifications` ไม่ได้ระหว่างทดสอบจริง**
  (migration `20260806100000_mfa_reset.sql`) — `service_role` มี `BYPASSRLS`
  แต่ยังต้องมี table-level `GRANT` ตามปกติของ Postgres เดิมไม่เคย grant insert
  ให้ role ไหนมาก่อน (insert ได้เฉพาะผ่าน trigger security definer)
- **ทดสอบด่านสิทธิ์ทั้งหมดแบบ black-box จริง** ผ่าน session จริงของบัญชีระดับ
  ต่างๆ ไม่ใช่แค่ตรวจโค้ดด้วยตา — ยืนยันว่า self-reset/non-super-admin/
  ข้อความยืนยันผิดถูกปฏิเสธจริง และ flow ที่ถูกต้องลบ factor จริงพร้อมบันทึก
  audit log และสร้าง notification จริง

## 22. ขอบเขตช่วงพัฒนาที่ 16 (Phase 16 Scope)

ปิดรายการค้างข้อแรกจาก Phase 15 backlog — บังคับ MFA สำหรับบัญชี Super Admin
โดยเฉพาะ (ดูรายละเอียดเต็มที่ `docs/superadmin-guide.md` หัวข้อ 14) บทบาทอื่น
(Member/Staff/Librarian/Admin) ไม่ได้รับผลกระทบ — MFA ยังเป็นทางเลือกเหมือนเดิม

### สิ่งที่พัฒนา
- **`/setup-mfa`** (ใหม่): หน้าบังคับตั้งค่า TOTP — enroll + สแกน QR + ยืนยัน
  รหัส 6 หลัก จัดการ factor ที่ค้างจากการตั้งค่าครั้งก่อนที่ทำไม่เสร็จอย่าง
  ปลอดภัย (unenroll อัตโนมัติก่อนเริ่มรอบใหม่)
- **`lib/supabase/middleware.ts`**: ใช้ `getAuthenticatorAssuranceLevel()`
  ค่าเดียวแยก 2 กรณี — ไม่มี verified factor เลย → เด้งไป `/setup-mfa`, มี
  factor แต่เซสชันนี้ยังไม่ยืนยันขั้นที่สอง → เด้งไป `/mfa-challenge` เหมือนเดิม
- **`app/superadmin/layout.tsx`**: ตรวจ `hasVerifiedMfa` ซ้ำอีกชั้น (defense
  in depth) ลบแบนเนอร์เตือนแบบเดิมออก (กลายเป็น code ที่ไปไม่ถึงแล้ว)
- **`requireMinRank()`**: เมื่อเรียกด้วย `minRank >= 50` ตรวจ `aal2` ซ้ำอีกชั้น
  ก่อนดำเนินการเสมอ — ป้องกันการเรียก Server Action ตรงโดยไม่ผ่านการนำทางหน้า
  ปกติ
- **`/setup-mfa`, `/mfa-challenge`, `/login`**: ยกเว้นจากด่านบังคับ MFA เสมอ —
  แก้ปัญหา chicken-and-egg lockout ด้วยการเว้นหน้าตั้งค่าเองออกจากด่านตรวจสอบ

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **บังคับเฉพาะ Super Admin เท่านั้นตามที่โจทย์กำหนด** — ไม่แตะโครงสร้างของ
  บทบาทอื่นเลย
- **ทดสอบด้วย TOTP code ที่คำนวณจริงจาก secret ผ่าน browser จริง** — ยืนยันครบ
  ทุกสถานการณ์: บล็อกเมื่อไม่มี MFA, ตั้งค่าสำเร็จแล้วเข้าได้จริง, step-up ปกติ
  สำหรับเซสชันใหม่, Server Action ถูกบล็อกที่ `aal1` ผ่านที่ `aal2`, และเซสชัน
  ที่เคยเป็น `aal2` มาก่อนถูกเด้งกลับ `/setup-mfa` ทันทีหลังถูกรีเซ็ต MFA
- **ไม่ต้องตั้งค่า Environment Variable ใหม่ใดๆ** — ใช้ความสามารถ MFA ของ
  Supabase Auth ที่มีอยู่แล้วทั้งหมด

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 17)
- ไม่มีหน้า UI สำหรับ Super Admin สั่งสแกนไฟล์เดิมซ้ำ (rescan)
- ไม่มีหน้าเดียวที่แสดงสถานะ MFA ของ Super Admin ทุกคนพร้อมกัน (ต้องดูทีละคน
  ที่ `/superadmin/users/[id]`)

## 23. ขอบเขตช่วงพัฒนาที่ 17 (Phase 17 Scope)

เพิ่มระบบค้นหาข้อความ *ภายในเนื้อหา* ไฟล์ PDF ของงานวิจัย ต่อยอดจากระบบค้นหา
บรรณานุกรมเดิม (ชื่อเรื่อง/ผู้วิจัย/คำสำคัญ/บทคัดย่อ) ซึ่งยังทำงานเหมือนเดิมทุก
ประการ ขอบเขตครอบคลุมเฉพาะ PDF ที่มีเลเยอร์ข้อความที่คัดลอกได้เท่านั้น (ไม่รวม
ไฟล์สแกนที่ต้องใช้ OCR) — รายละเอียดสถาปัตยกรรมเต็มดูที่
`docs/pdf-full-text-search.md`

### สิ่งที่พัฒนา
- **`research_document_texts`** (ตารางใหม่): เก็บข้อความที่ดึงได้แยกจาก
  `research_items` พร้อม `extraction_status` 5 ค่า (`pending`/`processing`/
  `completed`/`no_text_found`/`failed`), hash/path ของไฟล์ต้นทาง (กันใช้
  ข้อความจากไฟล์คนละเวอร์ชัน), RLS สะท้อนสิทธิ์ของ `research_items` แถวเดียวกัน
  ทุกประการ (รวม `metadata_only` ที่ไม่มีใครเห็นข้อความเลย)
- **`lib/pdf/extract-text.server.ts`**: ดึงข้อความด้วย `pdfjs-dist` (legacy
  Node build) — dependency เดิมจาก Flipbook Viewer ในช่วงที่ 13 ไม่เพิ่ม
  library ใหม่
- **`lib/pdf/process-extraction.server.ts`**: orchestrator ที่ล็อกแบบ atomic
  กันประมวลผลไฟล์เดียวกันซ้ำซ้อน (`acquire_extraction_lock()`), ดาวน์โหลดไฟล์
  ด้วย Service Role, คำนวณ SHA-256, บันทึกผล — ไม่เคย throw error ออกไปหา
  Server Action ที่เรียก (อัปโหลด/เผยแพร่ PDF ไม่มีวันล้มเหลวเพราะดึงข้อความ
  ไม่สำเร็จ)
- **ระบบค้นหา (`lib/data/research-search.server.ts`)**: รวมค้นหาบรรณานุกรมและ
  เนื้อหา PDF เข้าด้วยกัน ใช้ `pg_trgm` (ไม่ใช่ PostgreSQL FTS มาตรฐานเพราะไม่มี
  dictionary ภาษาไทย) จัดลำดับผลลัพธ์: ชื่อเรื่อง > ผู้วิจัย/คำสำคัญ > บทคัดย่อ
  > เนื้อหา PDF แล้วตามด้วยปีเผยแพร่ — ตัด snippet + ไฮไลต์คำที่ตรงด้วยตำแหน่ง
  ดิบฝั่งเซิร์ฟเวอร์ (ไม่ใช้ `dangerouslySetInnerHTML`) ทุก query ผ่าน Supabase
  query builder เท่านั้น
- **`/research`**: เปลี่ยนเป็น Server Component อ่าน `searchParams` โดยตรง
  (แทนการ fetch-all-then-filter ฝั่ง Client แบบเดิม) เพิ่มตัวเลือกโหมด "ทั้งหมด/
  ข้อมูลบรรณานุกรม/เนื้อหา PDF" และตัวกรองระดับการเข้าถึง คงตัวกรองหมวดหมู่/ปี/
  การเรียงลำดับเดิมทั้งหมด
- **`/research/[slug]/read`**: แจ้งสถานะว่าค้นหาเนื้อหาได้หรือไม่ (`completed`)
  หรือเป็นไฟล์สแกน/ไม่มีข้อความ (`no_text_found`) โดยไม่สัญญาว่าจะมี OCR
- **`/dashboard/research/[id]/edit`**: การ์ดสถานะการดึงข้อความ + ปุ่ม
  "ประมวลผลข้อความใหม่" จำกัดเฉพาะ Librarian/Admin/Super Admin (`rank >= 30`)
  ทุกครั้งที่กดบันทึกลง Audit Log (`action: "research_text_reprocess"`)

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **เลือก `pg_trgm` แทน PostgreSQL FTS มาตรฐาน** — FTS ไม่มี dictionary/
  tokenizer ภาษาไทยในตัว ตัดคำผิดเพี้ยนจนค้นหาคำไทยกลางประโยคไม่เจอ ส่วน
  `pg_trgm` ทำงานแบบ substring บน trigram ไม่สนใจภาษา ใช้ได้ทั้งไทย/อังกฤษด้วย
  กลไกเดียวกัน (ข้อแลกเปลี่ยน: ไม่มี relevance ranking จริงแบบ `ts_rank` จึงใช้
  ชั้นความสำคัญคงที่แทน)
- **`ResearchItem.id` คือ slug ไม่ใช่ uuid จริงเป็นธรรมเนียมเดิมของโปรเจกต์**
  (เพื่อ URL ที่เป็นมิตรกับ SEO) แต่ `research_document_texts.research_item_id`
  เป็น uuid จริงเสมอ — ต้องผูก uuid จริงไว้คู่กับทุก object ที่ส่งผ่านฟังก์ชัน
  ค้นหาภายใน และแยกฟังก์ชันอ่านสถานะการดึงข้อความเป็น 2 ตัวชัดเจนตามชนิด id ที่
  รับ (`getExtractionStatus` รับ uuid จริงสำหรับหน้าจัดการที่ `SubmissionItem.id`
  ถูก set เป็น uuid จริงเสมอ, `getExtractionStatusBySlug` รับ slug สำหรับหน้า
  สาธารณะ)
- **ไม่มีโครงสร้าง job queue ในโปรเจกต์นี้** จึงยังดึงข้อความแบบ synchronous ใน
  คำขออัปโหลดเดียวกัน (รูปแบบเดียวกับการตรวจ magic-byte/สแกนมัลแวร์ในช่วงที่ 14)
  แต่ออกแบบ `processResearchDocumentExtraction(researchItemId, pdfPath)` เป็น
  ฟังก์ชันอิสระโดยเจตนา รับพารามิเตอร์ขั้นต่ำ เพื่อย้ายไปเรียกผ่าน queue/
  background worker ได้ในอนาคตโดยไม่ต้องแก้ signature
- **ทดสอบด้วยไฟล์ PDF จริงหลายภาษาและ RLS จริง** — ยืนยันดึงข้อความภาษาลาว/
  ไทย/อังกฤษถูกต้องจากไฟล์จริง 19 หน้าที่เคยอัปโหลดในช่วงที่ 13, จำลอง role
  `anon`/`authenticated` ผ่าน `psql` โดยตรงยืนยันว่า guest มองไม่เห็นเนื้อหาของ
  งาน `member_only` แต่บัญชีระดับ member เห็นได้ปกติ, ทดสอบ retry-after-failed
  จริง (ไฟล์ดาวน์โหลดไม่ได้ → `failed` พร้อมข้อความสุภาพ ข้อความเดิมยังอยู่ครบ
  → ประมวลผลใหม่ด้วยไฟล์จริง → กลับเป็น `completed` ครบทุกฟิลด์)

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 18)
- ไม่รองรับ OCR สำหรับ PDF ที่เป็นภาพสแกน (`no_text_found`) — ดู
  `docs/pdf-full-text-search.md` หัวข้อ 10 สำหรับแนวทางที่เป็นไปได้ในอนาคต
- ไม่มีปุ่ม "ประมวลผลข้อความ PDF ใหม่ทั้งหมดพร้อมกัน" (bulk backfill) — ต้องทำ
  ทีละรายการผ่านหน้าจัดการ
- การดึงข้อความยังรัน synchronous ในคำขออัปโหลดเดียวกัน — บน Serverless
  platform ที่มี hard timeout ไฟล์ PDF ขนาดใหญ่มากอาจดึงข้อความไม่ทัน (ไม่กระทบ
  ความสำเร็จของการอัปโหลดไฟล์เอง)
- ไม่มีหน้า UI สำหรับ Super Admin สั่งสแกนไฟล์เดิมซ้ำ (rescan) — ค้างจาก Phase
  17 (ดู `docs/file-security.md` หัวข้อ 7)

## 24. ขอบเขตช่วงพัฒนาที่ 18 (Phase 18 Scope)

เพิ่มระบบขอสิทธิ์เข้าถึงเอกสาร (สำหรับ `read_only`/`metadata_only` ที่ทุกคน
เห็นแถวได้แต่เนื้อหาถูกจำกัดเหมือนกันหมด) และระบบติดตามหมวดหมู่เพื่อรับแจ้ง
เตือนงานวิจัยใหม่ ต่อยอดจากระบบสิทธิ์ (`access_level`) และการแจ้งเตือน
(`notifications`) เดิมโดยไม่แก้ไขพฤติกรรมเดิมแม้แต่จุดเดียว — รายละเอียด
สถาปัตยกรรมเต็มดูที่ `docs/document-access-requests.md`

### สิ่งที่พัฒนา
- **4 ตารางใหม่**: `access_requests` (คำขอ 7 สถานะ), `document_access_grants`
  (สิทธิ์ที่อนุมัติแล้วจริง — ถาวรหรือมีวันหมดอายุ, แยกจากคำขอ),
  `notification_preferences` (4 สวิตช์ต่อผู้ใช้), `category_subscriptions`
  (หมวดหมู่ที่ติดตาม) — กันคำขอ/สิทธิ์ active ซ้ำซ้อนด้วย partial unique index
  ระดับฐานข้อมูล
- **`document_access_grants` เป็นชั้นสิทธิ์เสริมที่ OR เข้ากับ
  `canReadOnline`/`canDownload(access_level)` เดิมเท่านั้น** —
  `getResearchReadUrl`/`getResearchDownloadUrl` (Phase 3) เพิ่มพารามิเตอร์
  `hasReadGrant`/`hasDownloadGrant` (ค่าเริ่มต้น `false`) โดยไม่แก้ไข logic
  เดิมเลย ไม่เปลี่ยน `access_level` หลักของเอกสารไม่ว่ากรณีใด
- **หน้ารายละเอียดงานวิจัย**: ปุ่มขอสิทธิ์อ่าน/ดาวน์โหลด เฉพาะเมื่อยังไม่มี
  สิทธิ์จริง (Guest พาไป login ก่อน) — `/access-requests` (สมาชิก) และ
  `/dashboard/access-requests` + `/dashboard/access-requests/[id]`
  (เจ้าหน้าที่ rank ≥ 30: อนุมัติ/ปฏิเสธ/ขอข้อมูลเพิ่ม/เพิกถอน ทุกการกระทำ
  บันทึก Audit Log)
- **`/profile/notification-settings`**: ติดตาม/เลิกติดตามหมวดหมู่ + เปิด/ปิด
  ช่องทางแจ้งเตือน — **`/notifications`**: หน้าแจ้งเตือนทั้งหมด
- **แจ้งเตือนผู้ติดตามหมวดหมู่เมื่อเผยแพร่งานวิจัยใหม่**: in-app ผ่านการขยาย
  trigger `log_research_status_change()` เดิม (Phase 3) — email ส่งจาก
  Server Action โดยตรง (trigger เรียก HTTP ไม่ได้) กันแจ้งซ้ำเมื่อเอกสารอยู่
  หลายหมวดหมู่

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **ไม่แก้ไข RLS การมองเห็นแถวของ `research_items` เลยแม้แต่จุดเดียว** —
  `member_only`/`staff_only` ยังมองไม่เห็นทั้งแถวสำหรับ rank ไม่ถึงเหมือนเดิม
  (เห็นแถวได้ = มีสิทธิ์เต็มอยู่แล้ว เพราะ `canReadOnline`/`canDownload` ไม่
  เช็ค rank) ระบบคำขอสิทธิ์จึงมีผลจริงกับ `read_only`/`metadata_only` เป็นหลัก
  โดยไม่ต้องแตะระบบสิทธิ์เดิมเลย
- **พบและแก้ RLS gap ระหว่างพัฒนา**: กลไก lazy-expire (ไม่มี job queue/cron
  ในโปรเจกต์นี้ จึงเช็คคำขอที่หมดอายุแบบ lazy ทุกครั้งที่เปิดหน้ารายการ) ใช้
  ไม่ได้เมื่อสมาชิกทั่วไปเปิดหน้าเอง เพราะ RLS เดิมอนุญาตแค่ pending→cancelled
  — เพิ่มนโยบาย `access_requests_self_expire` (เฉพาะ approved→expired ที่
  หมดอายุจริงตามเวลาเท่านั้น) ทดสอบยืนยันแล้วทั้งสองฝั่ง
- **ไม่ใช้ Service Role เลยในฟีเจอร์นี้** — ต่างจาก Phase 17 ที่ต้องใช้สำหรับ
  ดาวน์โหลดไฟล์มาประมวลผล ฟีเจอร์นี้ไม่มีขั้นตอนที่ต้องข้าม RLS เลย ทุก
  query/mutation ผ่าน client ของผู้ใช้เอง
- **ทดสอบด้วย session จริงของบัญชีหลายระดับผ่าน HTTP จริง**: Guest ถูกพาไป
  login, Member ส่ง/ยกเลิกคำขอได้เฉพาะของตัวเอง, มองไม่เห็นคำขอผู้อื่น
  (ยืนยันซ้ำผ่าน RLS simulation ด้วย `psql`), Librarian อนุมัติ/ปฏิเสธ/ขอ
  ข้อมูลเพิ่ม/เพิกถอนได้จริงพร้อม Audit Log, อนุมัติ "อ่าน" ไม่ให้สิทธิ์
  "ดาวน์โหลด" โดยอัตโนมัติ, สิทธิ์หมดอายุ/ถูกเพิกถอนแล้วเข้าถึงไฟล์ไม่ได้ทันที,
  แจ้งเตือนผู้ติดตามหมวดหมู่ถูกต้องทั้ง in-app และอีเมล

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 19)
- คำขอที่ `approved` แต่หมดอายุแล้วอาจแสดงสถานะค้างชั่วคราวจนกว่าจะมีใครเปิด
  หน้ารายการคำขอ (lazy expire — ไม่กระทบการตรวจสอบสิทธิ์จริงตอนสร้าง Signed
  URL) — ดู `docs/document-access-requests.md` หัวข้อ 6
- เผยแพร่งานวิจัยผ่านการสร้างใหม่โดยตรง (ไม่ผ่าน workflow อนุมัติ) ไม่ส่ง
  อีเมลแจ้งผู้ติดตามหมวดหมู่ (ข้อจำกัดเดียวกับ `approval_logs`/`audit_logs`
  ตั้งแต่ Phase 3)
- ไม่รองรับ OCR สำหรับ PDF ที่เป็นภาพสแกน — ค้างจาก Phase 17
- ไม่มีหน้า UI สำหรับ Super Admin สั่งสแกนไฟล์เดิมซ้ำ (rescan) — ค้างจาก Phase
  17

## 25. ขอบเขตช่วงพัฒนาที่ 19 (Phase 19 Scope)

เพิ่มระบบผู้วิจัย/หน่วยงานมาตรฐาน (authority control) รองรับ ORCID และตรวจจับ
งานวิจัยที่อาจซ้ำ พร้อมกลไกรวมข้อมูล (merge) ที่ปลอดภัยสำหรับผู้วิจัย หน่วยงาน
และงานวิจัย — ไม่มีการรวมข้อมูลอัตโนมัติที่ไหนเลย ทุกการรวมต้องยืนยันจาก
เจ้าหน้าที่และบันทึก Audit Log เสมอ รายละเอียดสถาปัตยกรรมเต็มดูที่
`docs/data-quality.md` และ `docs/orcid-integration.md`

### สิ่งที่พัฒนา
- **`authors`**: เพิ่ม `display_name_en`, `normalized_name_th/en` (auto
  ผ่าน trigger), `title_prefix_th/en`, `orcid` + `orcid_verified_at`,
  `biography`, `is_active`, `merged_into_author_id` — คอลัมน์ `name` เดิมยัง
  เป็น "ชื่อแสดงผลไทย" เหมือนเดิม ไม่เพิ่มคอลัมน์ซ้ำซ้อน
- **`organizations`**: เพิ่มโครงสร้างหลัก/ย่อยด้วย `parent_id` (ชื่อเดียวกับ
  `categories.parent_id` เดิม) พร้อม trigger กัน cycle แบบเดียวกัน,
  `organization_code`, `website_url`, `merged_into_organization_id`
- **`research_authors.author_role`**: `principal_investigator`/
  `co_investigator` กำหนดอัตโนมัติจากลำดับผู้วิจัยในฟอร์มเดิม (คนแรก = ผู้วิจัย
  หลัก) ไม่แก้ไข UI ฟอร์มส่งงานวิจัยสาธารณะ
- **ORCID**: ตรวจรูปแบบ + checksum (ISO 7064 MOD 11-2) ฝั่งแอปพลิเคชันก่อน
  บันทึกเสมอ, unique index กันซ้ำ (ยกเว้นแถวที่ถูกรวมแล้ว), ลิงก์ไป orcid.org,
  เจ้าหน้าที่ยืนยันด้วยตนเองได้ — ยังไม่เชื่อม ORCID API/OAuth จริง
- **ตรวจสอบงานวิจัยซ้ำ**: `find_similar_research_items()` (SQL, `pg_trgm` +
  ISBN/DOI/PDF hash + ผู้วิจัยหลัก) คำนวณคะแนน/เหตุผลฝั่งแอปพลิเคชัน บันทึกลง
  `duplicate_research_reviews` อัตโนมัติหลังส่ง/แก้ไขงานวิจัย (เฉพาะชื่อ
  เรื่อง/ปีเปลี่ยน) ไม่เคยบล็อกการบันทึก
- **`/dashboard/authors`, `/dashboard/authors/[id]`, `/dashboard/organizations`
  (ขยายเดิม), `/dashboard/data-quality`, `/dashboard/duplicate-reviews`,
  `/dashboard/duplicate-reviews/[id]`**: ค้นหา/เพิ่ม/แก้ไข/ปิดใช้งาน คำเตือน
  ชื่อซ้ำ, เปรียบเทียบ+รวมงานวิจัยสองรายการ, รายงานข้อมูลขาดหาย

### การตัดสินใจด้านเทคนิคที่สำคัญ
- **Merge ทั้งสามแบบเป็น PostgreSQL function (`security definer`) ไม่ใช่
  TypeScript หลายคำสั่งต่อกัน** — รับประกัน atomic transaction เมื่อย้ายความ
  สัมพันธ์หลายตารางพร้อมกัน แต่ละฟังก์ชันตรวจสอบสิทธิ์ rank ซ้ำในตัวเองเสมอ:
  รวมผู้วิจัย/หน่วยงาน rank ≥ 30 (Librarian), รวมงานวิจัย rank ≥ 40 (Admin —
  กระทบความสัมพันธ์กว้างกว่ามาก: favorites, ประวัติการอ่าน/ดาวน์โหลด, คำขอ
  เข้าถึงเอกสาร, สิทธิ์ที่อนุมัติแล้ว, ข้อความ PDF ที่ดึงไว้)
- **พบและแก้ RLS gap ระหว่างพัฒนา 2 จุด**: ลืม grant `insert` บน
  `duplicate_research_reviews` (มีแค่ select/update) ทำให้การตรวจจับอัตโนมัติ
  ล้มเหลวเงียบๆ และนโยบาย update เดิมสงวนที่ rank ≥ 30 ขัดกับการ upsert
  อัตโนมัติจากผู้ส่งงานวิจัยที่ rank ≥ 20 — แก้ด้วยนโยบายแยกสำหรับ "ระบบ
  refresh คะแนนอัตโนมัติ" จำกัดเฉพาะแถวสถานะ `pending` เท่านั้น
- **`getResearchById` เดิมกรอง `status = 'published'` ในฟังก์ชันใช้ร่วม จึงไม่
  เคยคืนรายการที่ `status = 'merged'`** — เพิ่ม `getMergedRedirectSlug()`
  แยกต่างหาก เรียกเฉพาะตอนหารายการปกติไม่เจอ แทนการแก้ query หลักที่ใช้ร่วม
  ทั่วระบบ (เสี่ยงกระทบหน้าค้นหา/รายการเกี่ยวข้อง) — ทดสอบยืนยันแล้วว่าทั้งหน้า
  รายละเอียดและหน้าอ่าน PDF redirect ไปยังรายการหลักถูกต้อง
- **ทดสอบด้วย session จริงของบัญชีหลายระดับผ่าน HTTP จริง**: ORCID ผิดรูปแบบ/
  checksum/ซ้ำถูกปฏิเสธถูกต้อง, รวมผู้วิจัยที่มีความสัมพันธ์ชนกันแก้ conflict
  ถูกต้องและย้ายรายการที่ไม่ชนกันถูกต้อง, รวมงานวิจัยย้าย favorites/ประวัติ
  การอ่านถูกต้องครบ (รวมกรณี conflict), Librarian ถูกปฏิเสธเมื่อพยายามรวม
  งานวิจัย (ต้อง Admin), โครงสร้างหน่วยงานหลัก/ย่อยกัน cycle ได้จริง

### สิ่งที่ยังไม่พัฒนาในช่วงนี้ (Phase 20)
- ไม่มีปุ่ม "ตรวจสอบงานวิจัยซ้ำย้อนหลังทั้งระบบ" — ดู `docs/data-quality.md`
  หัวข้อ 6
- ยังไม่ได้เชื่อมต่อ ORCID API/OAuth จริง — ดู `docs/orcid-integration.md`
  หัวข้อ 3
- เกณฑ์คะแนน/น้ำหนักการตรวจงานวิจัยซ้ำเป็นค่าคงที่ ยังไม่มีหน้าตั้งค่า
- คำขอที่ `approved` แต่หมดอายุแล้วอาจแสดงสถานะค้างชั่วคราว — ค้างจาก Phase 18
- ไม่รองรับ OCR สำหรับ PDF ที่เป็นภาพสแกน — ค้างจาก Phase 17
- ไม่มีหน้า UI สำหรับ Super Admin สั่งสแกนไฟล์เดิมซ้ำ (rescan) — ค้างจาก Phase
  17
